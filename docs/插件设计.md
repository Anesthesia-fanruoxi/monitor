# 插件设计

> 定位：**一个只做采集、只输出明文 JSON 的独立进程。**
> 读者：写插件的人（可能是你，也可能是别人用别的语言写）。
> 相关文档：`docs/插件化架构设计.md`（协议与决策）、`docs/壳设计.md`（对端行为）、`docs/服务端设计.md`（下游消费者）。
> 本文只讲插件，不重复论证架构选择的理由。

---

## 一、插件是什么 / 不是什么

| 是 | 不是 |
|---|---|
| 一个**独立可执行文件**，由壳拉起并常驻 | 不是一个库（绝不链接进壳） |
| 从 stdin 读一行 JSON、往 stdout 写一行 JSON | 不认识网络、不认识 URL、不认识密钥 |
| 只输出**明文**指标数据 | 不做压缩、不做加密、不做重试 |
| 日志一律走 stderr | 不往 stdout 写任何非协议内容 |
| 采集、解析、单位换算、差值计算都在这里 | 不做聚合、不做判断、不做告警 |
| 可以跨轮缓存状态（长驻进程） | 不允许依赖其它插件 |

**加解密与上报只在壳里做一次**：如果每个插件各自实现一遍 AES-GCM + gzip + HTTP，你会得到 N 份各不相同的重试、超时、密钥处理逻辑，将来换协议要改 N 个地方。插件作者只需要会打印 JSON。

## 二、目录与制品布局

### 2.1 仓库内（源码）

```
agent-plugs/
├── go.mod                      # module: agent-plugs
├── sdk/                        # 插件 SDK（Go 版）
│   ├── plugin.go               #   Run / Plugin 接口 / 协议分发
│   ├── config.go               #   读 config.yaml 的 plugins.<name>（带 mtime 缓存）
│   ├── stdout_guard.go         #   把 fmt.Println 重定向到 stderr
│   └── README.md               #   面向非 Go 语言的协议说明
├── hard/
│   ├── main.go                 #   采集逻辑
│   └── default.yaml            #   默认配置（随制品分发）
├── nginx/  ssl/
├── k8s/                        # 原 k8sContainer + k8sController 合并
│   ├── main.go
│   └── default.yaml
├── build.sh                    # 交叉编译 + 打包 + 生成 index.json
└── dist/                       # 构建产物（gitignore）
```

### 2.2 制品包（分发单元）

整包分发，**不允许只发二进制**——否则会出现"新二进制配旧默认配置"的版本错配：

```
hard-1.2.0-linux-amd64.tgz
├── hard                # 二进制
├── default.yaml        # 默认配置（升级时随包覆盖）
└── manifest.yaml       # 名称/版本/平台/入口/协议版本/min_agent_version
```

`manifest.yaml`：

```yaml
name: hard
version: 1.2.0
proto: 1
platform: linux/amd64
entry: hard
min_agent_version: 1.0.0

# 采集周期与注销阈值：壳唯一的调度参数来源，config.yaml 可覆盖（§3.6）
default_interval: 15s
default_timeout: 45s

remote_config_keys: []      # 预留：声明哪些配置键可以被外部覆盖
```

**`default_interval` / `default_timeout` 与 `version` 一样是制品元信息**：`cat manifest.yaml` 就能审计这个插件的采集节奏，不用启动进程——而排障的时候插件往往正好起不来。壳在这里读到周期与阈值后，做三级取值（config 覆盖 → manifest → 兜底）并过钳制表，然后才交给调度器（`壳契约-v1.md` §9）。

### 2.3 部署机上（运行期，由壳生成）

```
<agent 二进制目录>/
├── agent
├── config.yaml
└── agent-plugs/
    ├── hard/
    │   ├── hard                # 二进制（从 service 下载）
    │   ├── manifest.yaml       # 制品自带
    │   └── default.yaml        # 制品自带（升级时覆盖，用户不要改）
    └── ssl/
```

**没有 `.state/` 目录，也没有 `effective.yaml`**：壳不保存业务状态、也不生成派生配置，已装版本直接读 `manifest.yaml`（`壳契约-v1.md` §9.1）。

## 三、协议（插件侧视角）

传输：**纯 stdio，按行 JSON**。壳写一行到插件 stdin，插件写一行到 stdout，必须以 `\n` 结尾并 flush。

### 3.1 三段命令

```jsonc
// ← 壳发：握手（启动后第一条）。只带协议版本——插件不需要知道自己在哪个项目下
{"id":1,"cmd":"hello","proto":1}

// → 插件回：只需报协议版本。名字、版本、周期都在 manifest.yaml 里，壳自己读
{"id":1,"ok":true,"proto":1}

// ← 壳发：采集（每轮一次）。只有命令本身，**不注入任何参数**（§3.7）
{"id":2,"cmd":"collect"}

// → 插件回：明文指标
{"id":2,"ok":true,"metrics":[ /* DeclaredMetric[]，见 §3.2 */ ]}

// ← 壳发：优雅退出
{"id":3,"cmd":"shutdown"}
{"id":3,"ok":true}
```

**响应里总共 4 个字段，3 个是传输语义**（`id` / `ok` / `proto`），**只有 1 个承载数据**（`metrics`）。插件名、版本、采集周期、注销阈值、诊断状态**一律不在响应里**——理由见 §3.6。

### 3.2 指标声明（线格式，**由 SDK 生成，你不手写**）

**这段 JSON 是线格式，不是你要写的东西。** 你在插件代码里声明指标、填值（§4.2 ①），SDK 收集完整轮数据后把它序列化成下面这个形状：

```json
{
  "name": "cpu_percent",
  "help": "CPU 使用率百分比",
  "type": "gauge",
  "labels": ["hostName", "cpu_model", "os_version", "kernel_version"],
  "common": {"cpu_model": "Xeon Gold 6248", "os_version": "Rocky 10", "kernel_version": "5.14.0"},
  "timeout": "45s",
  "samples": [{"labels": {"hostName": "web-01"}, "value": 12.3}]
}
```

| 字段 | 谁填 | 说明 |
|---|---|---|
| `name` / `help` / `labels` / `type` | 你（声明时一次） | SDK 累积，**每轮原样重发** |
| `timeout` | **SDK 自动填** | 来自 manifest 的 `default_timeout`（由壳注入，见 §3.6）；个别指标要不同值时用 `g.Timeout(d)` 覆盖 |
| `common` | **SDK 自动推导** | 某标签在该指标**全部样本**上取值相同时自动提到这里（§4.2 ①） |
| `samples[].labels` | 你（填值时） | 只放各样本**不同**的那部分标签 |
| `samples[].value` | 你（填值时） | |

**`common` 的自动推导是纯报文优化**：不改变语义（服务端把 `common` 与 `samples[].labels` 合并后再写序列），但能把"每台机器重复 32 遍的 `cpu_model`"压成一份。1500 台的量级下这是实打实的带宽，也是 §6.7「减小载荷」里最容易拿到的一项。

### 3.3 四条不可动摇的约定

1. **`project` 绝不出现在 `labels` / `common` / `samples` 里**。它只有两个来源，都在壳与 service 侧：**壳**从 `config.yaml` 读出来写进上报报文，**service** 再把它注入成标签。**插件从头到尾不知道 project**——同一份插件二进制要能装在任意项目的任意机器上，所以它不该有任何"我属于哪个项目"的知识，实测也没有任何地方用得上它（§3.7）。
2. **标签用 map 不用数组**。数组要求两端顺序严格一致，错位就是静默的数据错乱（主机名被当成内核版本）。
3. **指标声明里的 `timeout` 由 SDK 自动填，你不用写**。它来自 `manifest.yaml` 的 `default_timeout`（`config.yaml` 可覆盖），由壳注入给 SDK；规则是**必须 ≥ 3 × 采集周期**。这条经验来自现状的 bug：`k8s/k8sController` 曾用 45s 阈值配 60s 周期，时间序列在两次上报之间被摘掉，Prometheus 抓到断点——**现在周期与阈值同源（同一份 manifest），这类不一致在结构上不会发生了**。
4. **描述必须是常量**。`name` / `help` / `labels` 在任何一轮都不能变（变了就被当成另一条指标）。特别地：**`help` 里绝不能拼时间戳、主机名、轮次号**——那会让服务端每轮都判定"形状变了"，反复注销重建 `GaugeVec` 并清空该指标全部时间序列，曲线碎成渣。这条不是服务端的限制，是 SDK 的硬性要求（§4.2 ①）。

### 3.4 协议不匹配时

- 插件 `proto > 壳支持的版本` → 壳**显式拒绝启动**该插件并报"需升级 agent"，不会静默降级。
- 插件少报 `metrics` → 合法，视为"本轮没采到"，**不算失败**。
- 插件少报 `ok` / `id` / `proto` → 壳按契约 §2.2 的宽容规则兜底，插件不会因为漏字段而起不来。

### 3.5 无并发

一个插件进程同一时刻只处理一个 `collect`。壳会保证上一轮结束后才发下一轮；如果上一轮没结束，壳直接跳过本轮（并计数）。

**这简化了插件实现**：不需要保护自己的状态，跨轮缓存可以直接用普通变量。

### 3.6 为什么响应里只有一个数据字段

这是本设计里最反直觉的一条：**插件不报自己的名字、版本、采集周期、注销阈值**。它们全部来自静态声明：

| 信息 | 以前在报文里 | 现在从哪来 |
|---|---|---|
| 插件名 | `hello` 响应 | `config.yaml` 的键名 / 目录名 |
| 版本 | `hello` 响应 | `manifest.yaml` 的 `version` |
| 采集周期 | `hello` 响应 | `manifest.yaml` 的 `default_interval`，`config.yaml` 可覆盖 |
| 注销阈值 | 每个指标自报 | `manifest.yaml` 的 `default_timeout`，同上 |
| 诊断信息 | `collect` 响应的 `status` | **不报了**，写日志 |

**分工因此可以压缩成一句话：插件只管产出数据，其余全由壳决定。**

两个好处都很实际：

1. **可审计**：`cat manifest.yaml` 就知道这个插件打算多久采一次。运行时自报的值，**不启动进程就看不到**——而排障的时候，插件往往正好起不来。
2. **周期成为运维参数**：某台机器 I/O 重，你想把它的采集周期从 15s 放宽到 60s，改 `config.yaml` 即可，不用碰插件、不用重新发布。

**插件知道、但壳拿不到的信息，写日志就够了。** 曾经有一个 `status` 字段专门传这类信息（"kubeconfig 里的证书 11 月到期"、"`ss` 命令不存在"），后来被整体砍掉，因为终点不对：`stderr` 由壳逐行加 `[plugs/<name>]` 前缀转发进日志，状态端点里也能看到壳记录的 `last_error`；为此多背一个协议字段、一条 1 KiB 钳制、一份 SDK 状态缓冲区并不划算（`壳契约-v1.md` §2.5）。

遇到问题时该怎么做：

| 你想表达 | 正确做法 |
|---|---|
| 一个**数值事实**（磁盘快满、证书剩余天数） | 做成指标——Grafana 能画、Alertmanager 能告警 |
| **为什么这轮没数据**（依赖命令不存在、kubeconfig 读不到） | 写 `stderr`，壳会带插件名前缀转发 |
| 一个需要跨轮观察的状态 | 做成指标（gauge 天然表达"当前值"） |

> **一条硬纪律：采集失败时要报 failure，不要报 0。** 因为**失败时的 `0` 和真实的 `0` 在指标上一模一样**，看面板的人分不出来。正确做法是回 `ok:false`（这一轮不发数据），并往 `stderr` 写一行原因。

### 3.7 插件需要的东西从哪来（**不靠注入**）

"谁提供什么"是实现插件时最容易搞混的一点。规则只有一句：

> **壳只注入"壳算出来才有的值"（配置路径、周期、阈值），业务事实一律插件自取。**

| 值 | 谁提供 | 怎么拿 |
|---|---|---|
| 自己的配置（值） | 壳给**文件路径**，合并由 SDK 做 | `sdk.Config()` 读 `MONITOR_CONFIG` 指向的 `config.yaml`，取 `plugins.<name>` 子树并与制品的 `default.yaml` 合并（§4.2 ⑤） |
| 生效的周期 / 阈值 | 壳 | `sdk.Interval()` / `sdk.Timeout()`（§4.2 ⑤）——只有壳做过三级取值与钳制 |
| **`project`** | **壳，且只留在壳内** | 插件**不需要也不知道**它。壳从 `config.yaml` 读出来写进上报报文，service 再注入成标签（§3.3 第 1 条） |
| **主机名** | **插件自己** | `sdk.Hostname()`：`os.Hostname()`，失败退回 `/etc/hostname`，带 5 分钟缓存。它就是 `hostName` 标签的值 |
| 其它本机事实（`cpu_model`、`os_version`、`kernel_version`……） | **插件自己** | 读 `/proc`、`sysfs`、执行命令 |

**这套分法的实际好处**：`collect` 请求就是 `{"id":2,"cmd":"collect"}`（§3.1），壳不需要在每轮往插件里塞东西；插件进程环境里也没有 `MONITOR_PROJECT` / `MONITOR_HOSTNAME` / `MONITOR_AGENT_VERSION`。插件因此能**脱离壳单独跑**（`./hard --selftest` 不需要任何注入就有完整输出），壳也少了一处"注入错了会让全网采集器一起出错"的风险面。

**一处必须知道的约束**：`hostName` 也出现在壳内的心跳指标（`heart`）里，两处必须由**同一套算法**得出（壳里另有一份实现——契约 I3 不允许壳依赖 SDK）。所以 `Hostname()` 不要改成"环境变量优先"这类玩法：一旦两边不一致，面板上同一台机器会分裂成两个主机名。

## 四、SDK（Go 版）

### 4.1 接口：**指标声明写在采集逻辑旁边**

这是整套设计里对"只改一处"贡献最大的一步——`Collect` **不返回指标结构体**，它只填值；描述由 SDK 自动收集（§4.2 ①）：

```go
package sdk

// Plugin 是插件要实现的一切。没有 Meta()——名字、版本、周期都不由插件声明（§3.6）。
type Plugin interface {
    Collect(ctx context.Context) error      // 只返回 error，不返回指标
}

// 声明指标并取得句柄。同一轮内同名重复调用返回同一句柄，不报错。
func Gauge(name, help string, labels ...string) *Gauge

// 给某个指标单独指定注销阈值（可选，不调就用壳注入的默认阈值）
func (g *Gauge) Timeout(d time.Duration) *Gauge

// 按声明顺序给出该指标的标签值，定位到一条样本
func (g *Gauge) WithLabelValues(values ...string) *Gauge

// 写入 / 覆盖这条样本的值
func (g *Gauge) Set(v float64)

// Run 阻塞运行直到收到 shutdown 或 stdin 关闭
func Run(p Plugin)
```

一个完整的插件：

```go
package main

import (
    "context"
    "strconv"

    "agent-plugs/sdk"
)

type hardPlugin struct{ startedAt time.Time /* 跨轮状态放这里 */ }

func (p *hardPlugin) Collect(ctx context.Context) error {
    // 指标名、说明、标签，就和采集逻辑写在一起——没有第二份定义
    cpu := sdk.Gauge("cpu_percent", "CPU 使用率百分比", "cpu")
    for _, c := range readCPUTimes() {
        cpu.WithLabelValues(strconv.Itoa(c.ID)).Set(c.Percent)
    }

    mem := sdk.Gauge("memory_used_percent", "内存使用率百分比")
    mem.Set(usedPercent)      // 无标签指标直接 Set

    return nil
}

func main() { sdk.Run(&hardPlugin{}) }
```

**注意这个文件里没有的东西**：没有 `version` 常量（在 `manifest.yaml`）、没有 `Interval` / `Timeout`（同上）、没有指标名清单（SDK 自动收集）、没有状态上报调用（写 `stderr`）。这个插件文件里只剩下**采集逻辑本身**。

**几个要点：**

- **`sdk.Gauge(...)` 写在 `Collect` 里，不写成包级变量。** 每轮重新声明是刻意的：它让定义与采集物理相邻，改采集逻辑时顺手就看到定义。重复声明由 SDK 去重，零成本。
- **`WithLabelValues` 只给 `labels` 的值**，`common` 由 SDK 推导（§3.2），你不用管。
- **全系统只有 `Gauge`**。没有 Counter / Histogram / Summary——理由见 `插件化架构设计.md §3.3` 与服务端 `Modles/declarative.go` 的注释（Prometheus 侧靠 `rate()` 从累积值算速率，Agent 侧不需要维护累加器，重启即清零的状态也更少）。
- **同一 key 后写覆盖先写**（一轮内同标签组合只产出一条样本）。

**由此得到的效果**：新增一个指标 = 在 `Collect` 里加一行 `sdk.Gauge(...)` + 填值，**服务端一个字不动、不改配置、不重启**。而"改了代码忘了改定义"这种事在结构上不可能发生——因为定义就在那行。

### 4.2 SDK 必须做的五件事

**① 声明收集器（`metrics.go`）——最重要的一条**

这是"指标定义只写一处"能成立的全部原因。SDK 维护一份**每轮重置**的注册表，`Gauge()` 声明时登记，`Set()` 累加样本，`Collect` 返回后由 `Run` 序列化成 `[]DeclaredMetric` 并把缓冲区清空：

```go
type spec struct {
    Name, Help string
    Labels     []string
    Timeout    time.Duration        // 零值则用壳注入的默认阈值（§3.6）
    Samples    map[string]sample    // 标签值拼接 key → 样本，后写覆盖先写
    order      []string             // 首次出现顺序，保证输出稳定（便于比对与测试）
}
```

三条实现纪律：

1. **重复声明同名指标返回同一句柄，不报错。** 因为 `sdk.Gauge(...)` 是写在 `Collect` 里的（§4.1），每轮都会重新声明——这是刻意的，不是妥协。
2. **`common` 自动推导**：一轮结束后，某标签在该指标**全部样本**上取值一致 → 提到 `common`；否则留在 `samples[].labels`。只剩一条样本时直接进 `common`（两种写法语义等价，进 `common` 更省字节）。
3. **由 `Run` 在调用 `Collect` 之前重置缓冲区**，不是之后。这样即使某轮 `Collect` panic，也不会把上一轮的残留数据混进本轮（壳那边看到的是 `ok:false`，不取数据）。`Collect` 是串行的（§3.5），但仍要一把 mutex——插件作者可能在 `Collect` 里起 goroutine 并发填值。

**② 保护协议流（`stdout_guard.go`）**

插件作者一行 `fmt.Println("debug")` 就会污染协议流，导致壳判定失败。SDK 在 `Run()` 开头把 `os.Stdout` 换成一个管道，只留一个私有 fd 给自己写协议，管道内容转发到 stderr：

```go
func guardStdout() (protoOut *os.File, restore func()) {
    real := os.Stdout
    r, w, _ := os.Pipe()
    os.Stdout = w                 // 此后所有 fmt.Println 都进管道
    go io.Copy(os.Stderr, r)      // 管道内容转发到 stderr
    return real, func() { w.Close(); r.Close(); os.Stdout = real }
}
```

约 15 行，但它把"插件作者犯错"的后果从"采集器静默失效"降级为"日志里多一行"。

**③ 日志重定向**：`log.SetOutput(os.Stderr)`。协议流只属于 SDK。

**④ collect 内 panic 不能杀进程**：

```go
defer func() {
    if r := recover(); r != nil {
        reply(Envelope{ID: id, OK: false, ...}, fmt.Errorf("collect panic: %v", r))
    }
}()
```

一个采集逻辑的 bug 应该是「这一轮失败」，而不是「采集器消失」。

**⑤ 读取配置、壳算出的值与本机事实（`config.go` / `host.go`）**

```go
// 配置：读 agent 的 config.yaml，取 plugins.<name> 子树，与制品 default.yaml 合并（规则见下）
func Config() *Conf                        // 带 mtime 缓存；每轮 Collect 调一次
func (c *Conf) String(key, def string) string
func (c *Conf) Int(key string, def int) int
func (c *Conf) Duration(key string, def time.Duration) time.Duration
func (c *Conf) StringSlice(key string, def []string) []string

// 壳注入的调度参数：manifest 默认值 + config 覆盖 + 钳制之后的最终值（§3.6）
func Interval() time.Duration              // MONITOR_PLUGIN_INTERVAL
func Timeout() time.Duration               // MONITOR_PLUGIN_TIMEOUT：SDK 用它填 DeclaredMetric.timeout

// 本机事实，不经注入：os.Hostname() → /etc/hostname 兜底 → 5 分钟缓存（§3.7）
func Hostname() string
```

**`Interval()` 只给插件自己安排跨轮逻辑用**（比如"每 4 轮做一次全量扫描"）；**调度是壳的事，插件不需要知道下一轮什么时候来**。

**SDK 里要做的那点合并逻辑**（就这一处，插件作者不写代码）：

```
config.yaml 的 plugins.<name>.*   ← 用户，优先（跳过壳保留键 enable / interval / timeout）
        ↓ 覆盖
制品目录里的 default.yaml          ← 插件作者，升级时随包覆盖
        ↓ 覆盖
Conf 调用点传的 def 参数            ← 代码里，最低
```

- **插件名从哪来**：`MONITOR_PLUGIN_DIR` 的 basename（壳保证目录名 == `config.yaml` 里的键名 == `manifest.name`）。目录被手改名时会查不到配置——此时 SDK **回落为纯 `default.yaml`** 并在 `stderr` 打一行 `plugin config not found: <name>`，**不退出**（脱壳自测时这就是正常路径）。
- **浅合并**（顶层键整体覆盖，不做递归合并）。要改 `k8s` 的 namespace 白名单就得写全整个列表——可预测优先于聪明。
- **壳保留键不进入插件可见范围**：`enable` / `interval` / `timeout` 由 SDK 读取时跳过。这三个键的名字与 `plugins` 容器键名是壳与插件共享的契约，改它要同步 SDK（`壳契约-v1.md` §12 第 1 条）。
- **读不到 `config.yaml` 时**（脱壳自测没指路）行为同上：只用 `default.yaml` + 一行 `stderr`。

**带 mtime 缓存**：每轮 collect 调一次 `Config()`，只有文件改动才重新解析。**改配置不重启插件，也不需要壳做任何中转**——用户改 `config.yaml`，下一轮 collect 插件自己就读到新值（`壳契约-v1.md` §9.1）。

### 4.3 壳注入哪些环境变量（只有下面这些）

| 变量 | 内容 | 为什么必须由壳给 |
|---|---|---|
| `MONITOR_CONFIG` | agent `config.yaml` 的绝对路径 | 只有壳知道它被 `-c` 指到哪 |
| `MONITOR_PLUGIN_DIR` | 插件自己的目录 | 壳才知道制品落在哪；SDK 用它的 basename 定插件名 |
| `MONITOR_PLUGIN_INTERVAL` | 生效的采集周期 | 只有壳做三级取值与钳制 |
| `MONITOR_PLUGIN_TIMEOUT` | 生效的注销阈值 | 同上；SDK 用它填 `DeclaredMetric.timeout` |

> 前两项注入的是**路径**，值由插件自己读；后两项注入的是**值**，因为那是壳算出来的（插件看不到 `manifest.yaml` 的兜底与钳制表）——这正是"壳只注入自己算出来才有的值"的分界线。

**没有 `MONITOR_PROJECT`、没有 `MONITOR_HOSTNAME`、没有 `MONITOR_AGENT_VERSION`**，也**没有 `collect` 请求的 `common` 字段**（§3.7）。规则是——**壳只注入"壳算出来才有的值"，业务事实一律插件自取。**

## 五、指标映射表（本次构建最关键的一张表）

现有 6 类采集器要变成插件，**指标名与标签集合必须一个字都不改**——名字是 Grafana 面板与告警规则的引用键，改名即断图（服务端设计 §13）。这里**没有兼容层兜底**：服务端会整体删掉静态定义，新链路必须报出完全一样的名字，否则该指标直接消失（服务端设计 §5.5）。

**这张表就是写插件时 `sdk.Gauge(name, help, labels...)` 三个参数的取值来源**：`name` 取"指标名"列，`labels` 取"标签"列，`help` 抄现有 Help 文本（在 `server/Metrics/*.go` 里，服务端对 `help` 只透传不加工）。改这张表里的任何一个字，等同于改 Grafana 面板。

现有的指标定义全部在服务端 `Metrics/*Metric.go` 里硬编码（共 80 个），而 agent 上报的只是扁平的 JSON 字段名。下表就是两者的对应关系，**实现时必须逐个核对**。

### 5.1 `hard` 插件（17 个指标）

- **source**：`hard`
- **标签集合**：`{hostName, project, cpu_model, os_version, kernel_version}`
- **声明方式**：`labels = ["hostName","cpu_model","os_version","kernel_version"]`；`common = {cpu_model, os_version, kernel_version}`（一轮内不变，放 common 压小载荷）；每条 sample 只带 `hostName`
- **timeout**：`45s`（周期 15s）

| 现有指标名（必须保持） | 采集来源 |
|---|---|
| `cpu_percent` | `/proc/stat` 与本轮差值计算。**首次 / 计数器回绕 / 距上轮超 1 分钟 → 只重建基线并返回该轮无数据** |
| `disk_total` / `disk_used` / `disk_free` / `disk_used_percent` | `df -P -k /` 最后一行第 2/3/4 列 ×1024 转字节；百分比由 `used/total` 计算 |
| `memory_total` / `memory_free` / `memory_buffered` / `memory_cached` / `memory_shared` / `memory_available` | `/proc/meminfo` 的 `MemTotal` / `MemFree` / `Buffers` / `Cached` / `Shmem` / `MemAvailable` |
| `memory_used` | 计算值 `total - free - buffered - cached` |
| `memory_used_percent` | `used/total×100` |
| `cpu_load_1` / `cpu_load_5` / `cpu_load_15` | `/proc/loadavg` 第 1/2/3 列 |
| **`cpu_total`** | `/proc/cpuinfo` 统计 `processor` 前缀行数；为 0 时回退 `runtime.NumCPU()`。**注意：agent 上报的字段名是 `cpu_count`，指标名是 `cpu_total`，两者不同名** |

**历史遗留（保持兼容，不要"顺手修"）**：

- `memory_*` 系列**单位是 kB 且原样上报**（没乘 1024），而 `disk_*` 是字节。Help 文本里也没写单位。这是现存的不一致，**重构不是修它的时机**——改了会让面板上的曲线差 1024 倍。
- `cpu_total` 的 Help 是 `cpu 核心数`（小写 cpu），保持。
- 静态信息（CPU 型号 / OS / 内核）在现有代码里走 30 分钟缓存，插件里保留同样的缓存（长驻进程正好适合）。

### 5.2 `nginx` 插件（13 个指标）

- **source**：`nginx`
- **标签集合**：`{hostName, project}`
- **timeout**：`45s`（周期 15s）
- **外部命令**：`systemctl is-active nginx`、`who -q`、`ss -s`

| 现有指标名 | agent 字段 |
|---|---|
| `nginx_is_run` | `isRun`（`systemctl is-active nginx` 的 stdout 精确等于 `active` → 1，否则 0） |
| `nginx_login_user_count` | `loginUserCount`（`who -q` 第 2 行 `# users=N`） |
| `nginx_re_total` | `reTotal`（`ss -s` 的 `Total: (\d+)`） |
| `nginx_raw_total` | `rawTotal`（`ss -s` 里 `RAW` 行） |
| `nginx_udptotal` | `udptotal`（`UDP` 行） |
| `nginx_tcp_total` | **`tcpTotal`** |
| `nginx_total_tcp` | **`totaltcp`** |
| `nginx_inet_total` | `inetTotal`（`INET` 行） |
| `nginx_frag_total` | `fragTotal`（`FRAG` 行） |
| `nginx_tcp_estab` | `tcpEstab` |
| `nginx_tcp_closed` | `tcpClosed` |
| `nginx_tcp_orphaned` | `tcpOrphaned` |
| `nginx_tcp_timewait` | `tcpTimewait` |

> **最容易搞错的两行是加粗的那两条**：agent 字段 `tcpTotal` 对应指标 `nginx_tcp_total`，而字段 `totaltcp` 对应指标 `nginx_total_tcp`——**词序是交叉的**。现有代码里这一对曾经写错过，实现时逐字核对。

**行为约定**：命令不存在或执行失败时，对应指标上报 **0** 并只告警一次（warn-once），不要因为缺 `ss` 就让整个插件失败。这也意味着 nginx 插件在缺少这些命令的精简镜像里会产出一堆 0——这是现状行为，保持不变。

### 5.3 `ssl` 插件（1 个指标）

- **source**：`ssl`
- **标签集合**：`{domain, comment, status, resolve, project}`
- **timeout**：`15m`（周期 5min）
- **无 hostName 标签**（现状如此）

| 现有指标名 | agent 字段 |
|---|---|
| `ssl_domain_days_left` | `days_left` |

- `domain` / `comment` / `status`（固定 `"正常"`）/ `resolve`（固定 `true`）→ **标签**
- `expiration`（RFC3339）→ **agent 上报了，但服务端从未定义对应指标**，没有面板依赖它。**丢弃，不声明**。

**域名来源三处**（按顺序去重合并）：

1. 递归遍历 `/etc/nginx/conf.d` 下所有 `.conf`，正则 `server_name\s+(.*);`
2. `/etc/hosts` 里的非 localhost 条目
3. **当前工作目录**下的 `domains.txt`（相对路径，非配置项）——**建议改为配置项** `domains_file`（这是本次唯一建议改的行为，因为它依赖 CWD，而壳的 CWD 不可控）

**采集行为**：

- 并发上限 20，单域名 5 秒超时
- **探测失败的域名本轮不上报**（跳过，不填 `days_left = -1`）
- 全部失败 → 本轮 metrics 为空数组（壳收到空 `metrics` 会正常返回，不记为失败）

### 5.4 `k8s` 插件（11 个指标，原两个采集器合并）

**原 `k8sContainer` 与 `k8sController` 合并为一个插件**，共用同一个 clientset（现状是两个采集器各自初始化一次 k8s client）。合并的另一个好处是**消掉了"插件间依赖"这个需求**——声明式协议的 `metrics` 本来就是数组，一个插件声明多组指标零损失。

- **source**：`k8s`（原 `k8sController` 这个 source 名随之退役；source 只用于服务端归属校验与日志分类，不影响任何面板查询）
- **timeout**：`3m`（周期 60s）
- **客户端初始化**：`kubeconfig` 为空 → `rest.InClusterConfig()`；非空 → `clientcmd.BuildConfigFromFlags("", path)`。**只初始化一次**（长驻进程的红利）
- **API 调用**：`CoreV1().Pods("").List`、`MetricsV1beta1().PodMetricses("").List`、`AppsV1().Deployments/DaemonSets/StatefulSets("").List`，全部全 namespace，上下文超时 30s

**容器组（8 个指标）**，标签集合 `{namespace, podName, container, controllerName, project}`：

| 现有指标名 | agent 字段 | 说明 |
|---|---|---|
| `container_cpu_usage` | `useCpu` | PodMetrics 的 `cpu` `MilliValue()/1000`，单位核心数 |
| `container_memory_usage` | `useMemory` | PodMetrics 的 `memory` `Value()`，字节 |
| `container_cpu_limit` | `limitCpu` | Limits[CPU] `AsApproximateFloat64()`，核心数 |
| `container_memory_limit` | `limitMemory` | Limits[Memory] `Value()`，字节 |
| `container_cpu_request` | `requestCpu` | Requests[CPU] |
| `container_memory_request` | `requestMemory` | Requests[Memory] |
| `container_restart_count` | `restartCount` | `ContainerStatuses` 同名容器的 `RestartCount` |
| `container_last_termination_time` | `lastTerminationTime` | `LastTerminationState.Terminated.FinishedAt` 与现在的差值，**单位分钟**（差值 <60s 记 0）。注意现有代码注释写"秒"，**实现是分钟**，Help 也写分钟——以分钟为准 |

`controllerName` 取 `Pod.OwnerReferences` 中 `Kind ∈ {ReplicaSet, Deployment, StatefulSet}` 的 `Name`，无控制器时为空串。

> **已知遗留**：`controllerName` 取的是 ReplicaSet 名，每次滚动发布都会产生新标签值 → 容器指标序列碎片化。这个问题的修法（改取 Deployment 名）会改变标签值，**面板会断图**，因此属**本次范围外**（`docs/README.md §四「本次范围外」`），需要单独拍板。本次保持现状。

**控制器组（3 个指标）**，标签集合 `{namespace, container, controllerType, project}`：

| 现有指标名 | agent 字段 | Deployment | DaemonSet | StatefulSet |
|---|---|---|---|---|
| `controller_replicas` | `replicas` | `Spec.Replicas` | `Status.DesiredNumberScheduled` | `Spec.Replicas` |
| `controller_replicas_available` | `replicas_available` | `Status.AvailableReplicas` | `Status.NumberAvailable` | `Status.ReadyReplicas` |
| `controller_replicas_unavailable` | `replicas_unavailable` | `Status.UnavailableReplicas` | `Status.NumberUnavailable` | `Replicas - ReadyReplicas`（负值截断为 0） |

> `container` 这个标签承载的是**控制器名**——字段名与语义错位，但它是既有契约，**保持不动**（改名会破坏面板）。

### 5.5 `heart`：**不下沉为插件**

心跳（`is_active`、`agent_version`）由**壳自己**上报。理由：如果心跳也是一个插件，那么"用户停用了 heart 插件"和"主机真的离线了"在服务端看来完全一样。

壳上报这两个指标时 source = `heart`、标签集合 `{hostName, project}`、timeout `45s`、周期 15s。详见壳设计 §10。

### 5.6 `trafficSwitching`：**不是插件**

它由流量切换平台直接 POST 到 `/metrics_data`（原来就不装在机器上）。36 个指标全部由平台侧自己声明，插件目录里没有对应目录。

由服务端统一提供一份「36 个指标的声明模板」（`t` 到 `docs/` 或仓库根），平台侧照着填值即可。

## 六、每个插件的实现要点

采集逻辑从现有代码搬过来，但有几处**因为"长驻进程"而变得更好的地方**，值得利用：

| 插件 | 长驻带来的红利 | 实现注意 |
|---|---|---|
| `hard` | CPU 使用率天然可以跨轮做差值（现有代码已经是这个模式，搬到插件后连状态不用重建）；`/proc/cpuinfo`、`/etc/os-release` 等静态信息可以永久缓存（现有是 30 分钟 TTL） | 首次 collect 必须能返回空 metrics（还没有上一轮基线），**不要返回错误** |
| `nginx` | `ss -s` 的结果可以缓存到下一轮（如果采集失败，可用上一轮值 + 标记） | 外部命令失败时上报 0 + warn-once，不要中断整个插件 |
| `ssl` | TLS 连接与证书解析可以复用连接池（现有是每域名一个 `tls.Dial`） | 5 分钟的周期，注意 collect 的硬超时（`max(2×interval, 60s)` = 10 分钟，够用）；失败的域名不上报 |
| `k8s` | **clientset 只初始化一次**（合并前是两次），这是合并的直接收益 | Pod 与 PodMetrics 按 `namespace/podName` 预建索引（现有做法）；全 namespace List 在集群大的时候可能很慢，留意 30s 上下文超时 |

**共同注意**：

1. **collect 里不要 sleep**。整轮的时间预算由壳的硬超时兜底，但一个 sleep 3 秒的插件会拖长自己的周期。
2. **不要缓存"上一轮上报成功"这种信息**。插件不知道壳有没有把数据发出去（协议里也没有这个回执），也不需要知道。
3. **stderr 可以随便打日志**，但要克制——1500 台 × 每轮几行 = 日志量可观。建议只在状态变化时打。
4. **控制上报范围，别把能采到的全报上来**。载荷大小与服务端的 gzip 解压、JSON 解析成本**线性相关**，而这两步是接收链路最贵的两项（见 `服务端设计.md §6.7`）。最典型的是 `k8s`：全 namespace × 全部容器 × 8 个指标，1500 台能轻易凑出百万级序列。按 namespace 白名单、或只报带 request/limit 的容器来收缩。
5. **失败要报失败，别把 `0` 当成"没采到"发出去**。典型场景是**依赖缺失**：`ss` 命令不存在、kubeconfig 读不到、API 返回 403、证书读不出。**采集失败时上报的 `0` 与真实的 `0` 在指标上一模一样**，看面板的人分不出来，只能上机器翻日志。正确做法是**返回 error**（这一轮回 `ok:false`、不发数据）+ 往 `stderr` 写一行原因——壳会加 `[plugs/<name>]` 前缀转发进日志，`curl` 状态端点也能看到它（§3.6）。

## 七、构建、打包与发布

### 7.1 `build.sh`

```sh
#!/usr/bin/env bash
set -euo pipefail

VERSION=${VERSION:-$(git describe --tags --always --dirty)}
PLUGINS="hard nginx ssl k8s"
PLATFORMS="linux/amd64 linux/arm64"

for p in $PLUGINS; do
  for plat in $PLATFORMS; do
    os=${plat%/*}; arch=${plat#*/}
    CGO_ENABLED=0 GOOS=$os GOARCH=$arch \
      go build -trimpath -ldflags "-s -w -X main.version=$VERSION" \
      -o "dist/$p/$VERSION/$os/$arch/$p" "./$p"
    # 打包：binary + default.yaml + manifest.yaml
    tar -czf "dist/$p/$VERSION/$os/$arch/$p.tgz" -C "dist/$p/$VERSION/$os/$arch" "$p" default.yaml manifest.yaml
  done
done
```

### 7.2 生成 `index.json`

打包后计算 sha256 与 size，生成清单（脚本的最后一步，纯 shell 或一个小 Go 程序均可）：

```json
{
  "generated_at": "2026-09-18T15:00:00+08:00",
  "plugins": {
    "hard": {
      "latest": "1.2.0",
      "min_agent_version": "1.0.0",
      "platforms": {
        "linux/amd64": {"sha256": "…", "size": 5242880, "url": "/agent/download/hard/1.2.0/linux/amd64"}
      }
    }
  }
}
```

### 7.3 发布

**发布由 service 决定**：制品目录里没有的文件，agent 就下载不到。所以：

- 制品随 service 镜像打包（`/data/artifacts/`）→ **回滚镜像即回滚插件**，不会出现"service 回滚了但插件还是新的"
- 只想发布某一个插件时，把它的新版本目录放进去即可，其它插件不动
- `latest` 字段由脚本生成，**不要手工编辑 `index.json`**

### 7.4 本地开发与自检

每个插件支持 `--selftest`：不走 stdio，直接打印自描述并跑一次 collect，把结果格式化输出。

```sh
$ ./hard --selftest
name: hard  version: 1.2.0          # 读自 manifest.yaml
interval: 15s  timeout: 45s         # 壳注入的最终值（manifest 默认 + config 覆盖）
cpu_percent            = 12.3
memory_used_percent    = 47.8
...（共 17 条）
```

`--selftest` 打印的**调度参数是壳算出来的最终值**（从环境变量读），所以它能回答一个很实际的问题："这台机器上这个插件到底多久采一次"——而不是"代码里写的是多少"。不启动壳就能确认。

也可以手工模拟壳的握手：

```sh
$ echo '{"id":1,"cmd":"hello","proto":1}' | ./hard
{"id":1,"ok":true,"proto":1}
```

**这两种调试方式必须在 SDK 里内置**——没有它们，写插件的人要先起一个壳才能验证，反馈回路太长。

| SDK 单测 | 三段命令的分发与应答格式；宽容处理（未知命令、缺 id）；`stdout_guard` 确实把 `fmt.Println` 转到了 stderr |
| 配置单测 | mtime 缓存生效（改文件后能读到新值）；缺省值；类型转换失败时的降级 |
| 插件单测 | 采集逻辑本身：procfs 解析（用 testdata 固定文件）、`ss -s` 输出解析（用 testdata 固定文本）、`df -P -k` 解析、证书剩余天数计算 |
| 进程级集成 | 用真实二进制跑 hello → collect → shutdown 全流程；**collect 里注入 panic，验证插件不退出而是返回 `ok:false`** |
| 调度参数注入 | `MONITOR_PLUGIN_INTERVAL` / `MONITOR_PLUGIN_TIMEOUT` 缺失时走内置兜底；`DeclaredMetric.timeout` 确实取了注入值，而不是写死的常量 |
| 本机事实自取 | `Hostname()` 不依赖任何注入就有值；与壳内 `heartbeat` 取到的主机名相等（§3.7 的一致性约束） |
| 端到端 | 与壳的假插件矩阵共用同一套手法（壳设计 §15.2） |

**采集逻辑的解析部分必须用 testdata 固定输入做单测**，不要依赖运行环境（CI 里没有 `/proc/meminfo` 的真实内容，也不一定有 `ss`）。现有代码把解析和读取写在一起，写插件时顺手拆开——**这是插件化带来的一个实际收益**。

## 九、用其它语言写插件

协议刻意选成"按行 JSON"，任何语言十行就能实现。Python 最小示例（完整可运行）：

```python
#!/usr/bin/env python3
import sys, json, os, socket

def handle(req):
    cmd = req.get("cmd")
    if cmd == "hello":
        # 只需报协议版本。名字、版本、周期都在 manifest.yaml，壳自己读（§3.6）
        return {"id": req["id"], "ok": True, "proto": 1}
    if cmd == "collect":
        # collect 请求不带任何参数；主机名这类本机事实自己取（§3.7）
        return {"id": req["id"], "ok": True,
                "metrics": [{
                    "name": "demo_value", "help": "示例指标", "type": "gauge",
                    "labels": ["hostName"], "common": {"hostName": socket.gethostname()},
                    # 从环境变量取，别写死——它是壳按 manifest + config 算出的最终值
                    "timeout": os.environ.get("MONITOR_PLUGIN_TIMEOUT", "90s"),
                    "samples": [{"value": 42.0}],
                }]}
    if cmd == "shutdown":
        return {"id": req["id"], "ok": True}
    return {"id": req.get("id"), "ok": False, "error": "unknown cmd"}

def main():
    for line in sys.stdin:
        line = line.strip()
        if not line:
            continue
        req = json.loads(line)
        resp = handle(req)
        print(json.dumps(resp, ensure_ascii=False), flush=True)   # flush 必须
        if req.get("cmd") == "shutdown":
            break

if __name__ == "__main__":
    main()
```

**非 Go 插件的三条硬要求**：

1. **`stderr` 只放日志，`stdout` 只放协议**，且每次输出必须 flush（Python 要显式 `flush=True`，否则壳会等到进程退出才收到数据 → 每轮都超时）
2. **必须常驻**，不要每轮退出——否则失去跨轮状态，且进程启动开销会体现在采集延迟上
3. **`collect` 里的异常要兜住并回 `ok:false`**，不要让进程崩溃（壳会重启它，但退避期间会丢数据）

**`timeout` 必须从 `MONITOR_PLUGIN_TIMEOUT` 取，不要写死**（§3.6）：它是壳按 manifest 默认值 + `config.yaml` 覆盖算出的最终值。写死会让 `config.yaml` 里 `timeout` 的覆盖失效，而**服务端的注销阈值也是按这个值注册的**——两边不一致会导致时间序列在两次上报之间被摘掉，Prometheus 抓到断点。
