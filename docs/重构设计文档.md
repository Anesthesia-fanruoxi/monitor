# monitor 项目重构设计文档

> 版本：v0.1（讨论稿）
> 范围：全项目（agent + server）
> 状态：待评审，文末列出需要拍板的问题

---

## 一、文档目的

当前系统已经能稳定运行，采集、上报、指标转换、超时注销整条链路是通的，并且经过多轮修补，安全基线和边界处理都做得比同类自研项目扎实。

但结构上有几处是"当时够用、现在扩展不动"的：

- 新增一个采集器，要改服务端 **5 个地方**；改动分散在 7 个几乎同构的文件里；
- Agent 是单体进程，任何采集器要更新，整个进程都得重启；
- 上报协议是两端靠约定对齐的 JSON，没有契约文件，字段对不上只能靠跑起来看。

本文档做三件事：

1. **记录当前设计里值得保留的部分**（重构不是推倒重来，这些是资产）
2. **给出目标架构与构建路径**
3. **给出技术选型建议**（含取舍，不是罗列）

## 二、现状评估

### 2.1 系统概览

```
┌──────────────┐   采集     ┌──────────────────────────────────────────┐
│ 被监控主机    │            │  monitor-server                          │
│              │            │                                          │
│  monitor-agent ────POST──▶│  /metrics_data                           │
│  （单进程）   │  JSON      │    ├─ AES-GCM 解密                       │
│              │  →gzip     │    ├─ gzip 解压                          │
│  ├ hard      │  →AES-GCM  │    ├─ project / source 白名单校验         │
│  ├ nginx     │            │    ├─ 立即回 200                         │
│  ├ ssl       │            │    └─ Worker Pool + 分片锁 异步处理        │
│  ├ k8s       │            │         └─ 写 GaugeVec（内存）            │
│  └ k8sCtrl   │            │                                          │
└──────────────┘            │  /metrics ◀──── Prometheus 定期抓取        │
                            └──────────────────────────────────────────┘
                                          │
                                    Grafana / Alertmanager
```

关键特征：**Agent 主动推 + Prometheus 主动拉**的两段式。Agent 不需要被 Prometheus 直连，这让内网、多项目、动态 IP 的场景变得可行。

### 2.2 设计优点（重构中必须保留的资产）

**① 自己只做"管道"，查询和告警完全交给 Prometheus 生态**

这是整个项目最重要的一次选型。自研时序存储要面对压缩、降采样、retention、PromQL 兼容这一堆无底洞；当前做法是 Agent 上报 → Server 转成 Prometheus 指标 → 下游用现成的 PromQL / Grafana / Alertmanager。**重构时这一点不应该动摇。**

**② 静态指标用 GaugeVec + 超时注销，而不是 counter**

Prometheus 的 pull 模型下，"主机下线"会导致时间序列残留，产生假告警。当前实现（`server/Handers/UnRegister*.go`）自己维护 `标签 → 最后上报时间`，超时后 `DeleteLabelValues` 摘掉序列，响应时间 45s 级别，比 Prometheus 默认 5 分钟的 staleness 快得多。

配套的一个细节体现了对语义的理解：**系统里没有用 counter**。因为 counter 被摘掉后再出现会从 0 重新计数，`rate()` 会算出一个错误的尖峰。用 gauge + 注销是自洽的。

**③ 传输层的工程取舍到位**

| 处理 | 价值 |
|---|---|
| JSON → gzip → AES-GCM | 压缩率实测 92%（k8s 载荷 328KB → 25KB） |
| AES-**GCM** 而非 AES-CBC+HMAC | GCM 单段完成机密性 + 完整性，没有"先加密再 HMAC"的经典坑 |
| 随机 nonce 前置拼装 | 避免了 nonce 复用的致命错误 |
| 解压上限 64MB / 请求体 10MB | 防 gzip 炸弹（10MB 压缩包可膨胀到 GB 级） |
| 时间戳 ±5 分钟校验 | 抵御密文重放，且对旧版 Agent 兼容放行 |
| 标签值 512 字节 / 单次 20000 条上限 | 防时间序列基数爆炸 |

**④ 并发模型：Worker Pool + FNV-1a 分片锁**

500 个 worker + 256 个分片锁，**同一 project 同类型串行、不同维度并发**。这个设计同时满足了两个互相冲突的需求：同一项目的指标写入要有序（否则同一次上报的数据可能乱序覆盖），而整体吞吐又不能被单个项目拖慢。队列满时降级为当前 goroutine 执行，**不丢数据**。

**⑤ 部署友好性做到了同类项目少见的程度**

- Agent 配置不存在时**自动生成带注释的模板**，不用先读文档才能起步；
- Server 启动时读 procfs 打印 `FD 限制` 和 `somaxconn` 并在偏低时告警 —— 这两个是"不检查就查不出原因"的部署坑（Agent 上千时会出现 `accept: too many open files`）；
- 守护模式 + PID 文件防多开 + 崩溃指数退避（1s→60s）（**保留**：`-d` 作为没有 systemd / 容器编排时的兜底，而"连续崩溃自动回滚 `.bak`"随自更新一起删除）；
- `syscall.Exec` 原地替换实现自更新（**容器场景下是坑**：PID 不变、容器不重建 → 容器内二进制与镜像版本漂移，重建即回退；重构中删除，改由 systemd / 容器编排负责）；
- IP 白名单支持域名（DNS 定期刷新）、字面 IP、CIDR 三种形式；
- 启动即校验关键配置（project / metrics_url / 密钥长度），非法直接退出并说明原因，而不是"启动成功但数据全丢"。

**⑥ 安全基线在小项目里算相当高**

密钥 fail-fast、代理头只在直连方可信时才采信（`X-Real-IP` 伪造防护）、更新端点与 metrics 端点白名单解耦、`.gitignore` 覆盖了配置目录使真实密钥从未进入 git 历史。

**⑦ 超时阈值按 source 独立**（`server/Handers/timeouts.go`）

这个改动解决了"20s 统一阈值 vs SSL 5 分钟采集周期"的矛盾 —— 阈值必须与采集周期挂钩，否则时间序列会在两次上报之间被清掉。这条经验在重构时要上升为**协议的一部分**（阈值随指标声明）。

### 2.3 结构性债务

按"重构要解决的"排序：

| # | 问题 | 位置 | 后果 |
|---|---|---|---|
| 1 | **指标定义硬编码在服务端**：新增采集器要改白名单、分发 switch、handler 函数、Modles 结构体、Metrics 定义 5 处 | `Handers/hander.go:79,436`、`Handers/HanderData.go`、`Metrics/*.go` | 插件化做不了，扩展成本随采集器数量线性增长 |
| 2 | **注销逻辑重复 7 份**，每个 source 一个文件 | `Handers/UnRegister*.go` | 改一处要同步 7 处，容易漏 |
| 3 | **Agent 单体进程**：所有采集器共享进程 | `agent/Collect/CollectData.go` | 一个采集器崩溃/内存泄漏影响全部；更新要重启整个进程 |
| 4 | **传输层自制且无契约**：密钥即唯一凭据、无签名、无双向认证 | `agent/Middleware/Send.go`、`Handers/hander.go` | 密钥轮换困难；两端字段靠约定对齐，错位是静默的 |
| 5 | **无持久化、无背压**：指标只在内存 | `Metrics/*.go` | Server 重启指标全丢；下游抓取间隔内的历史无法回溯 |
| 6 | 配置双读（yaml.v3 + viper 各读一遍）、无优雅停机 | `server/main.go` | 行为不一致；停止时可能丢在途请求 |
| 7 | 标签命名混用（`hostName`/`podName` 驼峰 vs `os_version` 蛇形） | `Metrics/HardMetric.go` | 写 PromQL 容易记错；改名会破坏现有面板，所以一直没动 |
| 8 | 指标语义与文档不符（如 `nginx_re_total` 取自 `ss -s`，与 Nginx 请求数无关） | `Metrics/NginxMetric.go` | 误导告警配置 |
| 9 | 测试覆盖极少（仅版本比较 11 用例） | — | 重构时缺少安全网 |
| 10 | 部分逻辑依赖外部命令（`systemctl`/`who`/`ss`） | `Metrics/Nginx.go` | 精简镜像里采集失败；应在重构时改为读 `/proc/net/*` 或明确声明依赖 |

## 三、重构目标与非目标

### 目标

1. **采集器可独立开发、独立发布、独立更新**：新增采集器不改服务端代码
2. **Agent 更新不中断采集**：换一个采集器只影响它自己
3. **两端有明确的契约**：字段错位在编译期或启动期就能发现，而不是运行期静默丢数据
4. **单机可跑，集群可扩**：不引入必须依赖外部组件才能启动的强制项

### 非目标（本次重构不做）

- **不替换 Prometheus / Grafana**：查询与告警继续复用生态
- **不自研时序存储**：除非明确需要"Prometheus 抓取间隔之外的历史"，否则不碰
- **不追求分布式一致性**：Server 仍可单实例部署；多实例通过一致性哈希或 project 分片解决

## 四、目标架构

### 4.1 Agent：壳 + 插件

```
┌─ Agent 部署单元 ────────────────────────────────────────┐
│                                                         │
│  ┌─ 壳（常驻，PID 1，唯一需要守护的进程）──────────────┐  │
│  │  配置中心 │ 加解密上报 │ 调度器 │ 插件监管 │ 状态 API│  │
│  └──────────────────────────────────────────────────┘  │
│         │ stdio JSON-RPC        ▲ 采样数据              │
│  ┌──────┴───┬──────────┬────────┬──────────┐           │
│  │ hard     │ nginx    │ ssl    │ k8s      │  未来插件  │
│  │ 独立进程  │ 独立进程  │ 独立进程│ 独立进程  │           │
│  └──────────┴──────────┴────────┴──────────┘           │
└─────────────────────────────────────────────────────────┘
```

要点：

- **插件是独立操作系统进程，不是 Go 动态库**。理由：Go 的 `plugin` 包只支持 Linux、要求主程序与插件依赖 hash 完全一致，且**无法卸载** —— 更新必须重启宿主，直接违反"更新不中断"的目标。
- **附带收益是崩溃隔离**：插件 OOM、死循环、文件描述符泄漏都不会影响壳和其他采集器。
- **心跳采集留在壳内**，不下沉为插件。它是"这个 agent 还活着"的信号，做成可卸载的插件会出现"插件被禁用导致主机显示离线"的误判。
- **插件自描述**：插件启动后响应 `describe`，返回自己的名字、版本、产生的指标、建议采集周期、注销阈值。壳据此自动调度并对外展示，**壳里不需要维护插件清单**。

### 4.2 插件协议（草案）

```
壳 → 插件   {"id":"1","cmd":"describe"}
            {"id":"2","cmd":"collect","config":{...}}
            {"id":"3","cmd":"shutdown"}

插件 → 壳   {"id":"1","ok":true,"name":"hard","version":"1.0.0",
             "interval":"15s","timeout":"45s"}
            {"id":"2","ok":true,"metrics":[ ...声明式指标... ]}
```

约定：**插件的日志写 stderr，stdout 只走协议**。这条必须在 SDK 里强制，否则插件一打日志就污染协议解析。

### 4.3 数据契约（插件 → 壳 → Server）

```json
{
  "project": "jiexianghua",
  "source": "hard",
  "timestamp": 1758180000000,
  "schema": "v2",
  "metrics": [
    {
      "name": "cpu_percent",
      "help": "CPU 使用率百分比",
      "type": "gauge",
      "labels": ["hostName", "cpu_model", "os_version", "kernel_version"],
      "common": {
        "cpu_model": "Xeon Gold 6248",
        "os_version": "Rocky 10",
        "kernel_version": "5.14.0"
      },
      "timeout": "45s",
      "samples": [
        {"labels": {"hostName": "web-01"}, "value": 12.3}
      ]
    }
  ]
}
```

三个关键设计决定：

1. **`project` 不进 `labels`，由服务端统一注入**。取值来自配置、还要映射中文显示名，这两件事必须服务端统一做；否则每个插件都要重复实现，还会出现同一项目在不同指标里写成不同值。
2. **标签用 map 而不是数组**。数组要求收发两端顺序严格一致，一旦错位就是**静默的数据错乱**（把主机名当成了内核版本）。map 由服务端按声明的 `labels` 顺序取值，天然免疫。
3. **`common` 承载一轮内不变的标签**。K8s 那类数据的标签重复极其严重，这个字段能显著压小载荷。
4. **`timeout` 随指标声明**。这是把"阈值必须匹配采集周期"这条经验固化进协议，避免 2.3 节第 1 条那类问题重演。

### 4.4 Server：契约驱动 + 动态指标

```
/metrics_data
   │
   ├─ 解密 / 解压
   ├─ project / source / 时间戳 校验
   ├─ 分流：有 metrics → 声明式路径；只有 data → 旧路径（兼容期保留）
   │
   ├─ 声明式路径（同步，错误立刻返回 400 带原因）
   │    ├─ 校验指标名 / 标签名 / 类型 / 基数上限
   │    ├─ 动态注册 GaugeVec（跨 source 重名拒绝）
   │    └─ 返回落库闭包
   │
   └─ 异步（Worker Pool + 分片锁）
        ├─ 写值 + 更新时间戳
        └─ 通用注销器按各指标声明的 timeout 清扫
```

**动态注册必须配套的防护**（否则上报方可控服务端内存）：

| 防护 | 原因 |
|---|---|
| 指标名 / 标签名正则校验、拒绝 `__` 前缀 | `__` 是 Prometheus 保留前缀 |
| 拒绝插件声明 `project` 标签 | 防止伪造项目归属 |
| **单指标时间序列基数上限** | **最关键**：没有它，插件只要不断变化标签值就能把内存吃光 |
| 指标名全局唯一 + 跨 source 重名拒绝 | 防止一个插件冒名篡改另一个插件的数据 |
| 动态指标总量上限 | 防止无限注册 |
| 注销阈值下限（如 20s） | 防止极短阈值导致序列频繁增删 |
| 标签集合变更时注销重注册 | 让插件能升级改标签，而不必重启服务端 |

## 五、关键设计决策

以下四项是重构中最贵的选择，选错了返工成本最高。

### 决策 1：指标接收端继续自研，还是改用 OTel Collector？

| 方案 | 优点 | 代价 |
|---|---|---|
| **A. 自研接收端 + 声明式契约**（推荐） | 对协议/标签/项目隔离有完全控制；无额外组件；单机可跑 | 防护要自己写；生态工具（重试、限流、批量）要自己实现 |
| B. OTLP + OpenTelemetry Collector | 借生态：重试、批量、背压、多信号（trace/log/metric 统一） | 引入必须部署的中间件；Collector 配置本身有学习曲线；多项目隔离要另想办法 |
| C. Agent 直接暴露 `/metrics` 给 Prometheus 抓 | 架构最简单，去掉整个 Server | 内网穿透 / 动态 IP / 多项目场景不可行；无法做服务端统一鉴权 |
| D. 用 vmagent / 现成 agent | 零开发 | 只适合基础设施指标，自定义业务指标表达不了 |

**建议 A**，但**在数据模型上向 OTel 靠拢**（指标 + 属性 + 资源三层结构），这样将来若需要接 OTel 生态，转换成本低。C 适合未来做"Prometheus 直抓"的降级方案。

### 决策 2：传输协议与认证方式

当前是"JSON + gzip + AES-GCM，密钥即唯一凭据"。问题：密钥轮换要所有 Agent 同步改；无双向认证；无天然的密钥版本协商。

| 方案 | 说明 |
|---|---|
| 保留 AES-GCM + 增加 **密钥版本号** | 最小改动实现平滑轮换：payload 带 `key_id`，服务端按版本选密钥，新旧并存一段时间 |
| 换成 **HTTPS + HMAC 签名 + 时间戳** | 用 TLS 做传输加密，HMAC 做报文完整性，密钥轮换仍要设计 |
| 换成 **mTLS** | 认证最强，每台 Agent 独立证书、可单独吊销；代价是证书签发/分发/续期需要一套流程（可用 SPIRE/step-ca，或自签 + 配置分发） |

**建议：短期做"密钥版本号"过渡，中期上 mTLS**（尤其 Agent 跨公网时）。同时**用 protobuf 替换 JSON** —— 契约强类型，字段错位在编译期就能发现，体积也更小。

### 决策 3：插件形态

| 方案 | 隔离性 | 热替换 | 跨平台 | 结论 |
|---|---|---|---|---|
| **独立进程 + stdio/IPC**（推荐） | 强（进程级） | 支持 | 全平台 | 唯一能真正满足"更新不中断 + 崩溃隔离"的 |
| hashicorp/go-plugin | 强 | 支持 | 全平台 | 上面方案的生产级实现：gRPC over unix socket、TLS、健康检查、日志转发都有现成的。**代价是依赖较重** |
| Go `plugin` 动态库 | 弱（同进程） | **不支持卸载** | 仅 Linux | 直接排除 |
| WASM（wazero） | 强 | 支持 | 全平台 | 沙箱最彻底，但插件要用 TinyGo/Go→WASM 编译，系统调用受限（读 procfs 就做不到） |

**建议：自己实现 stdio 协议**（零依赖、协议简单、可控），或者用 **hashicorp/go-plugin**（省掉 IPC 细节、有健康检查）。如果插件需要读 procfs、执行命令，**WASM 不可行**，排除。

### 决策 4：是否需要持久化

当前指标只在内存，Server 重启即丢，且只有 Prometheus 抓取间隔内的历史。

- **不需要** → 保持现状，Prometheus 就是唯一存储
- **需要**（比如要保留 1 年、要跨重启对比）→ 引入 **VictoriaMetrics**（兼容 PromQL、单机部署简单、压缩率高），Server 通过 remote write 或直接写 VM 的摄入接口转发

**建议先不做**，明确写下"历史查询由 Prometheus 的 retention 负责"，避免范围蔓延。

## 六、技术选型建议

### 6.1 逐项推荐

| 维度 | 推荐 | 备选 | 理由 |
|---|---|---|---|
| HTTP 路由 | 标准库 `net/http`（Go 1.22+ 的 ServeMux 已支持方法+路径参数）+ `chi` 中间件 | Gin / Echo / Fiber | 本项目只有 4 个端点，不需要重框架。chi 兼容标准库、中间件生态好、零依赖膨胀 |
| 配置 | `koanf` | Viper（现用）/ 自研 | Viper 依赖上百个包、热加载语义隐晦、同名 key 优先级容易踩坑。koanf 轻、合并语义清晰。**或者**继续自研 yaml.v3 + fsnotify（当前已有一半） |
| 日志 | 标准库 `log/slog` | zap / zerolog | 结构化 + JSON 输出，标准库无依赖。当前项目还在用 `log.Printf`，迁移成本很低 |
| 插件机制 | 自研 stdio 协议 或 `hashicorp/go-plugin` | — | 见决策 3 |
| 数据契约 | `protobuf` + `buf` | JSON Schema / OpenAPI | 强类型、跨语言、体积小。配合 `buf breaking` 可以做契约兼容性检查 |
| 指标库 | `prometheus/client_golang`（现用） | OTel SDK | 是事实标准，且与 Prometheus 生态天然一致 |
| 参数校验 | `go-playground/validator` | 手写 / `ozzo-validation` | 声明式 tag 校验，减少手写 if 链 |
| 测试 | `testify` + `go-cmp` + `testcontainers-go` | 标准库 | 断言可读性；`testcontainers` 用于起真实 Server 做端到端 |
| 错误处理 | 标准库 `errors` + `%w` 包装（现用） | `pkg/errors` | 标准库 `errors.Is/As` 已足够 |
| 依赖注入 | **不引入** | `google/wire`、`uber/fx` | 项目规模手工装配更清晰，DI 框架带来的间接层在这里是负担 |
| 存储（如需要） | VictoriaMetrics | ClickHouse / TimescaleDB | 兼容 PromQL、单机简单、压缩率高 |
| K8s 客户端 | `client-go`（现用） | — | 唯一选择 |
| 定时调度 | 自研 Ticker（现用） | `robfig/cron` | 固定周期用 Ticker 语义更准；cron 只在需要"每天几点"时才引入 |
| 构建/发布 | `goreleaser` | Makefile + 脚本 | 多平台二进制 + 校验和 + 版本注入一条命令搞定 |
| API 文档 | `buf` 生成的 protobuf 文档，或 `oapi-codegen`（若走 OpenAPI） | — | 契约即文档 |

### 6.2 建议的项目结构

```
monitor/
├── api/                          # 契约先行：protobuf 定义 + 生成的 Go 代码
│   └── v1/
│       ├── ingest.proto          # 上报协议
│       └── plugin.proto          # 壳 ↔ 插件协议
├── cmd/
│   ├── monitor-server/main.go    # 只做装配，不写业务
│   └── monitor-agent/main.go
├── internal/
│   ├── agent/
│   │   ├── shell/                # 壳：生命周期、调度
│   │   ├── supervisor/           # 插件进程监管（启动/健康检查/重启/热替换）
│   │   ├── config/               # 配置中心（壳取 enable/interval/timeout；plugins 子树交给插件自读）
│   │   └── api/                  # 本地状态端点
│   ├── server/
│   │   ├── ingest/               # 接收管道：解密、解压、校验、分流
│   │   ├── auth/                 # 认证（密钥版本 / mTLS / 白名单）
│   │   ├── registry/             # 动态指标注册表 + 防护
│   │   ├── lifecycle/            # 通用超时注销
│   │   └── transport/            # HTTP / gRPC 层
│   └── platform/                 # 跨端复用：日志、错误、版本
├── pkg/
│   └── pluginsdk/                # 对外发布的插件 SDK（插件作者只用这个）
├── plugins/                      # 各采集器，各自独立构建
│   ├── hard/
│   ├── nginx/
│   ├── ssl/
│   └── k8s/
├── deploy/
│   ├── systemd/
│   └── helm/
└── docs/
```

要点：

- `cmd/` 只做装配，业务全在 `internal/`（防止被外部 import）；
- `api/` 契约先行，两端都从同一份 .proto 生成代码，**这是消除"字段错位"这类 bug 的根本手段**；
- `pkg/pluginsdk` 是插件作者唯一需要接触的包，接口要刻意做窄；
- `plugins/` 与 `internal/` 分离，表示"插件是外部产物"，与壳的演进解耦。

## 七、构建路径

**不做迁移。** 新架构不与旧系统并存（2026-09-20 用户拍板），因此没有"双轨并存""逐批切换""安全网"这些阶段——**没有新旧并存的窗口**。四个阶段都是**构建新系统**，每个阶段结束时系统都应该是可上线状态。

### 阶段 0：抽契约 + 落壳防腐层

- 抽 `pkg/plugproto`（独立 module），三端共享协议类型
- 落 `agent/internal/proto` 防腐层（≤110 行，恰好 4 个字段）
- 工程门禁固定为每次改动的必跑项：`go build ./...` / `go vet ./...` / `gofmt -l .` / `CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build ./...`
- **不为现有实现补测试网**——那套代码在阶段 1 一开始就会被删除。测试只写在新代码上

### 阶段 1：service 只保留声明式链路

- **先删旧链路**：80 个静态定义、旧 `data` 路径、`HanderData.go`、7 个 `UnRegister*.go`、`timeouts.go`、`allowedSources`
  - **这是新链路的前置条件，不是迁移完成后的清理**：动态注册与静态定义同名即 400，不删则新链路一个指标都报不进来
  - 旧 `data` 路径显式返回 4xx + 日志，不静默丢弃
- 抽 `internal/registry` / `internal/ingest`，打通声明式路径
- 动态注册防护 + 全局序列闸门 + `monitor_ingest_*` 自监控
- **压测基线是硬闸门**：不达标不进入下一阶段

### 阶段 2：插件 SDK + hard 打样

- 实现插件 SDK（stdio 协议 + 配置读取 + stdout 保护 + 指标声明收集）
- 用最简单的 `hard` 插件走通全链路
- 心跳**不下沉**为插件（否则"用户停用了心跳"与"主机离线"无法区分）

### 阶段 3：agent 壳 + 其余插件

- 实现壳：配置读取、插件监管（懒下载 / 原子替换 / 熔断）、调度打散、上报、只读状态端点
- **壳不做自更新**：进程生命周期交给 systemd 与容器编排（物理机换二进制 + `systemctl restart`，容器换镜像 tag）
- 存量采集器逐个做成插件：`nginx` / `ssl` / `k8s`
- **指标名与标签集合与 `插件设计 §5` 逐字一致**——静态定义已删，那张映射表是 80 个指标名的唯一对照物

**不在本次范围**（需单独拍板、单独排期）：标签命名统一、`controllerName` 取 Deployment 名、`cleanNamespace` 去硬编码、外部命令改读 procfs、传输层升级（protobuf / 密钥版本号 / mTLS）。这五项都会改指标契约，混进构建流程会让"构建失败"与"改名失败"无法归因——清单见 `docs/README.md §四「本次范围外」`。

## 八、风险与"不做的事"

**风险**

| 风险 | 应对 |
|---|---|
| 插件化引入的进程管理复杂度（僵尸进程、孤儿进程、FD 泄漏） | 壳必须处理子进程退出回收；容器里注意 PID 1 的僵尸回收问题 |
| 动态指标基数失控 | 见 4.4 的防护表，其中"单指标序列上限"必须在阶段 1 就实现 |
| 静态定义删了、旧 agent 仍在报 | 旧 `data` 路径显式 4xx + 日志，以便识别还有谁落在旧路径上（服务端设计 §2.2） |
| 标签命名统一会打破现有面板 | 属本次范围外，单独拍板（`docs/README.md §四「本次范围外」`） |
| 契约变更导致老 Agent 失联 | protobuf 的字段只增不删；服务端按 `schema` 版本分流 |

**明确不做**

- 不替换 Prometheus / Grafana / Alertmanager
- 不自研时序数据库
- 不引入必须依赖外部组件才能启动的强制项（Kafka、Redis、etcd 等）
- 不做多租户 RBAC（当前"项目"级别的隔离已经够用）

## 九、需要你决策的问题

1. **重构范围**：只重构 Agent（壳+插件），还是 Server 一起改？Server 不改的话，插件化只能覆盖现有 4 类采集器。
2. **接收端形态**：继续自研（方案 A），还是引入 OTel Collector（方案 B）？
3. **插件机制**：自研 stdio 协议，还是直接用 `hashicorp/go-plugin`？
4. **认证方式**：短期"密钥版本号"过渡 + 中期 mTLS，是否接受？还是维持现状不动认证？
5. **是否需要持久化历史数据**？需要的话 VictoriaMetrics 是首选方案。
6. **团队约束**：是否有"必须使用/禁止使用某个框架"的既有约定？是否有 Go 版本下限要求（影响 slog、ServeMux 增强等特性的可用性）？
7. **部署形态**：Agent 只跑在 RHEL 宿主机，还是也要跑在容器里（distroless/scratch）？这决定插件是否必须避免依赖外部命令。
