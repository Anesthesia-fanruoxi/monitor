# 服务端（service）设计

> 定位：**接住 1500 台机器在同一时刻发来的加密上报，把字节变成 Prometheus 能拉的指标。**
> 读者：实现 service 的人。
> 相关文档：`docs/插件化架构设计.md`（总体架构与决策）、`docs/壳设计.md`、`docs/插件设计.md`。
> 本文只讲 service，不重复论证架构选择的理由。

---

## 一、service 的职责边界

| 做 | 不做 |
|---|---|
| 解密、解压、校验、限流 | 不解析指标的业务含义 |
| 按上报方自描述动态注册指标 | 不硬编码任何采集器的字段结构 |
| 超时注销时间序列 | 不聚合、不计算、不做告警规则 |
| 分发插件制品与 agent 制品 | 不主动连接 agent（一律 agent 主动拉） |
| 暴露 `/metrics` 给 Prometheus | 不存储历史数据（那是 Prometheus 的事） |

**一句话**：service 是一个「带自描述契约的指标注册中心 + 制品分发点」，不是一个数据处理系统。所有需要理解数据的活都在插件里干完了。

### 2.2 静态定义整体删除，不设兼容层

动态注册用的是 `registry.Register`（不是 `MustRegister`），**与静态指标同名时会返回 `AlreadyRegisteredError`，被判定为 400 拒绝**。也就是说"静态定义还在"与"插件上报同名指标"不能同时成立，**必须有一个先退场**。

**决策（2026-09-20）：直接删掉 80 个静态定义与旧 `data` 路径。**

**关键认识：这不是"迁移动作"，而是新链路的"前置条件"。** 本项目不存在新旧架构并存的窗口（新架构不与旧 agent 混跑），所以删除不需要等任何条件、不需要与谁对齐批次——**不删，新链路一个指标都报不进来**。

删除的时间点是**实现顺序的第一步**（§13 步 1），在"抽包"与"端到端打通"之前。理由：把它留到最后，中间每一步的端到端验证都会撞在那 400 上。

不设兼容层的额外收益：

| 省掉的东西 | 说明 |
|---|---|
| 80 条 `compatMetrics` map + `EnsureMetric` 里的复用分支 | 约 20~40 行代码与一次查表 |
| "已上线指标的标签集合不可变" | 一条**为兼容层而存在**的临时约束 |
| "迁完记得删掉兼容层" | 一个只有靠人记住才会发生的收尾动作 |

**唯一必须保留的动作**：删静态之后，旧 `data` 路径不静默丢弃——**显式返回 4xx 并在日志打出 `source=hard 的上报走了已废弃路径`**。这不是为了兼容，而是为了**可观测**：否则你无从知道还有哪些机器落在旧路径上，那些来源会静默缺数据、直到有人看面板才发现。

## 三、目录结构

```
server/
├── cmd/server/main.go            # 入口：配置、路由、启动、优雅退出
└── internal/
    ├── config/                   # 配置加载（yaml.v3 + 环境变量覆盖）
    ├── ingest/                   # 接收链路：解密 → 解压 → 校验 → 分流
    │   ├── handler.go            #   HTTP 入口
    │   ├── decode.go             #   AES-GCM + gzip
    │   ├── validate.go           #   时间戳、字段、长度、条数校验
    │   └── pipeline.go           #   批量写队列
    ├── registry/                 # 动态指标注册表（现 Metrics/Dynamic.go）
    ├── pluginrepo/               # 制品仓库：index、下载、HMAC 校验、打包
    ├── projectdict/              # projects.json（代号 → 中文名）
    ├── whitelist/                # （现 IpPass）
    ├── selfmetrics/              # service 自身监控指标
    └── metricsapi/               # /metrics 暴露（promhttp 薄封装）
```

**为什么把 `registry` 与 `ingest` 分开**：注册表的生命周期比单次请求长（sweeper 常驻、指标跨请求复用），混在 handler 包里会让锁与状态难以审计。这也让「注册表」可以单独做单测，不需要起 HTTP。

## 四、接收链路

### 4.1 端点契约

| 路径 | 方法 | 认证 | 说明 |
|---|---|---|---|
| `/metrics_data` | POST | AES 密钥 | 唯一的数据入口 |
| `/metrics` | GET | `ipPass` 白名单 | Prometheus 拉取（promhttp） |
| `/agent/index.json` | GET | `update.ipass` | 制品清单 |
| `/agent/download/<name>/<version>/<os>/<arch>` | GET | `update.ipass` + HMAC | 制品下载 |
| `/healthz` | GET | 无 | 进程存活（给 Docker healthcheck） |

> **`/version` 与 `/agent/agent` 已废弃**：壳不做自更新（更新交给 systemd / 容器编排），这两条端点连同 `serveStaticFile` 一并删除。`update.ipass` 只保留给**插件**制品下载。原因见 `壳设计.md §十一`。

`/metrics_data` 的请求体是 `application/octet-stream`，内容是 `AES-GCM(nonce || ciphertext)`，明文是 `gzip(JSON)`。

响应：

- `200 {"code":200,"msg":"ok"}` —— 校验通过且已**入队**（不代表已写入）
- `400 {"code":400,"msg":"<具体原因>"}` —— 校验或注册失败，原因必须具体（`指标名 hard_cpu_percent 含非法字符`、`common 中的标签 "x" 未在 labels 中声明`），插件作者靠它排错
- `405` 非 POST
- `413` 解压后超限

> **`200` 的语义是「已接受」而不是「已写入」。** 这一点与旧路径一致，也是 agent 侧重试逻辑简单的原因：agent 只关心"服务端有没有收下"，不关心"什么时候生效"。

### 4.2 解密与解压

```go
MaxRequestBodySize = 10 << 20   // 10 MiB 压缩态
MaxDecompressedSize = 64 << 20  // 64 MiB 解压后
MaxClockSkew = 5 * time.Minute
```

顺序固定为 **先限长 → 再解密 → 再限长解压**：压缩包是攻击者可控的，`gzip` 的膨胀比可以极大，所以解压必须用 `io.LimitReader` 而不是"读完再看长度"。

非对称的 10:64 是刻意的——正常上报（1500 台里最大的一台，含 K8s 容器全量）压缩后不过几百 KB，留出 10 倍余量；而解压上限 64 MiB 是按「服务端单次分配峰值」定的，不是按数据量定的。

**密钥**：`SetEncryptionKey(string) error`，启动时长度非 16/24/32 即 `Fatal`；环境变量 `MONITOR_ENCRYPTED` 优先于配置文件（这样镜像里可以不落密钥）。热加载路径上出现非法值只告警并**保留原密钥**——不因为一次配置写错就让全网上报失败。

### 4.3 校验顺序（每一步失败都返回 400 且原因具体）

| # | 校验 | 上限常量 | 失败理由 |
|---|---|---|---|
| 1 | Content-Type 与请求体长度 | `MaxRequestBodySize` | 413 |
| 2 | 解密 | — | 400 `解密失败`（不透露是密钥错还是数据坏） |
| 3 | 解压（流式限长） | `MaxDecompressedSize` | 413 |
| 4 | JSON 解析 | — | 400 `payload 格式错误` |
| 5 | `project` 非空且在 `projects.json` 中 | — | 400 `未知 project` |
| 6 | `source` 格式 `^[a-zA-Z][a-zA-Z0-9_]{0,31}$` | — | 400 |
| 7 | `timestamp` 与本地时间偏差 | `MaxClockSkew` | 400 `上报时间戳无效` |
| 8 | `schema == "v2"` | — | 400 `不支持的协议版本` |
| 9 | `len(metrics)` ∈ [1, 64] | `MaxMetricsPerReport` | 400 |
| 10 | 每个指标的 `name/help/type/labels` | 见 §5.4 | 400，带第几个指标的序号 |
| 11 | 每个指标 `samples` 条数 | `MaxSamplesPerMetric` | 400 |
| 12 | 所有 sample 的标签必须已在 `labels` 声明 | — | 400 `样本中的标签 "x" 未在 labels 中声明` |
| 13 | 标签值长度 | `MaxLabelValueLen = 512` | 400 |
| 14 | 采样总条数 | `MaxDataItems = 20000` | 400 |
| 15 | 注册（可能失败） | `MaxDynamicMetrics` | 400 `指标与服务端已注册的指标重名` |

**为什么校验必须在响应之前同步做完**：旧路径是「先 200 再异步」，字段写错就是数据静默消失，排查要靠翻日志。插件由人发布，让作者在第一次联调时就拿到 `指标名非法` 这种明确报错，比事后对账省太多。校验本身只是正则和 map 查找，1200 QPS 下不是瓶颈。

**唯一的例外**：`len(metrics) == 0` 的情况不报错，直接 200 —— 这对应"本轮没有采到任何数据"（比如 ssl 插件所有域名探测失败），不是错误。

### 4.4 协议分流：从"两条路径"收敛为"一条"

现状是 `SendPayload` 同时有 `Data` 与 `Metrics` 两个字段，靠 `len(payload.Metrics) > 0` 分流。目标态删掉 `Data` 与 `allowedSources`，只留声明式：

```go
type SendPayload struct {
    Project   string          `json:"project"`
    Source    string          `json:"source"`
    Timestamp int64           `json:"timestamp"`
    Schema    string          `json:"schema"`
    Metrics   json.RawMessage `json:"metrics"`
}
```

`Metrics` 用 `json.RawMessage` 而不是 `[]DeclaredMetric` 是刻意的：**metrics 的结构错误不应该连带整个 payload 被判 400**——先解出外层字段，再单独解 metrics，报错能精确定位到"metrics 字段格式错误"。

## 五、动态指标注册表

这是 service 的心脏。它面对的是一个旧路径没有的风险：**指标的形状由上报方决定，不再由服务端代码决定**。因此每一条限制都是为了「不让上报方决定服务端的内存占用」。

### 5.0 指标契约：描述随每轮上报携带（2026-09-18 定）

**service 不知道任何指标的名字，也不需要知道。** 插件在采集代码旁声明指标，SDK 自动收集成描述，随每轮数据一起发来；service 首次见到就注册，以后按名字匹配。三条展开：

1. **不做清单、不做清单校验。** service 只做形状校验（名字/标签正则、数量与基数上限）——校验的是"这份声明合不合法"，不是"这份声明我认不认识"。校验在 `Metrics/Dynamic.go` 的 `validateSpec`，那里的规则**不含任何业务指标名**。
2. **但要记录见过的指标。** 记首次出现与最后出现时间，**不阻断上报**。这不是清单，是观测结果：清单是事前人工维护的，这里是事后自动积累的。用途有两个——运维视图（"当前全网有哪些指标、各自多久没更新"），以及**缺失检测**（某 project 某插件的指标超时未上报）。没有它，某台机器静默失效要等到有人问"这个项目的图怎么少了一条线"才会发现。
3. **描述必须每轮重发。** 刻意不支持"首次描述、后续只发值"的两阶段协商：那要求 service 主动回一句"这个指标我不认识"，随之而来的是 service 重启后描述丢失、重发时机、并发重发幂等一整串问题。每轮重发换来的是 **service 重启即自愈**——下一轮上报就把形状带回来了，不需要任何协调代码。代价是报文里多一段高度重复的描述，被 gzip 吃掉大半（§6.7 有量化），另有 §5.6 的三条纪律约束。

**为什么不做清单（记录在案，避免日后重推）**：指标名、标签、Help 本质上就是采集代码的一部分——写下 `cpu_percent` 那段采集逻辑的时候，指标名已经定了。再要求维护一份清单，等于把同一份知识写在两个地方，每加一个指标都要改两处。这一条被明确否决："基本都是我写，但不想改指标的时候又是改服务端又是改插件。"

### 5.1 数据结构与锁

```go
type DynMetric struct {
    Name, Source, Help string
    Labels  []string      // 业务标签，只读快照
    Timeout time.Duration
    Registry *prometheus.Registry

    gauge *prometheus.GaugeVec

    mu         sync.RWMutex   // 保护下面各项
    labels     []string
    timeout    time.Duration
    series     map[string]*seriesEntry   // 标签值拼接 key → 最近出现时间
    warnedFull bool
    firstSeen    time.Time    // 注册时刻，只写一次
    lastSeen     time.Time    // 每次 Observe 在锁下更新，供 §5.0 第 2 条的观测视图与缺失检测
    reRegisterN  int          // 形状反复变化的计数，见 §5.6 的重注册抑制
    reRegisterAt time.Time    // 计数窗口起点
}

var (
    dynMu          sync.RWMutex
    dynamicMetrics = map[string]*DynMetric{}   // 指标名 → 定义，全局唯一
)
```

**锁顺序约定（必须遵守，否则死锁）：`dynMu` → `DynMetric.mu`，永远不可反向获取。**

热路径设计：`EnsureMetric` 先走 `dynMu.RLock()` 快路径（已存在且形状一致 → 只更新阈值），绝大多数请求在这里返回，不进写锁。分支细节：

| 情况 | 处理 |
|---|---|
| 不存在 | 建 GaugeVec → `Register` → 入 map |
| 存在，同名同源同标签 | 只更新 `timeout`（快路径，无写锁） |
| 存在，同名**异源** | **拒绝**：`指标 x 已由 source A 注册，source B 不能重复注册` |
| 存在，同源但**标签集合变了** | 注销旧 GaugeVec → 注册新的 → **清空该指标全部时间序列**（旧序列的标签值数量已不匹配） |
| 指标总数达 `MaxDynamicMetrics` | 拒绝 |

「标签集合变化时清空序列」是个**破坏性操作**，必须有日志。它换来的是「插件改了标签不用重启服务端」，这个权衡是值得的（插件升级是常态，重启 service 会全网断图）。

### 5.2 写入：`Observe`

```go
func (m *DynMetric) Observe(project string, samples []Sample) (written, dropped int)
```

对每条样本：

1. 拼标签值数组：`[project] + [labels[i] 对应的值]`（**`project` 恒为第 0 位**，由服务端注入）
2. 用 `\x1f`（不可见字符）拼接成序列 key（用不可见字符是为了不与标签值本身冲突）
3. 序列不存在 → 检查基数上限，超限则 `dropped++` 并 **warn-once**（不刷屏）
4. 序列已存在 → **以首次记录的 `values` 为准**（避免 `common` 缺省导致同一 key 两次写入不同的标签值组合）

第 4 条容易忽略：如果第一次上报带了 `common`、第二次没带，标签值数组会不一致，`WithLabelValues` 会创建出两个不同的时间序列。所以 `series` 里存首次的 `values` 并在后续复用。

### 5.3 超时注销

`sweep` 每 5 秒扫一次（`StartDynamicSweeper`），摘掉「超过 `timeout` 未更新」的序列，调用 `gauge.DeleteLabelValues` 同时从 `series` 删除。

**为什么是 5 秒**：所有阈值都有 20s 下限，5 秒精度足够；开销只与序列数线性相关。

**`heart` 的语义差异**：旧路径里心跳超时是 `is_active = 0`（**保留序列**），因为 Grafana 面板靠 `is_active == 0` 判断离线。动态注册表的行为是**删除序列**。

**已定（2026-09-20）：方案 A —— 面板改 PromQL，协议不动。**

| 方案 | 做法 | 代价 | 结论 |
|---|---|---|---|
| **A. 面板改 PromQL** | 面板用 `absent(is_active{...})` 或 `is_active != 1` | 改面板，一行 | **✅ 采用** |
| B. 壳自己兜 | 壳每轮上报 `is_active=1`，并上报**所有已知主机**的 `is_active` | 壳不知道谁离线 | ✗ 否决 |
| C. 协议加字段 | `DeclaredMetric` 增加 `on_timeout: "zero"` | 改协议 + 改注册表，但不用改面板 | ✗ 否决 |

**为什么不用 C**：它是唯一不动面板的方案，却把**展示问题**（"面板怎么表达离线"）变成协议字段——`on_timeout` 要进 `plugproto`、服务端注销逻辑要多一个分支，只为省面板上的一行。而"序列还在 = 这台机器在报"本来就是 Prometheus 的惯用语义，`absent()` 就是为这个场景设计的。

**唯一外部动作**：把用到 `is_active` 的查询从 `is_active == 0` 改为 `absent(is_active{...})` 或 `is_active != 1`。

### 5.4 防护常量表

现状已实现（保留）：

| 常量 | 值 | 作用 |
|---|---|---|
| `MaxMetricNameLen` | 200 | |
| `MaxMetricHelpLen` | 1024 | |
| `MaxLabelsPerMetric` | 32 | |
| `MaxSamplesPerMetric` | 20000 | |
| `MaxMetricsPerReport` | 64 | |
| `MaxSeriesPerMetric` | 50000 | **最关键**：没有它，插件不断变化标签值就能吃光内存 |
| `MaxDynamicMetrics` | 2000 | |
| `MinTimeout` | 20s | 防止插件声明 1s 导致序列频繁增删 |
| `MaxTimeout` | 24h | |
| `DefaultTimeout` | 45s | 未声明时兜底 |

**已定（2026-09-20）新增以下三条：**

| 常量 | 值 | 理由 |
|---|---|---|
| `MaxSeriesTotal` | 200000 | 现在的上限是「每个指标 5 万序列」，2000 个指标 = 10 亿，**等于没上限**。需要一个全局序列总数闸门 |
| `MaxSamplesTotalPerReport` | 20 万 | 现有 `MaxDataItems=20000` 只对单指标生效，`64 × 20000 = 128 万` |
| `MaxLabelValueLen` | 512（已有） | 需在**合并 `common` 之后**再校验一次长度 |

**全局闸门为什么必须加**：单指标上限只挡住"一个插件发疯"，挡不住"2000 个指标各写 5 万序列"。真实数字按 `1500 台 × 每台每指标 1 条序列` 估算，容器指标是大头（假设每台 100 个容器 × 8 个指标 = 120 万条，这也太大）——**实际应该在插件侧限制上报范围**（只关心 namespace / 只报有 request/limit 的容器），但服务端必须有兜底闸门。

### 5.5 为什么不做兼容层（否决记录）

`EnsureMetric` 撞上静态定义时，本可以加一层"复用已有 GaugeVec"的中转（原方案的 `compatMetrics`），让新旧上报方写同一个 `GaugeVec`，从而支持"逐台迁移、面板零改动"。**本项目不采用**——它要解决的问题在这里不存在。

评估过的三条路：

| 方案 | 作用 | 结论 |
|---|---|---|
| ① `compatMetrics` 查表复用现有 `GaugeVec` | 让新旧 agent 并存、面板零改动、可逐台推进 | **否决**：本项目不出现新旧并存（§2.2），为它付出"80 条 map + 复用分支 + 迁移期标签不可变 + 迁完必须记得删"不划算 |
| ② 指标名加 source 前缀 + Prometheus relabel 去前缀 | 绕开撞名，名字不用变 | **否决**：多一层改名机制、要写 relabel 规则、要小心误伤，收益为零 |
| ③ 直接删静态定义与旧路径 | — | **采用**（§2.2） |

> 方案 ① 曾是本文档的正式方案，并在 `workflow` 里排成过独立任务（05 兼容复用层）。2026-09-20 确认"新架构不会与旧架构并存"后，该任务随之下线。

**一个仍需注意的技术细节**：动态注册路径的标签**顺序即填充顺序**，形状比对时**逐位比较**（`GaugeVec.WithLabelValues` 按创建时的顺序填值）。这与要不要兼容层无关，任何情况下都不能改成集合比较——否则会写出"值对但标签串位"的序列，比直接报错更难发现。

### 5.6 描述每轮重发的代价、纪律与兜底

§5.0 契约的实现后果集中在这里。

**代价（量化见 §6.7）**：每轮多一次描述 JSON 解析（约 30 μs）与形状比对（约 40 μs），100 QPS 下单核约 0.7%。**这不是选静态指标的理由**——链路里 75% 的开销（gzip 解压 + 采样数据解析）两者完全共用。

**抑制手段**：形状比对走 `dynMu.RLock()` 快路径，命中"同名同源同标签"时**只更新 `timeout`**，不进写锁、不碰 `GaugeVec`。稳态下每轮成本 = 一次 map 查找 + 一次切片比较。

**三条纪律（插件侧必须遵守，违反会让曲线碎掉）**

| 纪律 | 违反的后果 |
|---|---|
| **描述必须是常量**：`help` 里不拼时间戳/主机名/轮次号 | 每轮判定"形状变化"→ 注销重建 `GaugeVec` + **清空该指标全部时间序列** |
| **指标名只增不改**：改名要新增 `xxx_v2`，不要改 `xxx` 的含义 | Grafana 面板与告警规则引用的是名字，改名即断图 |
| **标签集合一旦上线不再变更** | 同上。改标签集合会让服务端注销旧 `GaugeVec` 并**清空该指标的全部序列** |

**service 侧兜底（必须做，否则"插件写错"会升级成"服务端雪崩"）**

1. **形状变化触发重注册时必须打日志**，含旧/新标签集合与来源 source。没有这条日志，事后的曲线碎片无法归因。
2. **重注册抑制**：记录窗口内次数（`reRegisterN` / `reRegisterAt`），超过阈值（建议 10 次/分钟）后**拒绝重注册、保持原形状并告警**。

第 2 条不是洁癖。一个 `help` 里拼了时间戳的插件，会让 service **每秒重建 `GaugeVec` 并清空序列**——那不只是它的曲线没了，是这台机器在这个指标上的数据全丢，同时把注册表的锁打热。相比之下，拒绝它、保留旧形状、报一条明确的告警，是更小的损失。

## 六、写入路径与高并发

### 6.1 量级先算清楚

| 项 | 估算 |
|---|---|
| 上报频率 | 1500 台 ÷ 15s = **100 QPS**（心跳/硬件/nginx 各 15s，但同一台机器同一刻只发一次聚合请求） |
| 最坏情况 | 相位打散失效，全挤在一秒 → **1500 QPS** |
| 单请求大小 | 压缩后 10~200 KB，解压后 100 KB~2 MB |
| AES-GCM 解密 | 微秒级，**不是瓶颈** |
| 真正的瓶颈 | ① 时间序列 map 的**锁竞争** ② 序列数量带来的 **GC 压力** |

**结论：瓶颈是锁竞争与 GC，不是 CPU。** 所以优化方向只有三条：把请求摊开、把锁持有时间缩短、把队列做有界。

### 6.2 相位打散（在 agent 侧，但服务端要校验效果）

壳的首次采集时间加 `rand(0, interval)` 抖动，把 100 QPS 的尖峰摊成一条平线。**这是唯一能把峰值降低两个数量级的改动**，必须在 agent v1 就有（改 agent 是最贵的事）。

服务端要做的：暴露 `monitor_ingest_qps`（按秒聚合），这样能**验证**打散是否生效——如果每秒请求数分布仍然尖峰，说明打散没做对。

### 6.3 批量写（把锁持有时长降一个数量级）

现状是每个请求直接 `Observe` 写 GaugeVec，每次都要拿 `DynMetric.mu` 写锁。改为：

```
请求 → 校验注册（同步） → 入批量队列（按 source+project 分组）
                                   ↓ 每 200ms 或累积 500 条
                            合并后一次拿锁批量写
```

效果：1500 次/秒的加锁变成 5 次/秒，锁竞争下降约 300 倍。

代价：`200` 的语义变成"已入队"，最多 200ms 后才可见。对 15 秒的采集周期，200ms 抖动无意义。

### 6.4 队列满：丢弃并计数，**不要**沿用现在的降级

现状 `taskQueue` 满了会走 `safeExecute(task)` —— **在 HTTP handler 的 goroutine 里同步执行**。这是雪崩起点：

```
上报洪峰 → 队列满 → handler 里同步做重活 → handler 变慢
        → 请求堆积 → 连接数暴涨 → 内存飙升 → 整个 service 一起死
```

**改为：入队失败直接丢弃 + `monitor_ingest_dropped_total` 计数器 + warn（每 10 秒最多一条）。** 丢弃的是 gauge 数据、周期 15 秒，丢一轮不影响趋势；而背压传导到接收层会让服务端整体不可用，两者不成比例。

### 6.5 分片锁

现有 256 个 FNV-1a 分片锁按 source 分片。批量写重构后，分片 key 从 `source` 扩展为 `source + ":" + project`——因为批量队列是按这个二元组分组的，同组分片内串行、不同组并发。

**注意**：分片锁现在保护的是旧路径的 `map[metricLabel]timestamp` 结构。动态注册表自己有 `DynMetric.mu`，所以分片锁的职责会收缩为「保护批量队列的分组结构」。如果批量队列用 channel + 单 goroutine 消费，可以完全去掉分片锁——**这是重构中应当顺手清理的部分**，不要把两套锁机制都留着。

### 6.6 service 自身监控指标（必须做）

用这套系统监控这套系统，否则 service 出问题时你没有任何信号：

| 指标名 | 类型 | 含义 |
|---|---|---|
| `monitor_ingest_requests_total` | counter | 接收到的上报请求数（**这是唯一允许 counter 的地方**，服务端自身指标不参与超时注销，不存在"序列重现导致 rate 尖峰"的问题） |
| `monitor_ingest_rejected_total{reason}` | counter | 被拒绝数，按原因分类（解密失败/校验失败/重名…） |
| `monitor_ingest_dropped_total` | counter | 队列满丢弃的采样数 |
| `monitor_ingest_queue_depth` | gauge | 队列水位 |
| `monitor_ingest_batch_flush_seconds` | histogram | 批量写耗时 |
| `monitor_dynamic_metrics` | gauge | 已注册的动态指标数 |
| `monitor_dynamic_series` | gauge | 时间序列总数（基数健康度） |
| `monitor_dynamic_swept_total` | counter | 超时摘除的序列数 |
| `monitor_repo_downloads_total{name,version}` | counter | 制品下载次数（看插件升级是否铺开） |
| `monitor_agent_versions{version}` | gauge | **各 agent 版本的在线数量**——决定真要滚壳时的工作量 |

最后一条特别重要：你选择了人工替换 agent 二进制，那么「多少台还在跑旧版本」就是你必须随时能回答的问题。壳在心跳里已经有 `agent_version`，service 侧顺手统计即可。

### 6.7 接收链路的耗时分解与优化优先级

§6.1~6.4 是「把请求摊开」的架构级削峰。这一节算的是链路级的账：**单次上报的时间到底花在哪，以及值不值得为它改变架构选择。**

以下是**量级估算，不是实测值**（真实数字由 §12.3 的压测产出）。以单次约 16 KB 压缩载荷为例：

| 步骤 | 静态方案 | 动态方案 | 说明 |
|---|---|---|---|
| 读取请求体 | 5 μs | 5 μs | |
| AES-GCM 解密 | 10 μs | 10 μs | 有硬件加速，**不是瓶颈** |
| **gzip 解压** | **100 μs** | **100 μs** | 最贵的两步之一 |
| **JSON 解析采样数据** | **120 μs** | **120 μs** | 最贵的两步之一 |
| JSON 解析指标描述 | — | 30 μs | 动态方案独有 |
| 形状比对与查找 | — | 40 μs | 动态方案独有 |
| 写入 GaugeVec | 60 μs | 60 μs | **两者完全一样** |
| **合计** | **295 μs** | **365 μs** | 动态比静态慢约 **19%** |

**换算成机器成本**：100 QPS（1500 台 ÷ 15s）下，这 70 μs 的差值 = 7 ms/秒 = **单核的 0.7%**；即使相位打散完全失效、全挤在一秒（1500 QPS），也只有 105 ms/秒 = **单核 10.5%**。

**结论：不要为了这 19% 放弃动态指标。** 它换来的代价（每次加指标都要改服务端 + 插件两处）是**架构属性、不可优化**，而它省下的是 0.7% 的单核。更关键的是，295 μs 里有 **220 μs（75%）是两者共有、选哪个都跑不掉的**。

#### 优化优先级（按收益排序）

**第一优先：替换 gzip 实现。**

标准库 `compress/gzip` 换 `github.com/klauspost/compress/gzip`，解压快 2~4 倍；`compress/flate` 同理可换 `klauspost/compress/flate`。

- **收益**：单这一项省 50~75 μs，**与「静态 vs 动态」的差异相当甚至更大**。
- **代价**：几乎为零——输出仍是标准 gzip 流，**不改变线格式，两端不需要同时升级**。这是本设计里性价比最高的一处改动。
- **只在服务端换，不要在壳里换。** 收益全在解压侧（agent 的压缩有 15 秒周期余量，根本不是瓶颈），而**壳契约 I3 规定壳的依赖白名单是「stdlib + yaml.v3」**。为一个不需要的收益去破坏壳的「零第三方依赖」，不划算。

**第二优先：减小上报载荷。**

杠杆最大的一项，因为 gzip 解压与 JSON 解析的成本**都与载荷大小线性相关**——载荷减半，这两步同时减半。

- **容器指标是大头**（见 §5.4 末尾）：全 namespace × 全部容器 × 8 个指标，1500 台能轻易凑出百万级序列。**已定（2026-09-20）**：`k8s` 插件提供 `plugins.k8s.namespaces`（白名单，空 = 全部）与 `only_with_limits` 两个配置项来收缩范围，**默认全量**（与现状一致），由运维按集群规模收紧（插件侧要求见 `插件设计.md §10`）。
- **标签值长度**：`MaxLabelValueLen = 512` 偏大，长标签值既撑大载荷又撑大序列基数。业务标签值绝大多数在 64 字节以内，建议逐字段设更严的上限。
- **小载荷可以不压缩**：压缩 2 KB 的 CPU 可能高于省下的网络传输。属可选项（需协议加标志位），不急。

**第三优先：分片 `dynMu`。**

动态方案的性能劣势集中在两把锁上（注意 §6.5 讲的是**旧路径**的分片锁，这里说的是**动态注册表自己**的锁）：

- 全局 `dynMu.RLock()`：`EnsureMetric` 的快路径**每请求每指标**都要拿一次。高并发下 RWMutex 的 RLock/RUnlock 是成对原子操作，存在 cache line 争用。
- 每指标的 `DynMetric.mu`：每次写值都要拿写锁。

做法与现有 256 分片锁一致：按指标名 FNV-1a 哈希分片成 N 个 `dynMu`；或更彻底一些，把「形状比对结果」缓存在请求侧（同一个插件的形状在一轮内不会变），避免每轮重复比对。

**收益只在 1500 QPS 的极端场景下可见，100 QPS 下几乎无感——所以它排在第三，不要过早优化。**

#### 一句话结论

**动态方案的性能劣势是「可优化」的（分片、缓存形状、批量写），静态方案的「改两处」是「不可优化」的（架构属性，不是实现细节）。** 所以「为了性能选静态」这个理由在任何量级下都不成立——真到瓶颈时，上面三件事的收益都大于它，而且都不会破坏「新增指标只改插件」。

## 七、插件制品仓库

### 7.1 制品布局（镜像内）

```
/data/artifacts/
├── index.json                          # 清单，agent 每次检查插件更新前先拉它
├── hard/
│   ├── 1.2.0/linux/amd64/hard.tgz
│   └── 1.1.0/linux/amd64/hard.tgz
├── nginx/  ssl/  k8s/
```

制品包 `hard.tgz` 内含：`hard`（二进制）、`default.yaml`、`manifest.yaml`。**必须整包分发**——只发二进制会出现"新二进制配旧默认配置"的版本错配。

### 7.2 `index.json`

```json
{
  "generated_at": "2026-09-18T15:00:00+08:00",
  "plugins": {
    "hard": {
      "latest": "1.2.0",
      "min_agent_version": "1.0.0",
      "platforms": {
        "linux/amd64": { "sha256": "…", "size": 5242880, "url": "…" },
        "linux/arm64": { "sha256": "…", "size": 5011200, "url": "…" }
      }
    }
  }
}
```

- `min_agent_version` 是**"agent 终生不改"下唯一的兼容阀门**：插件用了 `proto=2` 的新能力时，靠它挡住老壳。
- `platforms` 必须列全；agent 找不到自己平台时**保持旧版本并告警**，绝不静默降级。

### 7.3 下载认证（复用 AES 密钥，不引入证书体系）

```
GET /agent/download/hard/1.2.0/linux/amd64
Headers: X-Agent-Ts: <unix 秒>, X-Agent-Nonce: <随机串>, X-Agent-Sign: HMAC-SHA256(key=encrypted, msg=path|ts|nonce)
```

四条校验，缺一不可：

1. `X-Agent-Ts` 与服务器时间偏差 ≤ 5 分钟
2. `nonce` 在 10 分钟窗口内未重复（内存 LRU）
3. HMAC 签名正确
4. 来源 IP 在 `update.ipass` 白名单内（**双保险**：签名挡伪造，白名单挡扫描）

用 AES 密钥做 HMAC 是安全的：算法族不同、用途域分离；但 service 端**只允许这一套密钥**，不要再派生别的用途。

### 7.4 与旧实现的衔接

旧实现是把 `agent` 二进制放在静态目录里，由 `serveStaticFile` 直接返回，路径写死 `/agent/agent`（配套 `/version`、`/agent/agent.sha256`）。

**这套通道整体废弃**：壳不做自更新（更新交给 systemd / 容器编排，见 `壳设计.md §十一`），所以制品仓库**只服务插件制品**，agent 不再进入制品体系。删除范围：`serveStaticFile` 与三个端点。`update.ipass` 白名单保留，只用于插件制品下载。

老 agent 换完之前这几个端点可以留着（标记废弃即可），换完随旧链路一起删——与静态定义的清理节奏一致。

## 八、白名单

三组白名单，规则完全不同，是最容易踩坑的地方：

| 端点 | 使用 | 说明 |
|---|---|---|
| `/metrics` | `ipPass` | 放 **Prometheus 的地址**（通常 1~2 个） |
| `/agent/index.json`、`/agent/download/*` | `update.ipass` | 放 **所有 agent 的地址**；未配置时回退 `ipPass`。**只服务插件制品** |
| `/metrics_data` | **无白名单** | 靠 AES 密钥认证 |

```go
func (w *IPWhitelist) Allowed(ip string) bool
func (w *IPWhitelist) SetEntries(entries []string)
func (w *IPWhitelist) Refresh()          // 每 5 分钟重解析域名
func SetTrustProxy(enabled bool)
func (w *IPWhitelist) clientIP(r *http.Request) (string, error)
```

**关键行为（必须记住的两条）**：

1. **空白名单 = 拒绝所有**（`flatSet` 与 `networks` 都为空时 `Allowed` 直接返回 false → 404），不是放行所有。没有"关闭白名单"的开关。
2. **代理头只在「直连方本身可信」时才被采信**（直连 IP 在白名单内或为本机回环）。所以 nginx 反代场景下，**nginx 的 IP 也必须进白名单**，否则服务端拿 nginx 的 IP 去判断，直接 404。

支持字面 IP、CIDR、域名（域名每 5 分钟重解析 DNS）。**生产建议全用 CIDR**——域名会随 DNS 变化导致白名单漂移，且 `ipPass` 里放 `www.example.com` 这类占位符会解析到公网 IP（现有配置里就有，应清理）。

`projects.json`（代号 → 中文显示名）保留：

**`project` 的中文映射必须留在服务端**，不能下发给上报方：这是全系统唯一一处展示层转换，下放会导致同一个项目在不同插件里写成不同值，Grafana 面板分裂成多套。

### 配置收敛建议

现状用 `yaml.v3` 与 `viper` 各读一遍 `config.yaml`，且 `projects.json` 不在热加载范围。重构时统一为一处加载（`gopkg.in/yaml.v3` 即可，service 侧的键很少，不需要 viper），并把 `projects.json` 纳入同一个 reload 流程。

## 十、无 agent 的上报方

`trafficSwitching` 由流量切换平台直接上报，本机不装 agent。它走**同一条声明式路径**，只是 `source = "trafficSwitching"`：36 个指标全部由它自己声明。

两种形态，需要选一个（§14 待拍板）：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. 直连上报（推荐）** | 平台直接 POST `/metrics_data`，自己实现 gzip+AES-GCM | 服务端零特殊逻辑；平台侧多一个加密实现（约 50 行） |
| B. 装一个"转发插件" | 在平台所在机器装壳 + 一个转发插件，插件从平台 API 取数再上报 | 平台侧简单，但要多部署一个 agent；且这个 agent 自己的存活成了新故障点 |

选 A。它本来就不是装在机器上的采集器，为它引入一个 agent 是增加了不可靠环节。

## 十一、Docker 打包

多阶段构建，最终镜像 `distroless` 或 `alpine`：

```
FROM golang:1.23-alpine AS build
  COPY . /src
  RUN cd /src/server && CGO_ENABLED=0 go build -trimpath -ldflags "-s -w" -o /out/monitor-server ./cmd/server

FROM gcr.io/distroless/static-debian12
  COPY --from=build /out/monitor-server /monitor-server
  COPY /data/artifacts /data/artifacts          # 制品随镜像分发（用户要求）
  ENV MONITOR_ENCRYPTED=""
  EXPOSE 8080
  ENTRYPOINT ["/monitor-server"]
```

要点：

- **制品随镜像打包**：插件版本与 service 版本绑定，回滚镜像即回滚插件，不会出现"service 回滚了但插件还是新的"。
- **容器内 GOMAXPROCS 与宿主核数不匹配是常见性能坑**，引入 `uber-go/automaxprocs`（一行 import）。
- 密钥走环境变量，不进镜像层。
- 需要持久化的只有制品目录（若是只读挂载也没问题，因为制品是只读的）。

**现状缺口**：没有优雅停机。应加 `http.Server.Shutdown(ctx)`，停止接收新请求 → 停止 sweeper → flush 批量队列 → 退出。否则重启会丢掉队列里最多 200ms 的数据（影响很小，但退出时静默丢数据不是好习惯）。

## 十二、测试与压测基线

### 12.1 单测

| 对象 | 用例 |
|---|---|
| `registry` | 同源重复注册复用；**异源同名拒绝**；标签集合变化时重注册且序列清空；单指标基数超限丢弃且 warn-once；**全局序列总数超 `MaxSeriesTotal` 时拒绝新建并计数**；单次上报样本总数超 `MaxSamplesTotalPerReport` 时拒绝；超时摘除；`MinTimeout`/`MaxTimeout` 边界 |
| `ingest/decode` | 密钥长度 16/24/32；密文截断；gzip 膨胀炸弹（限长生效） |
| `ingest/validate` | 逐条对照 §4.3 的 15 项，每项一个失败用例 + 一个通过用例 |
| `whitelist` | 空白名单拒绝所有；CIDR 边界；代理头只在可信直连时采信；域名解析失败保留旧值 |
| `pluginrepo` | HMAC 签名正确/过期/nonce 重放；路径穿越（`../`）拒绝 |

### 12.2 端到端（复用已验证的模板）

临时目录放 `config/`（`port=18082`、`ipPass=[127.0.0.1]`、`trustProxy=true`）+ `projects.json`，构建后后台启动，用纯 stdlib 的 Go 客户端构造 `JSON→gzip→AES-GCM→POST` 跑断言。2026-09-17 已用这套跑通 33 项，重构后应扩充声明式路径的用例：

- 正常声明式上报 → 指标出现在 `/metrics`（校验 HELP、标签顺序含 `project` 在第 0 位）
- `schema: v1` → 400
- 指标名含 `-` → 400
- `common` 里有未声明的标签 → 400
- 样本里有未声明的标签 → 400
- 声明 `project` 标签 → 400
- 同一指标被两个 source 上报 → 第二个 400
- 超时后序列消失（`/metrics` 里查不到）
- 中文 project 映射正确

**Windows 执行注意**：模拟"非可信来源"要用 `net.Dialer{LocalAddr: <本机非回环 IP>}` 连到该 IP 自身；判断指标值要解析行尾数字，不要用 `") 0"` 这种子串匹配。

### 12.3 压测基线（准入条件，不达标不进入下一阶段）

| 项 | 目标 |
|---|---|
| 负载 | 1000 并发连接、每请求 50 KB 压缩体、持续 60 秒 |
| P99 延迟 | < 200 ms（不含异步写入） |
| 错误率 | 0（不含主动拒绝的非法请求） |
| 内存 | 稳态 RSS 增长 < 200 MB，无持续增长（观察 10 分钟） |
| 序列数 | 20 万条序列下 `sweep` 单次 < 100 ms |
| 打散验证 | 每秒请求数 P99 / 均值 < 3 |

**必须用 Go 写压测客户端**（`vegeta`/`k6` 要自己实现 AES-GCM 请求体，不如直接写）。压测前先确认 `ulimit -n` 足够（现有代码启动时会打印 FD 限制与 somaxconn 并在偏低时告警）。

## 十三、实现顺序（service 侧）

**这不是"迁移步骤"。** 不存在"旧系统还要继续服务一段时间"的场景，所以没有灰度、没有切换窗口、没有回退演练——这是**构建顺序**：

| 步 | 动作 | 退出条件 |
|---|---|---|
| 1 | **删旧链路**：80 个静态定义 + 旧 `data` 路径 + `HanderData.go` + 7 个 `UnRegister*.go` + `timeouts.go` + `allowedSources`；旧 `data` 路径**显式 4xx + 日志** | 相关 grep 无残留；`go build`/`go vet` 干净；代码量下降约一半 |
| 2 | 抽出 `internal/registry`、`internal/ingest` | 两包各自单测全绿 |
| 3 | 声明式路径端到端打通 + **80 个指标名逐个落地验证** | §12.2 的 9 条用例全过；80 个名字全部能注册成功 |
| 4 | 加自监控指标 `monitor_ingest_*` + 批量写 + 队列满丢弃计数 | `/metrics` 里能看到接收量、队列水位、丢弃计数、`reRegisterCount` |
| 5 | 上线制品仓库（index + 下载 + HMAC） | 手工 `curl` 能下载到制品并校验 sha256 |
| 6 | **压测基线达标**（硬闸门） | §12.3 六项全达标 |

**第 1 步放在最前是刻意的。** 静态定义不删，第 3 步的每一次端到端验证都会撞 `AlreadyRegisteredError` → 400；把它留到最后，等于让整个开发期都在跟一个**已知的、可一次性消除的**障碍较劲。

**第 3 步里的"80 个指标名逐个落地"是 §2.2 那条决策的兜底验证**：按 `插件设计 §5` 的映射表逐个构造最小声明并上报，全部能注册成功——这证明仓库里已无任何静态定义残留与之冲突。

**第 6 步是闸门，不是"尽量"**：接收端扛不住时，后面的壳与插件全部无意义。
