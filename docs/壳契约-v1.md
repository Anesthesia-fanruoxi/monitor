# Agent 壳契约 v1（冻结）

> 本文回答一个问题：**怎么保证插件怎么改，壳都不会被牵连。**
> 主文档 `docs/插件化架构设计.md` §2.3、§3.5 是原则，本文是把原则落成**可 grep、可 CI、可测试**的硬约定。
> 与主文档冲突时，以本文为准。

---

## 〇、先校准一句话："插件变更不影响壳"的准确含义

这句话**不能字面成立**——如果插件改掉 `collect` 响应的字段名，壳必然被打到。所以要先把它换成一句能证明的话：

> **凡是协议 v1 允许的插件演进（新增插件、增删指标、改标签、换语言实现），壳都不需要改动；壳对插件输出的全部认知，被限制在 1 个文件、4 个字段、约 110 行代码之内。**

这就是"影响面可枚举"：**超出这 4 个字段的一切内容，对壳在法律意义上不存在。** 插件在 `metrics` 里塞什么、塞多少、嵌套多深，壳不解析、不校验、不关心，只测量它的字节长度然后原样搬运。

壳的本质由此重新定义——**它不是"插件宿主"，而是一个"读一行、测长度、压缩、加密、发 HTTP"的通用搬运工**：连一个业务字段名都不认识。它的失败模式只允许与"进程活着吗、管道能读吗、字节能送到吗"有关，与"字节内容是什么"无关。

> **字段数在 2026-09-18 由 9 个收缩到 4 个。** 移出的五项是 `name` / `version` / `interval` / `timeout` / `status`，理由见 §2.5——一句话概括：**壳能从别处拿到的，就不该问插件要；壳拿不到的，也不要。** 契约此时尚未落地为代码，因此直接按本版实现，不存在"旧壳 + 新插件"的组合需要兼容。

由此推出一条很好的自检标准，本文第十一节的评审清单会反复用到它：

> **领域无关性检验**：如果新增一个壳的测试用例时，需要构造真实的 nginx / k8s / 磁盘数据才能跑起来，说明业务知识漏进壳了。
> 壳的测试只需要一个会 echo 固定 JSON 的假插件就应覆盖其全部逻辑。

## 一、壳的全部输入：四类，无第五类

壳能从外部世界读到的东西，一条不漏地列在这里。**表外的一切，壳都不读。**

| # | 输入 | 来源 | 壳用它做什么 | 出错的后果边界 |
|---|---|---|---|---|
| 1 | `config.yaml` | 用户手工维护 | 决定启用哪些插件、上报的 `project`、上报地址与密钥 | 启动自检失败则退出（§8）；热加载非法值保留旧值 |
| 2 | 插件 stdout 的信封 | 插件进程 | 只拿四样：请求配对、本轮成败、协议版本、指标字节块 | 零信任降级（§2），**绝不 fatal** |
| 3 | 进程状态 | 内核 | 退出码、管道可读写、进程存活 | 按 §5 隔离，只影响该插件 |
| 4 | service 的制品响应 | HTTP | `index.json` 制品清单、制品包本体、制品包校验值 | 失败则沿用本地已有制品，不中断采集 |

第 2 类就是唯一的"数据面"，也是全系统最需要钉死的一处边界。**壳从它身上只取 4 个字段**，其余一律不碰。

> **记录一次边界判断（2026-09-18）**：曾考虑为"插件自述状态"新增一条通道，候选之一是壳监听 `127.0.0.1` 供插件 POST。**已否决**，理由有两条：
> 1. 它会让壳多出**第 5 类输入**，而这类输入**本机上任意进程都能伪造**——要么不认证，要么壳得自造一套认证；再叠上端口分配、端口冲突、body 限制、超时，约 150 行**全部落在内核冻结区**（§10）。
> 2. 插件与壳之间**本来就有一根私有双向管道**。`stdin`/`stdout` 是最便宜且天然隔离的通道，再开一个网络接口去传同样的信息是净负债。
>
> 结论：**不新增通信机制、不新增输入类别。** 壳的输入恒为四类。（该诊断功能本身后来也整体砍掉了，见 §2.5。）

## 二、壳对插件输出的全部认知：4 个字段

### 2.1 Envelope —— 壳眼里的插件响应，只有这些

```go
// internal/proto/decode.go —— 壳里唯一允许读插件输出的文件
package proto

// Envelope 是壳对插件响应的全部认知。4 个字段，不再增加。
type Envelope struct {
    ID      uint64          `json:"id"`      // 1. 请求响应配对
    OK      bool            `json:"ok"`      // 2. 本轮成功与否
    Proto   int             `json:"proto"`   // 3. 协议版本，只接受 1
    Metrics json.RawMessage `json:"metrics"` // 4. 指标字节块，不透明，永不解码
}
```

`Metrics` 是 `json.RawMessage`，**它的内容壳永远不 `Unmarshal`**。壳只对它做两件事：测长度、算 sha256（可选，用于排障时确认两端看到的是同一份字节）。

这四个字段**全部是传输语义**，没有一个是业务字段——这是判断"某个东西该不该进信封"的唯一标准。凡是"插件知道的业务事实"（采集周期、插件版本、诊断信息、指标名列表），一律不进。

### 2.2 宽容解析：三种写法都接受

插件可能用 Go、Python、Shell 写，同一语义会被写成不同 JSON 形态。壳必须全部接受，否则"换语言实现"就会打到壳。

| 字段 | 接受 | 说明 |
|---|---|---|
| `id` | 数字 / 字符串数字 / 缺失 | 缺失时按"当前在途请求"匹配——壳一次只允许一个在途请求 |
| `ok` | `true` / `false` / 缺失 | 缺失视为 **false**（保守，宁可计一次失败） |
| `proto` | 数字 / 缺失 | 缺失视为 `1`；`> 1` **显式拒绝**并提示"需升级 agent" |
| 其它任何键 | 一律忽略 | 前向兼容的唯一手段 |

**宽容必须留痕**：所有降级走 `warn-once`（每个插件每个字段只告警一次，避免刷屏）。宽容却不告警，等于把插件的 bug 永久藏起来。

### 2.3 缺省降级表（插件少报字段 = 壳照常工作）

| 情形 | 取值 | 备注 |
|---|---|---|
| `metrics` 缺失 / 为空 | 本轮无数据，**不记为失败** | "这轮没采到"不是错误，`ok:true` 且无数据是合法的 |
| `ok:false` | 判该轮失败 + 计数 | `metrics` 内容一律忽略（不发送、不缓存） |
| `proto` 缺失 | 视为 `1` | |
| `proto > 1` | 拒绝该插件，不启动 / 停止重启 | 报"需升级 agent"，**不静默降级** |
| `id` 不匹配 | 丢弃该响应 + 计一次失败 | 不 panic、不串轮 |
| 整行不是 JSON | 判该插件失败（按"写坏 stdout"处理） | 见 §5 |

### 2.4 参数钳制表（不可信输入一律回落）

**凡是壳不能自己保证的数值，一律视为不可信输入**——包括插件自报的（输出长度）和配置文件里的（周期、阈值）。没有这张表，一个往 stdout 无限输出的插件会吃光内存，而一个 `interval: 0` 会让壳空转。

| 参数 | 允许范围 | 越界处理 |
|---|---|---|
| 单行 stdout | ≤ 8 MiB | 超限：kill 进程 + 判该轮失败（防无限输出） |
| 单轮输出总量 | ≤ 32 MiB | 同上 |
| 单插件并发 collect | 1（协议不支持并发） | 上一轮未结束则跳过本轮并计数 |
| `interval`（来源是配置，非插件） | `[1s, 30m]` | 回落 `30s` + 告警 |
| `timeout`（来源是配置，非插件） | `[2×interval, 30m]` | 回落 `2.5 × interval` |

最后两行**也必须留在表里**，尽管它们的来源已经从插件挪到了 `manifest.yaml` / `config.yaml`（§9）——**写配置的人同样会写错**，而一个 `interval: 0` 会让壳空转、一个 `timeout < interval` 会让时间序列在两轮之间被摘掉。

### 2.5 为什么这五项不在信封里（2026-09-18 决策）

信封曾经有 9 个字段：`id` / `ok` / `proto` / `name` / `version` / `interval` / `timeout` / `metrics` / `status`。收缩到 4 个不是"少写几个 key"，而是**把两类责任从插件手里拿走**：

| 移出字段 | 新来源 | 为什么 |
|---|---|---|
| `name` | `config.yaml` 的键名（= 目录名） | 壳本来就要用这个名字找目录、起进程、写日志前缀，插件再报一遍就是**第二份事实来源** |
| `version` | `agent-plugs/<name>/manifest.yaml` 的 `version` | 制品自己带着版本，壳下载/解压/校验时本来就在读它 |
| `interval` | `manifest.yaml` 的 `default_interval`，`config.yaml` 可覆盖 | 见下 |
| `timeout` | `manifest.yaml` 的 `default_timeout`，`config.yaml` 可覆盖 | 见下 |
| `status` | **整条线砍掉** | 见下 |

#### 为什么周期与阈值要移到静态声明

现状那个 bug（`k8s` / `k8sController` 用 45s 阈值配 60s 周期，时间序列在两次上报之间被摘掉、Prometheus 抓到断点）的根因，正是**周期和阈值都由插件在运行时自报，而且两者还能互相不一致**。搬到静态文件后有两个直接好处：

1. **可审计**：`cat manifest.yaml` 就知道这个插件打算多久采一次、阈值多少。运行时自报的东西，不启动进程是看不到的——**这恰好是最需要审计的时刻**（排障时插件可能已经起不来了）。
2. **可覆盖**：采集周期本质上是**运维参数**——某台机器 I/O 重，你想把它的采集周期从 15s 放宽到 60s，这是你的权利，不该被插件代码锁死。

代价是**插件作者改周期要改 manifest 并重新打包**，而不是改一行代码。考虑到周期本来就不该频繁变，这个代价可以接受。

#### 为什么诊断（`status`）整条线砍掉

它曾是第 9 个字段，用来让插件说出"kubeconfig 里的证书 11 月到期"这类**壳永远猜不到**的原因。砍掉的理由是**它到不了正确的终点**：

它的去向只有本机 `statusapi`（不上报、不落盘），而**壳已经有一份同源信息**——插件的 `stderr` 由壳逐行加 `[plugs/<name>]` 前缀转发进日志，`statusapi` 里也展示壳观测到的 `last_error`。为了让一句诊断文字进一个本机 JSON，要多背一个字段、一条 1 KiB 钳制、一份 SDK 状态缓冲和一条独立不变式（I9），**投入产出不成立**。

#### 一并留档：被否决的两个替代方案

1. **本地 HTTP 端点**（壳监听 `127.0.0.1` 供插件 POST）——会让壳多出第 5 类输入，且本机任意进程都能伪造；叠加端口分配、body 限制、超时后约 150 行全落在内核冻结区。
2. **隐藏状态文件**（如 `.plugs.state` 记录启用状态与版本）——会成为 `config.yaml` 与 `manifest.yaml` 之外的**第三份事实来源**，三者不一致时无法判断该信谁；而且它只覆盖了壳已经知道的部分。

将来若真要让插件健康度"出网"，正确做法不是复活字段，而是让**壳**把观测结果推导成一条独立指标（§14）。

#### 由此得到的分工规则：壳只注入自己算出来的值

字段收窄之后，"谁提供什么"也变得可判定。规则一句话：

> **凡是壳能从 `config.yaml` / `manifest.yaml` / 进程本身拿到的，都不注入插件；凡是插件能从自己所在机器拿到的，也不要壳给。**

| 值 | 谁提供 | 从哪来 |
|---|---|---|
| `project` | **壳，且只留在壳内** | `config.yaml`（§9）。它是上报报文的字段，**插件任何地方都不出现 project**——同一份二进制要能装在任意项目的任意机器上，而且插件也没有任何地方用得上它 |
| `source` | 壳 | 插件目录名 / `manifest.name` |
| `timestamp` | 壳 | 采集时刻 |
| 插件自己的配置 | 壳给**文件路径**，合并由插件读 | `config.yaml` 的 `plugins.<name>` 子树，经 `MONITOR_CONFIG`（§9）；壳不合并、不落盘 |
| 生效的周期 / 阈值 | 壳 | manifest 默认 + config 覆盖 + §2.4 钳制，结果经 env 交给 SDK 填 `timeout` |
| `hostname` 及其它本机事实 | **插件自己** | `os.Hostname()`、`/proc`、命令输出……（SDK 提供 helper） |

**`source` / `timestamp` 归壳侧，2026-09-20 定稿，不再悬置。** 两者都是"壳本来就知道"的事实：`source` 就是它按目录名调度的那个插件，`timestamp` 是它打包上报的时刻。反过来让插件报，信封要从 4 个字段回到 6 个、要走 §12 评审，还多两个可伪造点——而 `source` 由壳填时天然等于目录名，插件连冒名的机会都没有。**结论：信封保持 4 字段，协议不动。**

于是 `collect` 请求就是 `{"id":2,"cmd":"collect"}`（§3），**没有 `common` 参数**；插件进程环境里也没有 `MONITOR_PROJECT` / `MONITOR_HOSTNAME` / `MONITOR_AGENT_VERSION`。**壳注入的只有"壳算出来才有的值"，业务事实一条都不注入。**

> 这一条不是洁癖：**注入是单点故障**——壳算错一个值，全网所有插件的相关指标一起错；而插件自取的数据错了只错那一个插件，且它自己就能验证。少一处注入，就少一条"壳的问题升级成全系统问题"的通道。

## 三、防腐层：把影响面收敛到一个文件

主文档 §10 的 `internal/pluginmgr` 与 `internal/scheduler` 都会碰到插件数据，所以必须再切一刀——**所有与"插件输出长什么样"有关的知识，只准出现在 `internal/proto/` 里**。

```
agent/internal/proto/          ← 唯一的知识点，防腐层，约 110 行
├── decode.go                  Envelope 4 字段 + 上限检查 + 宽容解析
├── encode.go                  请求侧：hello / collect / shutdown 三行 JSON
└── proto_test.go              字段兼容性用例（不含任何监控领域知识）
```

这一层的对外接口极窄：

```go
func DecodeEnvelope(line []byte) (Env, error)  // 宽容；只在"根本不是 JSON"时返回 error
func EncodeHello(id uint64) []byte             // {"id":1,"cmd":"hello","proto":1}
func EncodeCollect(id uint64) []byte           // {"id":2,"cmd":"collect"}
func EncodeShutdown(id uint64) []byte
```

上游（pluginmgr / scheduler / transport）只拿到 `Env.OK` 与 `Env.Metrics` 两个值，**拿不到也不需要知道 `Metrics` 里是什么**。

> 注意：`interval` / `timeout` 已经**不在这条链路上**了（§2.5）。它们由 `config` 模块在启动时算好（manifest 默认值 + config 覆盖 + 钳制），直接交给 `scheduler`——**插件输出里没有任何调度参数**。这让 `proto` 比上一版少了 `Duration` 的宽容解析，行数预算从 160 降到 110。

> 这一层就是整套架构里唯一的"协议耦合点"。将来协议真要演进（proto=2），改动被限制在这个目录里，而不是散在十个文件里——这是"影响面可枚举"从口号变成结构的过程。

## 四、八条不变式（每条都能被 CI 拦住）

| # | 不变式 | 校验方式 |
|---|---|---|
| **I1** | **壳不解析指标内容**：`internal/proto` 里**只允许出现 4 个 json tag**（`id`/`ok`/`proto`/`metrics`）；`internal/proto` 之外不得出现 `"samples"` / `"labels"` / `"common"` / `"help"` 字面量 | `grep -o 'json:"[a-z_]*"' agent/internal/proto/decode.go \| sort -u` 应恰好 4 行；另一条 grep 应为空 |
| **I2** | **壳不认识插件名**：不出现 `"hard"` / `"nginx"` / `"ssl"` / `"k8s"` / `"k8sController"` / `"trafficSwitching"` 字面量 | 同上 grep，应为空。新增插件绝不可能需要改壳 |
| **I3** | **依赖白名单**：壳只用 stdlib + `gopkg.in/yaml.v3` | `cd agent && go list -m all`，除自身与 `plugproto` 外只应出现 yaml.v3 |
| **I4** | **不落业务状态**：壳只允许写 `agent.pid`、`agent-plugs/`（仅制品解压产物，**不含任何派生配置**） | 测试断言临时目录内的文件清单完全匹配 |
| **I5** | **插件失败不上升**：任一插件的任意失败模式，壳与其它插件继续工作 | 假插件矩阵（§11）全绿 |
| **I6** | **不因插件输入 fatal / panic**：对插件输出零信任，一切异常降级为默认值 + warn-once | 假插件矩阵 + `go test -fuzz` 跑 `DecodeEnvelope` |
| **I7** | **参数钳制生效**：越界值一律回落，不进入调度器 | 2.4 表的逐行单测 |
| **I8** | **领域无关性**：新增壳的测试用例不需要构造真实监控数据 | 评审清单（§12）人工把关 |

**I2 的唯一例外：`heart`。** 心跳留在壳内（不下沉为插件，否则"插件被停用"会被误判为主机离线），所以壳必须以 `source = "heart"` 上报它。准确的 grep 规则是：

```
壳内不得出现 "hard" / "nginx" / "ssl" / "k8s" / "k8sController" / "trafficSwitching" 字面量
"heart" 允许，但只允许出现在 internal/heartbeat/ 内
```

I1 与 I2 看起来像洁癖，实际是这套架构能不能兑现承诺的**唯一客观证据**：只要这两条 grep 是空的，"插件演化打到壳"在结构上就不可能发生，而不是靠人记得别写错。I1 里那条"恰好 4 个 json tag"尤其重要——**任何人往 Envelope 里加第 5 个字段，CI 当场就会红**，不必等评审时有人发现。

## 五、失败域隔离矩阵

壳里有三个层次的失败，必须各自**就地终止**，不允许跨层传播：

| 层 | 失败情形 | 处理 | 绝不发生 |
|---|---|---|---|
| **插件级** | 进程退出 / collect 超时 / stdout 混入非 JSON / 输出超限 / proto 不匹配 | 该插件计失败 + 指数退避重启（1s→60s，存活 >1min 重置）；连续 5 次且从未健康则标记 `failed` 停止重启，仅保留状态展示 | 影响其它插件；打爆日志与 CPU |
| **轮次级** | 单轮上报失败（网络、超时、413） | 重试 N 次 → 丢弃本轮 + 计数；下一轮照常 | 数据积压到内存爆掉；阻塞调度 |
| **进程级** | 壳内某 goroutine panic | **每轮 collect、上报 goroutine 一律 `defer recover()`** + 记录堆栈 + 继续下一轮 | panic 冒到主 goroutine 让壳整体退出（那是可用性事故） |

只有一种情况允许壳退出：**启动自检失败**（§8）或**收到 SIGTERM**。其余一切异常都要在更小的作用域里被吃掉。

> 这一条是"降低壳出错风险"最实际的一招。壳的代码量再小也可能有 bug，但只要**每个失败域都有 `recover` 兜底**，"某个插件相关代码里的一个小 bug"最多损失一轮数据，而不是整台机器的采集全停。

## 六、壳的安全底线（三条，全在 pluginmgr 里）

壳是唯一以 agent 身份执行外部文件的组件，这三条必须在 v1 就写对，事后补等于重写下载器：

1. **路径穿越防护**：解压制品包时拒绝任何 `..`、绝对路径、符号链接条目。制品包来自 service，但壳不能假设 service 永远是可信且无 bug 的（`tar` 里的 `../../etc/...` 是经典提权手法）。
2. **大小上限**：下载制品 ≤ 64 MiB，解压后总量 ≤ 256 MiB。超限即中止并删除临时文件。
3. **只执行明确路径**：`exec` 的路径恒为 `agent-plugs/<name>/<name>`，**不查 PATH、不 glob、不执行目录下其它文件**。插件名必须命中"配置里声明的插件名"，不接受任何外部来源的名字。

## 七、壳自身状态：不落盘

除了 `agent-plugs/`（制品解压产物）与 `agent.pid`，壳**不保存任何运行状态**：没有队列文件、没有"上次成功时间"、没有"待重试列表"、没有"已装版本清单"，**连配置缓存也没有**——2026-09-18 起不再生成 `effective.yaml`（§9.1）。

理由不是洁癖，是**重启即自愈**：壳崩了重启，一切从零重建，不存在"残留状态导致诡异行为"这一类最难排查的 bug。**事实来源已经存在且唯一**——插件是否启用由 `config.yaml` 决定，已装版本看 `agent-plugs/<name>/manifest.yaml`，采集周期同样来自这两处（§2.5）。壳重启后从这里重建即可。

> 代价是断网期间的数据真的丢了——但这是 gauge、周期 15s，丢一轮不影响趋势，主文档 §2.2 已确认。

## 八、启动自检（当前缺失，必须补）

现在 agent 起来后只会打日志，配置错了也照样"活着"。改为启动时做 6 项检查，任一不过**直接退出**（退出码非 0，交给 systemd `Restart=always` 或容器重启策略接管）：

1. 配置可解析、必填项齐全（上报地址、密钥、project）
2. 密钥长度合法（16 / 24 / 32 字节）
3. 插件目录可写（不能写 = 无法下载插件，早死早超生）
4. **每个已启用插件的 `manifest.yaml` 可解析，且 `default_interval` / `default_timeout`（连同 config 覆盖值）通过 §2.4 钳制表**——这是周期从"插件自报"搬到静态声明后新增的检查项
5. 能连通 service（`/healthz` 可访问）——**已定（2026-09-20）：默认要求连通；`allow_offline: true` 时退化为"仅告警并继续"，并在状态端点与心跳里标注 `offline_mode`**（用于内网纯离线机器）
6. 已启用插件的制品是否已在本地（不在则尝试下载一次，失败即退出）

**为什么必须退出而不是"降级运行"**：一个"进程活着但半死"的 agent 是最难排查的状态——systemd 认为它健康、监控面板认为它离线、日志里全是零散告警。**宁可反复重启（日志明确、退避可见），也不要半死不活。**

同理，**热加载时的非法配置只告警并保留旧值**（现有 `LoadConfig` 已是此行为）：让"改错配置"退化为"5 秒后还是旧配置在跑"，而不是"整机采集停摆"。这两条一进一出，覆盖了配置面全部的出错可能。

## 九、配置 schema 也是壳的一部分

`config.yaml` 的键名等价于壳的接口——**改它就要改壳**，所以它同样冻结。

```yaml
project: jiexianghua            # 冻结：上报报文的 project 就是它，空则拒绝启动
metrics_url: https://.../metrics_data   # 冻结
encrypted: <32 字节>            # 冻结
ip_pass: [...]                  # 冻结
trust_proxy: false              # 冻结
auto_update: false              # 冻结：只决定插件制品是否自动更新，壳自身不更新（壳设计 §十一）
allow_offline: false            # 冻结：true = 启动自检"能连通 service"失败时仅告警并继续（§8 第 5 项）
plugins:                        # 容器键冻结
  hard:
    enable: true                # 壳认识的键，只有这三个
    interval: 15s               # 覆盖 manifest 的 default_interval（可省略）
    timeout: 45s                # 覆盖 manifest 的 default_timeout（可省略）
    # 下面是插件自己的参数：壳不看、不校验，插件自己来读这一子树（§9.1）
```

`project` 是这份 schema 里**唯一会进入上报报文的业务项**——其余键要么壳自己用（`metrics_url` / `encrypted` / `ip_pass` / `trust_proxy` / `auto_update`——这个只决定插件制品是否自动更新；`allow_offline`——只影响启动自检是否因连不上 service 而退出），要么留给插件自己读（§9.1）。壳读出 `project` 写进 payload 的 `project` 字段（分工表见 §2.5），**插件完全不参与**。

> 现有实现的键名是 `agent.project` / `agent.metrics_url` / `metrics.<name>.enable`，本版拍平为 `project` / `metrics_url` / `plugins.<name>`。老 agent 是一次性替换的，所以按新 schema 重写 `config.yaml` 即可，不做兼容层。

关键设计：**`plugins.<name>` 下壳只认 `enable` / `interval` / `timeout` 三个键，其余全部留给插件。** 插件想加什么参数都行，壳不需要知道——这样"插件新增配置项"永远不会打到壳，也不会因为壳不认识而报错。

### 9.1 插件读的是同一份文件（2026-09-18 改判）

**`config.yaml` 只有一份，壳和插件都读它**：壳读 `enable` / `interval` / `timeout`，插件读同一棵 `plugins.<name>` 子树里的其余键（壳通过 `MONITOR_CONFIG` 给它路径）。**壳不再合并出 `effective.yaml`**——合并（`plugins.<name>` 覆盖制品的 `default.yaml`）由 SDK 在插件进程内完成（插件设计 §4.2 ⑤）。

| | 之前 | 现在 |
|---|---|---|
| 合并 | 壳合并 → 写 `effective.yaml` | **SDK 在插件内合并**（产物只在内存里） |
| 壳读 | 三个键 + 全量透传落盘 | 只读三个键，其余不碰 |
| 插件读 | `effective.yaml`（派生文件） | `config.yaml` 的 `plugins.<name>` + 自己的 `default.yaml` |
| 改配置生效 | config → 壳 5s 缓存 → 重写 effective → 插件 mtime 缓存 | **config → 插件 mtime 缓存（少一跳）** |

四条理由，按重要性排：

1. **少一个文件就少一个"该信谁"**。`effective.yaml` 是派生文件，一旦它和 `config.yaml` 不一致（壳写失败、版本对不上、有人手改了它），现场没人能立刻判断哪份是准的。而排障时最自然的动作恰恰是"改那个文件试试"——然后下一次被壳覆写，变成经典的"改了没生效"。
2. **壳的不落盘承诺变干净**。I4 原本要给 `effective.yaml` 开一个例外（"配置缓存不算状态"），现在例外消失：`agent-plugs/` 下只剩制品解压产物。而原来的实现是把派生文件写进**会被升级覆盖的制品目录**，本身就是两类东西混放。
3. **热加载少一跳**。之前是"改 config → 壳重写 → 插件读"，任何一环卡住都表现为"配置改了没生效"；现在插件直接看 `config.yaml` 的 mtime。
4. **脱壳调试更真**。以前要手写一份"合并后形态"的 `effective.yaml`（写错了反而不自知）；现在直接指一份真实的 `config.yaml` 就能跑（`MONITOR_CONFIG=... ./hard --selftest`）。

**代价与取舍（必须知道）**：

- **`plugins.<name>` 里除三个壳保留键之外的所有键，从此是壳与插件共享的契约。** 改 `plugins` 这个容器键名、或改那三个保留键的名字，等于同时改壳和 SDK——已写进评审清单（§12 第 1 条）。壳仍然**只依赖这一个位置**，不依赖任何顶层键，所以以后顶层加键（比如加 `log_level`）不影响插件。
- **`config.yaml` 里含 `encrypted`（AES 密钥），而现在插件被设计为要读这份文件。** 取舍记录：插件与壳本来就同机同用户运行、文件权限相同，**旧方案拦不住插件去读它，只是没要求它读**——净变化是**架构意图**而非实际访问能力。当前接受（插件全部自研）。**SDK 层面收敛**：`sdk.Config()` 只暴露 `plugins.<name>` 子树，签名里拿不到顶层键——这不是安全边界，但是降低误用的默认姿势。
  > **触发条件**：一旦出现第三方插件、要给插件做最小权限隔离、或 `agent-plugs/` 被放到权限更宽松的位置 → 把密钥移出 `config.yaml`（`MONITOR_ENCRYPTED` 环境变量优先，或 `agent/secret.key`，0600）。**插件侧的路径与键位完全不变，一个插件都不用改**——这条后路是刻意留的。
- 附带的正面效果：**要"看生效值"不必再落一份文件**。壳契约 §14 那条"插件健康度由壳推导成指标"的思路同样适用——需要展示合并结果时，由 `statusapi` 在内存里算一遍即可（只读端点，I4 不受影响）。

### 9.2 壳自己那部分：周期与阈值的三级取值

`interval` / `timeout` 的**三级取值**（与 §2.3 的字段降级是同一套逻辑，只是来源换了）：

```
config.yaml 的 plugins.<name>.interval   ← 运维覆盖，优先
  → manifest.yaml 的 default_interval    ← 插件作者给的推荐值
    → 30s                                ← 最终兜底
```

`timeout` 同理，缺省值为 `2.5 × 最终 interval`（保证恒 `> interval`）。**三级取值算完后统一过 §2.4 的钳制表**，再交给 `scheduler`。

这与 §2 的收窄策略是同一个思路：**壳只认自己那一点，其余一律不透明。**

## 十一、契约测试套件：假插件矩阵

"插件变更不影响壳"要有**可执行的证明**，而不是文档里的一句话。做法是在 `agent/internal/pluginmgr/testdata/` 放一组极简假插件（每个 20~30 行 Go，只 `os.Exit` 和 `fmt.Println`），CI 里当作真实子进程跑：

| 假插件 | 行为 | 断言 |
|---|---|---|
| `okplug` | 正常应答，`metrics` 里塞**故意带未知字段和深层嵌套**的 JSON | 字节级原样透传（证明壳没重排、没解码；I1） |
| `slowplug` | 应答时间 > timeout | 被 kill + 计一次失败 + 退避重启 |
| `badjson` | stdout 混入一行日志 | 判该插件失败 + 明确告警 + **其它插件照常** |
| `nodata` | 响应只有 `{"id":1,"ok":true}`，没有 `metrics` | 本轮无数据、**不算失败**、不崩（§2.3） |
| `wtfvalues` | `id` 报字符串、`ok` 报 `null`、`proto` 报 `"abc"` | 按 §2.2 宽容解析，不崩 |
| `unknownfield` | 响应塞 1000 个未知字段 + 10 层嵌套 | 忽略，不崩、不慢 |
| `hugeplug` | 单行输出 100 MiB | 按上限 kill + 计失败，**壳内存不爆** |
| `zeroplug` | 启动后立刻退出 | 退避重启；连崩 5 次标记 `failed` 并停止重启 |
| `proto2` | 自报 `proto: 2` | 显式拒绝启动 + 报"需升级 agent"，不静默降级 |
| `exitcode` | 应答后以 exit 3 退出 | 按退出处理，不读后面可能残留的输出 |

这套矩阵的价值在于：**它一个监控概念都不涉及**。只要它能全绿，壳就是领域无关的（§0 的检验标准），插件的任何采集逻辑变化都不可能动摇它。

另外给 `DecodeEnvelope` 加 fuzz 测试（`go test -fuzz`，输入为任意字节流），这是 I6 的机器化保证——**"插件给我什么垃圾，壳都不许 panic"** 靠人工是保证不了的。

## 十二、评审清单（进 PR 模板）

任何改动 `agent/` 的 PR，逐条回答：

1. **是否动了壳与插件共享的约定？** 两类：
   - **(a) 信封字段**：是否让壳读到了新的插件字段？→ 若是，这属于三端协议变更，要同步改插件 SDK 与 service 文档。**先过 §2.5 那道门**：这个字段能不能像 `name`/`version`/`interval`/`timeout` 一样，从 `config.yaml` 或 `manifest.yaml` 拿到？能，就不该进信封。
   - **(b) 配置位置（2026-09-18 新增）**：是否改了容器键 `plugins`、壳保留键 `enable`/`interval`/`timeout`，或插件取配置的路径来源（`MONITOR_CONFIG`）？→ 改任一项都要同步改 SDK 与插件设计文档（§9.1、§5.2）。**但给 `config.yaml` 顶层加键不算**——插件不依赖任何顶层键。
   - 若确认必须进：字段**可选且可忽略**（旧壳忽略它、新壳遇旧插件走缺省）→ **不 bump `proto`**，但必须同时发布 SDK。
   - 字段**必填、语义改变、或删除已有字段** → **必须 bump `proto`**，且壳显式拒绝自己不认识的高版本。
   - 无论哪种，I1 那条"`internal/proto` 恰好 4 个 json tag"都要同步更新——**这条 lint 会拦住你，不要绕过它**。
2. **是否新增了第三方依赖？** → 若是，说明为什么 stdlib 不行（I3）。
3. **是否让壳做了业务计算或解析指标内容？**（I1）
4. **是否让壳知道了某个具体插件名？**（I2）
5. **是否新增了落盘状态？**（I4）
6. **新代码的失败是否会传播到其它插件或壳本身？**（I5，需 `recover` 或隔离）
7. **新增的测试用例，是否需要构造真实监控数据？**（I8，若是则设计有问题）
8. **内核行数预算是否仍满足？**（§10）

八条里前七条都是"否"，就说明这次改动没有扩大壳的出错面。

## 十四、延伸：插件健康度如果将来要出网（现在不做，留档）

用户当前的决策是**插件诊断信息完全不出网**，也**不在信封里**（§2.5）。这一节只记录"如果将来要在 Grafana 上看插件健康度"该怎么落，避免那时候重新推导一遍。

**做法：由壳推导，而不是让插件上报。** 壳已经掌握全部事实——进程状态、最近一次成功时间、失败与跳过计数、已装版本。把这些**推导成一条独立指标**：

```
monitor_plugin_health{project, host, plugin, version, state} = 1
```

- `state` 是**枚举值**（`running` / `backoff` / `failed` / `disabled`），不是自由文本；
- 由壳主动上报，走现有的 `/metrics_data` 声明式链路；
- **service 不需要新增非指标数据路径**，Grafana 能画、Alertmanager 能告警。

**为什么不能直接把一句诊断文字搬上去**（三条硬约束，这才是本节的价值）：

| 约束 | 原因 |
|---|---|
| 必须**枚举化** | 自由文本会成为高基数标签：1500 台 × 4 插件 × 每台错误字符串都不同 → 序列无上限 |
| 必须**周期性重发** | service 是指标源、Prometheus 是拉模型，没有"事件"概念。一个只在异常时才有意义的状态被迫每 15 秒重发一次，且**无法区分"刚刚恢复"和"十分钟前就恢复了"** |
| 会逼 service **新增一条非指标数据路径** | 现状 service 的一切都是"指标"，混入非指标数据会污染动态注册表模型（服务端设计 §5） |

这件事现在不做，且**不影响任何既有设计**：它是壳侧的一个外围模块（`statusapi` 的数据已经在内存里），随时可加，不挡任何东西。
