## 一、三层架构与职责切分

```
┌─ 插件层 (plugs) ──────────┐      ┌─ agent 壳 ─────────────────┐      ┌─ service ────────────┐
│  独立进程，一采集器一插件   │      │  常驻，唯一需要守护的进程    │      │  Docker 单实例        │
│                           │      │                            │      │                      │
│  hard     nginx    ssl    │ stdio│  配置合并 / 插件监管         │ HTTPS│  解密 解压 校验       │
│  k8s      ...             │─────▶│  调度 / 加解密 / 上报        │─────▶│  动态注册 / 注销      │
│                           │ JSON │  心跳 / 只读状态端点         │      │  插件制品仓库         │
│  只输出明文指标，不碰网络   │      │  不解析指标内容（仅 8 字段）  │      │  Prometheus 拉 /metrics│
└───────────────────────────┘      └────────────────────────────┘      └──────────────────────┘
      不需要改 agent 就能新增         内核 ≤1400 行、契约冻结            制品由 agent 主动拉取（§5）
```

三层各自只做一件事：

- **插件**：采集，输出明文指标。不碰加密、不碰网络、不认识 service。（例外见 §9.4：无 agent 的上报方直连 service）
- **agent 壳**：编排与传输。把插件当黑盒子进程管起来，把结果压缩加密发出去。
- **service**：接收与暴露。解密后落到 Prometheus Registry，插件制品由它分发（**agent 主动拉取，service 不反向连接 agent**）。

**为什么加解密只在壳内做一次**：如果每个插件各自实现一遍 AES-GCM + gzip + HTTP，你会得到 N 份各不相同的重试、超时、密钥处理逻辑，将来换协议要改 N 个地方。收敛到壳里，插件作者只需要会打印 JSON。

## 二、Agent 职责边界（冻结清单）

你说"agent 可能终生不会做修改，所以一开始就要全部计划好"。做法是把职责**列成白名单**，白名单之外一律不加。

### 2.1 Agent 只做这 7 件事

1. **读配置**：读 `config.yaml`，自己取 `enable` / `interval` / `timeout` 三个键（过钳制表）；`plugins.<name>` 的其余部分**原样留给插件**——壳不合并、不落盘（壳契约 §9）
2. **插件生命周期**：按本机 `config.yaml` 判断启用 → 懒下载 → 校验 → 启动 / 停止 / 重启 → 版本替换
3. **调度**：按 `manifest.yaml` 声明、`config.yaml` 可覆盖的 `interval` 派发 `collect`，每插件一个 goroutine，上一轮没结束就跳过本轮
4. **组装上报报文**：`project` 读 `config.yaml`、`source` = 插件目录名、`timestamp` = 采集时刻——**三项都不问插件**；同时**不向插件注入任何业务参数**，插件需要什么自己取（见壳契约 §2.5 分工表）
5. **传输**：聚合 → JSON → gzip → AES-GCM → POST `/metrics_data`，带重试与背压
6. **心跳**：`heart` 采集留在壳内，**不下沉为插件**（否则"插件被停用"会被误判为主机离线）
7. **只读状态端点**：本机 HTTP 展示已装/已启插件、各插件版本与最近一次采集时间与状态

### 2.2 明确不做（防止日后膨胀）

| 不做 | 原因 |
|---|---|
| 插件间依赖 | 见 §7，组合复杂度爆炸，用"单插件多组指标"替代 |
| 远程配置下发 | 插件启用由本机 `config.yaml` 决定，见 §6.0 |
| 指标聚合 / 计算 | 插件算完再给，壳不做业务逻辑，否则壳会随业务演化 |
| 数据落盘重放 | 300~1500 台量级不需要；断网期间的 gauge 数据丢一轮不影响趋势 |
| 查询 / 告警 / 面板 | 继续交给 Prometheus + Grafana 生态 |
| 插件沙箱 | 依赖 Linux namespace/seccomp 会使插件跨平台受限；用"源码可信 + 独立进程崩溃隔离"代替 |
| 在壳里实现采集逻辑 | 全部下沉到插件，壳不做业务计算，见 §2.3 |

> 白名单之外**没有例外**，壳里不需要任何"远程指令通道"：插件启用由本机 `config.yaml` 决定（§6.0），需要批量调整时用配置管理工具推文件，仍然不需要 agent 配合。

### 2.3 壳会出问题，所以先让它"没什么可出错的"

你担心的"壳出问题"是对的：壳是唯一不可就地替换的组件（插件坏了换插件，壳坏了要动二进制）。控制风险分两步——**先降低出错概率，再兜住出错后果**。

降低概率靠"把代码量压到最小"，四条：

1. **壳不解析插件数据。** 插件给的已经是完整的声明式 JSON，壳用 `json.RawMessage` **原样透传**，绝不反序列化成结构体。这一条的分量比看起来大：它意味着"上游数据格式怎么变"永远打不到壳——新增字段、改标签、加指标组，壳都不知道也不关心。
2. **壳不做任何业务计算。** 采集、解析（procfs / df / ss / kubectl）、单位换算、差值计算全在插件里。壳只做五件事：配置解析、进程管理、调度、加解密、HTTP。
3. **壳的第三方依赖趋近于零。** 目标：标准库 + `gopkg.in/yaml.v3`（读配置）。**不要在 agent 侧引入 koanf / viper / chi**——"两层配置合并"就是"读两个 map、后者覆盖前者"，手写约 30 行；引入配置框架反而让壳多背一个可能出破坏性变更的依赖。选型表（§11）已按此修正。
4. **壳的每个环节都有测试。** 配置合并、协议编解码、加密、调度、进程监管、崩溃重启全部单测；进程监管用真实的假插件二进制做集成测试，而不是 mock。

可校验指标：**壳的内核控制在 1140 行以内、总量 1580 行以内**（不含注释与测试）。数字的意义不在精确，而在涨到 2 倍时你能立刻察觉有东西溜进来了。

> **本节已细化成独立文档 `docs/壳契约-v1.md`**，把"没什么可出错"落成可 grep、可 CI、可测试的硬约定：壳对插件输出的全部认知只有 **4 个字段**、所有协议知识锁在 **1 个文件**（`internal/proto/`，约 110 行）、**8 条不变式**、**10 个假插件的契约测试矩阵**。要动的不是原则，而是那份契约。

### 2.4 壳不做自更新：更新交给 systemd 与容器编排（2026-09-18 改判）

**本节推翻上一版结论。** 上一版主张"复用现有 `CheckVersion.go` 的自更新能力、默认关闭"，理由是"壳出问题更新很麻烦"。这个理由不成立——解药不在壳里，**在部署形态里**：

- **物理机**：systemd 管进程（`Restart=always`），滚壳 = 换二进制 + `systemctl restart`
- **容器**：编排器管进程，滚壳 = 换镜像 tag，由滚动更新策略逐节点推进

**并且自更新在容器里是个真坑**：现有实现用 `syscall.Exec` 原地替换，**PID 不变、容器不重建**——结果是容器内跑的二进制与镜像里的版本发生漂移，下次容器重建就悄悄回退了。一个"看起来成功、实际是假象"的更新通道，比没有更危险。

删掉它的收益：

| 项 | 变化 |
|---|---|
| `Middleware/CheckVersion.go` | 393 行整段删除（含 `.new` / `.bak` / `restart.flag` / 连崩回滚） |
| 壳的故障面 | 少掉"替换自己崩在半路"这一整类最难排查的状态 |
| 总量预算 | 1830 → **1580** |

**代价要认**：壳里出现必须修的缺陷时，1000+ 台要动二进制。但这条在容器场景下是"改一个镜像 tag"，在物理机场景下是"换二进制 + restart"，**属于成熟工具链的常规操作**，不是找不到解药的问题。缓解手段仍是那三条（§6.8）：把易变的东西放进插件、agent 必须被 systemd / 编排器托管、`agent_version` 在 service 侧可见以便知道工作量。

**`auto_update` 这个配置键保留，但语义收窄为"是否自动更新插件制品"**——壳自身不再有任何更新行为。

### 2.5 关于"采集逻辑会变"：这正是插件化要解决的问题

你说"最多采集逻辑会有所变化改动"。这类改动 100% 应该落在插件里，壳完全不动。前提是协议字段被冻结，边界见 §3.5。

## 三、插件协议 v1（冻结）

### 3.1 传输

纯 stdio，**按行 JSON**。agent 写一行到插件 stdin，插件写一行到 stdout，必须以 `\n` 结尾并 flush。

**硬规则：stdout 只走协议，日志一律走 stderr。** agent 把 stderr 逐行转发到自己日志并加 `[plugs/<name>]` 前缀。这条必须由 SDK 强制（SDK 在 Go 里把 `log` 默认输出重定向到 stderr 并接管 stdout），否则插件作者一行 `fmt.Println` 就会污染协议流。agent 侧还要做自检：收到非 JSON 行直接判定该插件失败并告警，而不是静默跳过。

### 3.2 三段命令

```jsonc
// agent → 插件：握手（启动后第一条）。只带协议版本
{"id":1,"cmd":"hello","proto":1}

// 插件 → agent：只需报协议版本。名字、版本、周期都在制品自带的 manifest.yaml，壳自己读
{"id":1,"ok":true,"proto":1}

// agent → 插件：采集（每轮一次）。只有命令本身，不注入任何参数
{"id":2,"cmd":"collect"}

// 插件 → agent：明文指标，格式复用服务端声明式契约（见 3.3）
{"id":2,"ok":true,"metrics":[ /* DeclaredMetric[] */ ]}

// agent → 插件：优雅退出
{"id":3,"cmd":"shutdown"}
{"id":3,"ok":true}
```

**响应里只有 4 个字段**：3 个是传输语义（`id` / `ok` / `proto`），**只有 `metrics` 承载数据**。插件名、版本、采集周期、诊断信息**一律不在协议里**（见 3.6）。

要点：

- `hello` **只用于握手与协议协商**，不带自描述——省下的那一次往返本来也没换来什么，而自描述的每一项壳都能从配置与制品里读到。插件侧仍可用 `./hard --selftest` 单独调试。
- **不注入任何参数**：`project` 由壳从 `config.yaml` 读出来写进上报报文，**插件完全不知道它**；主机名等本机事实插件自己取（`sdk.Hostname()`）。壳只注入"壳算出来才有的值"（配置路径、周期、阈值）——分工表与理由见 `壳契约-v1.md §2.5`。
- `proto` 版本不匹配（插件 `proto > 1`）→ agent 拒绝启动该插件并明确告知"需升级 agent"，这就是"agent 终生不改"的代价边界，必须显式报错而不是降级运行。
- **每轮 collect 有硬超时**：取 `manifest.yaml` 的 `default_timeout`（`config.yaml` 可覆盖，下限 `2 × interval`）。超时则 kill 插件进程并按"崩溃"处理重启。没有这一条，一个卡死的插件会挂掉整个采集循环。
- `id` 用于匹配请求响应，允许插件串行处理；本协议不支持并发（一个插件进程同时只处理一个 collect）。

### 3.3 插件输出的指标结构

直接复用服务端声明式契约（现有 `server/Modles/declarative.go` 已定义，将上移为共享模块）：

```json
{
  "name": "hard_cpu_percent",
  "help": "CPU 使用率百分比",
  "type": "gauge",
  "labels": ["hostName", "cpu_model", "os_version", "kernel_version"],
  "common": {"cpu_model": "Xeon Gold 6248", "os_version": "Rocky 10"},
  "timeout": "45s",
  "samples": [{"labels": {"hostName": "web-01"}, "value": 12.3}]
}
```

**这个结构由 SDK 自动生成，插件作者不手写**（2026-09-18 定）：插件里只在采集逻辑旁写一行 `sdk.Gauge("cpu_percent", "CPU 使用率百分比", "cpu")`，SDK 把 `(name, help, labels, timeout)` 收进注册表，采集完序列化成上面的形状。**描述与采集代码同源，不存在第二份定义**——这是"新增指标不需要改服务端"能真正兑现的前提（细节见 `插件设计.md §4.1/§4.2`）。

四条不可动摇的约定：

1. **`project` 不在 labels 里**，由 service 注入。取值来自 agent 的 `config.yaml`（壳读出来写进上报报文），service 再映射中文显示名——**插件既不产出也不参与**（分工表见 `壳契约-v1.md §2.5`）。
2. **标签用 map 不用数组**。数组要求两端顺序严格一致，错位就是静默的数据错乱（主机名被当成内核版本）。
3. **`timeout` 由 SDK 从壳注入的值填**（来源是 `manifest.yaml` 的 `default_timeout`，`config.yaml` 可覆盖）。这条把"阈值必须匹配采集周期"的经验固化进**同一个来源**——周期与阈值同源之后，当前 `k8s/k8sController` 那个"45s 阈值配 60s 周期"的不一致在结构上不会再发生。
4. **描述必须是常量**。`name` / `help` / `labels` 跨轮不能变，`help` 里不得拼时间戳或轮次号。service 靠"描述与上轮是否一致"判断要不要重注册；描述每轮都变会让它反复注销重建 `GaugeVec` 并清空序列（`服务端设计.md §5.6` 有抑制兜底，但那是最后一道闸）。

**为什么不把描述做成一次性的（清单 / 启动注册）**：清单要求把指标名再抄一份，等于把同一份知识写在两个地方；启动注册则依赖 service 记住它，service 一重启描述就丢，插件得做周期性重注册来兜底。每轮重发的代价只是一段高度重复的 JSON（gzip 吃掉大半），换来的是 **service 重启即自愈**，且插件侧完全无状态。**"指标名只增不改"是这套做法的配套纪律**——描述可以变，名字不能变，因为 Grafana 面板引用的是名字。

### 3.4 崩溃与监管

| 情形 | agent 行为 |
|---|---|
| 插件进程退出（非 shutdown） | 指数退避重启：1s → 2s → 4s … 上限 60s；存活超 1 分钟则重置退避 |
| 单轮 collect 超时 | kill 进程 + 计一次失败 + 退避重启 |
| 连续失败 ≥ 5 次且从未健康跑过 | 标记 `failed`，**停止自动重启**，只保留状态展示与日志（避免打爆日志和 CPU） |
| 插件写坏 stdout | 判定失败，同"进程退出"处理，并附带明确告警 |
| agent 收到 shutdown 信号 | 向所有插件发 `shutdown`，等 5s，未退出的 SIGTERM，再等 2s 未退出 SIGKILL |

### 3.5 冻结边界（什么变了不用改壳）

这份表就是"壳终生不改"的**准确含义**——不是绝对的，而是"日常演化不触发"：

| 变更 | 要改壳吗 | 说明 |
|---|---|---|
| 插件内的采集逻辑 | 不用 | 插件自己的事 |
| 新增一个插件 | 不用 | 壳按 `config.yaml` 的条目 + 制品目录工作，不维护插件清单 |
| 插件新增 / 删除指标、改标签 | 不用 | 壳用 `json.RawMessage` 透传，不解析（§2.3） |
| 插件改用另一种语言实现 | 不用 | 只要遵守 stdio 按行 JSON |
| 改 `manifest.yaml` 的 `version` / `default_interval` / `default_timeout` | 不用 | 重新打包发布即可；壳只读这几个键，不认它们的语义 |
| 改 `config.yaml` 里某插件的 `interval` / `timeout` | 不用 | 下一轮调度生效，不重启进程 |
| 新增 `hello` / `collect` / `shutdown` 之外的命令 | **要** | 命令集是冻结的；确实需要时用 `proto` 版本号协商 |
| 改这三个命令的顶层字段名 | **要** | 字段名即契约 |
| 改指标声明的字段名（`name`/`labels`/`samples`/`common`/`timeout`） | **要** | 同上 |

真要加新命令时，用 `proto` 版本号协商，并且壳必须**显式拒绝自己不认识的高版本**（§3.2），而不是静默降级——静默降级会让插件以为功能生效了，是最坏的结果。

### 3.6 边界判断：插件状态既不新开通道，也不进协议

"给 agent 加一个接收接口"（典型方案是壳监听 `127.0.0.1` 供插件 POST）**已否决**，完整理由记在 `壳契约-v1.md` §一与§七。两条要点：

1. 它会让壳多出**第 5 类输入**，而这类输入**本机上任意进程都能伪造**（要么不认证，要么壳自造一套认证）；再叠上端口管理、端口冲突、body 限制、超时，约 150 行**全部落在内核冻结区**。
2. 插件与壳之间**本来就有一根私有双向管道**——`stdin`/`stdout` 是最便宜且天然隔离的通道，再开一个网络接口去传同样的信息是净负债。

**最终结论是连协议字段也不加**（2026-09-18 定）：插件诊断信息**整条线砍掉**。它的终点只有本机 `statusapi`（不上报、不落盘），而壳已经有一份同源信息——插件的 `stderr` 由壳逐行加前缀转发进日志，状态端点里也展示壳记录的 `last_error`。为此多背一个协议字段、一条长度钳制、一份 SDK 状态缓冲区，投入产出不成立。

这个否决不损失排障能力，只是把信息放回了正确的去处：

| 你想表达 | 正确做法 |
|---|---|
| 一个**数值事实**（磁盘快满、证书剩余天数） | 做成指标——Grafana 能画、Alertmanager 能告警 |
| **为什么这轮没数据**（依赖命令不存在、kubeconfig 读不到） | 写 `stderr`，壳带插件名前缀转发 |
| 跨轮观察的状态 | 做成指标（gauge 天然表达"当前值"） |

将来若真想在 Grafana 上看插件健康度，正确落法是**壳把自己的观测结果推导成一条独立指标**（`monitor_plugin_health{project,host,plugin,version,state}`），枚举化发生在壳侧，而不是把插件的自由文本搬上去当标签（代价与做法见 `壳契约-v1.md` §十四）。

## 四、`agent-plugs` 目录与两级配置

### 4.1 仓库内（源码）

```
agent-plugs/
├── go.mod                     # module: agent-plugs
├── sdk/                       # 插件 SDK：协议收发、日志重定向、配置读取
│   ├── plugin.go
│   └── README.md              # 面向插件作者（可以是别的语言）
├── hard/                      # 一个采集器一个目录，一一对应
│   ├── main.go
│   └── default.yaml
├── nginx/
├── ssl/
├── k8s/                       # 原 k8s + k8sController 合并（共享 clientset）
│   ├── main.go
│   └── default.yaml
└── build.sh                   # 交叉编译全部插件到 dist/
```

### 4.2 部署机上（运行期，由 agent 生成）

```
<agent 二进制目录>/
├── agent                       # 壳
├── config.yaml                 # 用户唯一需要手工维护的文件
└── agent-plugs/                # agent 全权管理，用户不要手改
    ├── hard/
    │   ├── hard                # 二进制（从 service 下载）
    │   ├── manifest.yaml       # 名称/版本/平台/入口（下载时解压得到）
    │   └── default.yaml        # 插件作者给的默认值（随版本更新而覆盖；用户不要手改）
    └── ssl/
```

**没有 `.state/` 目录——壳不保存任何业务状态。** 这是壳契约里的一条硬约束（`docs/壳契约-v1.md` §7），理由是**重启即自愈**：壳崩了重启，一切从零重建，不存在"残留状态导致诡异行为"这类最难排查的 bug。

那三份原本要落盘的状态，现在都有了更好的来源：

| 原本要落盘 | 现在从哪来 | 好处 |
|---|---|---|
| `installed.json`（已装版本） | 直接读 `agent-plugs/<name>/manifest.yaml` | 目录本身就是事实来源，不可能与文件不一致 |
| `desired.json`（期望状态） | **不需要**——已砍掉远程管理（§6.0），启用状态就在 `config.yaml` 里 | 少一份可能过期的缓存 |
| `desired.version` | 同上 | — |

**壳不生成任何运行时配置文件**（2026-09-18 改判）。曾经由壳合并写出的 `effective.yaml` 已取消：合并改在插件 SDK 里做，壳只把 `config.yaml` 的路径交给插件（§4.3）。于是 `agent-plugs/` 下只剩制品解压出来的东西，不会出现"运行时派生文件与制品内容混放"的情况。

### 4.3 两级配置的优先级（合并发生在插件侧）

```
agent config.yaml 的 plugins.<name>.*      （用户覆盖，最高）
        ↓ 覆盖
agent-plugs/<name>/default.yaml            （插件默认值，升级时随包覆盖）
        ↓ 覆盖
插件代码里 Conf 调用点传的 def              （最低）
```

规则：

- **升级插件会覆盖 `default.yaml`**，所以用户绝不能改它——要改就写在 `config.yaml` 里。这是"两层"方案能安全工作的前提，必须在 README 里用醒目方式说明。
- **`config.yaml` 只有一份，agent 与插件都读它**。agent 读 `plugins.<name>` 下的 `enable` / `interval` / `timeout`（壳保留键）；插件读同一棵子树里的其余键，并与自己的 `default.yaml` 做浅合并。**合并逻辑在插件 SDK 里**（约 30 行），**agent 不做合并、也不生成任何派生配置文件**（2026-09-18 取消 `effective.yaml`，理由见 `壳契约-v1.md §9.1`）。
- **公共参数不写在插件配置里**，由 agent 注入——但**只注入"agent 算出来才有的值"**：`MONITOR_CONFIG`（`config.yaml` 绝对路径）、`MONITOR_PLUGIN_DIR`、`MONITOR_PLUGIN_INTERVAL`、`MONITOR_PLUGIN_TIMEOUT`（生效的周期与阈值）。
  - `collect` 请求**不带任何参数**：`project` 由 agent 从 `config.yaml` 读出后写进上报报文，**插件不知道也不需要它**；主机名等本机事实插件自己取（`sdk.Hostname()`）。分工表与理由见 `壳契约-v1.md §2.5`。
- 配置变更**不重启插件**：插件每轮 collect 都读一次 `config.yaml`（SDK 带 mtime 缓存），改动下一轮自然生效，**中间不需要 agent 做任何事**。只有 `enable` 变化或插件版本变化才动进程。
  - 生效路径只有一跳：`config.yaml` → 插件。以前是"agent 先合并出 `effective.yaml`，插件再读"，多一个可能卡住的环节。

### 4.4 `config.yaml` 长这样

```yaml
project: "jiexianghua"            # 必填；上报报文的 project 就是它，插件不知道它
metrics_url: "http://monitor.example.com:8080"
agent_id: ""                      # 留空则用 hostname + 机器码派生，稳定且唯一
auto_update: false                # 只影响插件更新，agent 自身不更新
allow_offline: false              # true = 启动自检连不上 service 时仅告警并继续（默认 false = 退出）

plugins:                          # 壳与插件共享的容器键（冻结）
  hard:
    enable: true                  # 壳保留键：只有这三个键壳会读
  nginx:
    enable: true
    interval: 20s                 # 壳保留键：覆盖 manifest 的 default_interval 15s（可选）
    extra_paths: ["/etc/nginx/conf.d"]   # 插件自己读：壳不认识、不校验（与 default.yaml 合并）
  ssl:
    enable: false                 # 未启用 → 不下载、不启动
  k8s:
    enable: false
    config_path: "/etc/kubernetes/admin.conf"

encrypted: ""                     # 16/24/32 字节
```

> 键名以 `壳契约-v1.md §9` 的**冻结 schema** 为准。本版把现有的 `agent.project` / `agent.metrics_url` / `metrics.<name>.enable` 拍平为顶层键——老 agent 是一次性替换的，不做兼容层。
>
> **这份文件是 agent 与插件共用的**：`plugins.<name>` 下的 `enable` / `interval` / `timeout` 归 agent，其余键归插件（插件按 `MONITOR_CONFIG` 指到的路径自己读，详见 §4.3）。

**未启用任何插件时，agent 不发起任何插件下载请求**，只做心跳上报——这样主机在 Grafana 上依然是在线状态，只是没有业务指标。

## 五、插件分发（service 侧）

### 5.1 制品布局（镜像内）

```
/app/plugins/
├── index.json                          # 清单，见 5.2
├── hard/1.2.0/linux/amd64/hard.tar.gz
├── hard/1.2.0/linux/arm64/hard.tar.gz
├── nginx/1.1.0/linux/amd64/nginx.tar.gz
└── k8s/2.0.1/linux/amd64/k8s.tar.gz
```

每个 `tar.gz` 内含：`<name>`（二进制）、`default.yaml`、`manifest.yaml`。**打包成一个包而不是三个文件**，这样下载、校验、解压是一次原子操作，不会出现"二进制换了但 default.yaml 没换"的版本错配。

### 5.2 清单接口

```
GET /agent/plugins/index
→ {
    "generated_at": "2026-09-18T10:00:00+08:00",
    "plugins": {
      "hard": {
        "latest": "1.2.0",
        "min_agent_version": "1.0.0",
        "artifacts": {
          "linux/amd64": {"sha256": "3f2a…", "size": 5242880},
          "linux/arm64": {"sha256": "9b1c…", "size": 4980736}
        }
      },
      "k8s": { "latest": "2.0.1", "min_agent_version": "1.1.0", "artifacts": { … } }
    }
  }
```

`min_agent_version` 是必需字段：它让插件作者可以声明"这个版本要求 agent ≥ 1.1"，agent 看到自己版本不够就**拒绝升级并保持旧版本继续采集**，而不是升上去跑不起来。这是"agent 终生不改"下唯一的兼容性阀门。

### 5.3 下载接口与认证

```
GET /agent/plugins/{name}/{version}/{os}/{arch}
X-Agent-Ts:  1758180000
X-Agent-Nonce: 8f3a2c…
X-Agent-Sign: hex(HMAC-SHA256(encrypted, "<path>|<ts>|<nonce>"))
```

service 侧校验：

1. `X-Agent-Ts` 与服务器时间偏差 ≤ 5 分钟（复用现有 `MaxClockSkew` 思路）
2. `nonce` 在时间窗内未重复使用（内存 LRU，窗口 10 分钟）
3. HMAC 签名正确
4. 来源 IP 在 `update.ipass` 白名单内（**双保险**：签名挡伪造，白名单挡扫描）

> 复用 AES 密钥做 HMAC 是安全的：AES-GCM 的密钥是 128/192/256 位随机串，用它做 HMAC-SHA256 的 key 没有密钥复用弱点（两者算法族不同、用途域分离）。但仍建议 service 端**只允许这一套密钥**、不要再派生别的用途。

### 5.4 Agent 侧下载流程

```
service 的 index.json 里 hard=1.2.0，而本地 manifest.yaml 是 1.1.0
   │
   ├─ 1. 查 index，取 linux/arm64 的 sha256（不匹配则报错并保持旧版本）
   ├─ 2. 下载到 agent-plugs/hard/.download/hard.tar.gz.tmp
   ├─ 3. 校验 sha256（不匹配则删文件、重试至多 3 次、保留旧版本继续采集）
   ├─ 4. 解压到 agent-plugs/hard/.download/（校验 tar 内不含 ../ 路径，防目录穿越）
   ├─ 5. 发 shutdown 给旧插件进程，等退出
   ├─ 6. 原子替换：rename 目录到 agent-plugs/hard/（旧的挪到 .old，成功后再删）
   ├─ 7. 启动新进程，发 hello；握手失败 → 回滚到 .old 并重启旧版本
   └─ 8. 清理 .download 临时目录（无状态落盘，版本以 manifest.yaml 为准）
```

第 7 步的回滚很关键：**升级失败必须退得回去**，否则一次坏发布就能让 1000 台机器的某个采集器全部消失。

### 5.5 Docker 打包

```dockerfile
# ---- 构建插件 ----
FROM golang:1.23 AS plugbuilder
WORKDIR /src
COPY agent-plugs/ ./agent-plugs/
COPY pkg/ ./pkg/
RUN cd agent-plugs && CGO_ENABLED=0 GOOS=linux GOARCH=amd64 ./build.sh

# ---- 构建 service ----
FROM golang:1.23 AS svcbuilder
WORKDIR /src
COPY server/ ./server/
COPY pkg/ ./pkg/
RUN cd server && CGO_ENABLED=0 go build -trimpath -ldflags "-s -w" -o /out/monitor-server .

# ---- 运行层 ----
FROM alpine:3.20
RUN apk add --no-cache ca-certificates tzdata
WORKDIR /app
COPY --from=svcbuilder /out/monitor-server /app/monitor-server
COPY server/config /app/config
COPY --from=plugbuilder /src/agent-plugs/dist /app/plugins
EXPOSE 8080
ENTRYPOINT ["/app/monitor-server"]
```

注意两点：`agent-plugs/dist` 里已经是 `<name>/<version>/<os>/<arch>/` 结构，直接对拷；`config/config.yaml` 含真实密钥，生产环境应改用 `MONITOR_ENCRYPTED` 环境变量注入（现有代码已支持）。

### 5.6 制品仓库只服务插件（agent 自己不进制品体系）

壳不做自更新（§2.4），所以**没有"agent 制品"这个概念**：制品仓库的 `index.json` 与下载端点只管插件。现有 `/version`、`/agent/agent`、`/agent/agent.sha256` 三端点标记废弃，等全部 agent 换完后随旧链路删除。

滚壳的顺序仍然存在，但由部署侧保证，而不是靠制品清单：**先在少量机器上换壳 → 验证 `agent_version` 上报正常、指标无缺失 → 再全量**。清单里的 `min_agent_version` 仍有用——它让壳在加载插件时就能拒绝"要求更高壳版本"的插件，从而把"先滚壳、再滚插件"变成一条可执行的检查，而不是靠人记。

## 六、启用 / 停用：本机配置 + 热加载

### 6.0 决策：不做远程管理（2026-09-18 用户确认）

你已明确「不需要远程管理操作，插件启动之后基本终生不会变动」。因此**本节 6.1~6.8 的声明式期望状态方案不实现**，仅作为将来可能的选项留档。

当前采用的方案是三者中最简单的：

1. **插件启用状态由本机 `config.yaml` 的 `plugins.<name>.enable` 决定**，agent 只读本地文件。
2. **`config.yaml` 变更热加载**：现有 `LoadConfig()` 已有 30 秒缓存，把 TTL 降到 5 秒（或加 fsnotify 立刻感知），改完配置 5 秒内生效，**不重启 agent、不重启插件**。
3. **批量调整用配置管理工具**（Ansible / SaltStack / 你自己的脚本）推 `config.yaml`。关键在于——**这条路完全不需要 agent 参与，也不需要在壳里加任何代码**。将来真要"从 service 上一键改所有机器"，答案也是"用 Ansible 推文件"，而不是"给 agent 加一个拉取接口"。

这样壳里**一行远程控制代码都没有**，插件启用这件事的复杂度降为零。代价是改配置要能触达每台机器——但 Ansible 本来就该具备这个能力，否则你也做不了 agent 滚动。

> 对 §6.8 结论表的读法要随之调整：下表中的"改一条规则"在现行方案里等价于"Ansible 推一次 config.yaml"，**仍然是一次操作，不随机器数增长**。

> **下面的 6.1~6.8 保留原文**，作为"如果将来确实需要 service 侧统一管理"时的备选方案。它对 agent 的唯一要求是接口形状（`/agent/desired` + 标签上报 + `current` 回执）必须在 agent v1 定下来；**既然现在决定不做，这个接口也从 agent v1 里删掉**。

### 6.1 两种模型

你提的"在 service 端直接操作所有 agent，启用/停用某台机器上的插件"，有两种实现：

| | 命令式下发（不推荐） | 声明式拉取（推荐） |
|---|---|---|
| 方向 | service → agent 推送指令 | agent → service 定时 GET |
| 连接 | 需要常驻长连接（WebSocket/gRPC stream） | 无，普通短连接 |
| service 状态 | 必须维护每台机器的当前状态表 | 无状态，只管"期望什么" |
| 可靠性 | 指令要幂等、去重、重试、补发、排序 | 天然幂等，拉失败就重拉 |
| 离线机器 | 需要待发队列 | 无需特殊处理，上线自动对齐 |
| 演进成本 | **指令集膨胀 → agent 必须跟着改** | 指令集永远只有一条 GET |

最后一行是决定性的。你选命令式，就等于承认"agent 会不断被改"，与你"终生不改"的前提自相矛盾。

### 6.2 接口契约（agent v1 即冻结）

```
GET /agent/desired?project=jiexianghua&agent_id=web-01&hostname=web-01&current=12
→ {
    "version": 13,
    "plugins": {
      "hard":  {"enable": true,  "version": "1.2.0"},
      "nginx": {"enable": true,  "version": "1.1.0", "config": {"interval": "20s"}},
      "ssl":   {"enable": false}
    }
  }
```

### 6.3 安全红线（三条，缺一不可）

因为这是唯一一条"service 能影响 agent 行为"的通道，必须严格收窄：

1. **只接受白名单内的插件名** —— 必须出现在 `/agent/plugins/index` 里，否则整条期望状态拒绝。
2. **只接受白名单内的配置键** —— 每个插件的可远程覆盖配置项由 `manifest.yaml` 的 `remote_config_keys` 声明，未声明的键一律忽略并告警。
3. **绝不接受命令行、脚本、任意文件路径** —— 这是硬红线。一旦开了这个口子，service 就变成"一条能 RCE 到全部 1000 台机器的通道"，风险等级从"监控系统"跳到"生产事故源头"。

### 6.4 断网兜底

- 拉取失败 / 校验失败 → **沿用 `.state/desired.json` 里最后一份有效期望状态**，采集不中断，记一次告警日志（每 10 分钟最多一条，防刷屏）。
- 期望状态 `version` 单调递增，agent **只应用比 `.state/desired.version` 更大的值**，防止 service 回滚或乱序导致反复启停。
- 首次启动且从未成功拉取过 → 退化为"只用本地 `config.yaml` 的 `plugins` 段"。**这是最简可用形态：service 端第一版完全可以只返回一个静态 JSON 文件，甚至不实现这个接口（404 即退化），管理界面后续再加，agent 无感。** 这一点很重要——它把"管理功能"和"agent 定型"解耦了。

### 6.5 拉取节奏

- 周期 60s，并在启动时加 0~10s 随机延迟，避免 1000 台机器同时打这个接口。
- 这是一个**极小载荷**的请求（响应几百字节），1000 台 × 每分钟 1 次 ≈ 17 QPS，与 `/metrics_data` 完全不在一个量级。

### 6.6 期望状态必须按规则匹配，不能按机器枚举

这是整套设计里**唯一决定运维成本**的地方，做错了比不改还糟。

**反例（绝对不能这么做）**：

```
desired/web-01.json → {"hard": true, "nginx": true}
desired/web-02.json → {"hard": true, "nginx": true}
…  × 1500
```

这样你就真有 1500 份配置要维护，而且比现状更糟——现在你至少只需要 scp 一份 `config.yaml`。

**正解：service 侧维护的是规则，agent 上报自己的标签，service 按规则匹配出该机器的期望状态。**

```
agent 上报：
GET /agent/desired?project=jiexianghua&agent_id=web-01&hostname=web-01
                 &labels=role:web,env:prod,k8s:true&current=12

service 侧规则（按优先级依次覆盖）：
  rule "default"        selector: *                            → hard=on, nginx=on
  rule "k8s-nodes"      selector: labels.k8s == "true"         → + k8s=on
  rule "ssl-special"    selector: hostname in [web-01..web-05] → + ssl=on
  rule "db-no-nginx"    selector: labels.role == "db"          → nginx=off
```

效果：

- 新增一台机器 → 命中默认规则，**零配置**
- 新增一类机器 → 加一条规则，仍是一处改动
- 例外机器 → 单独一条规则，例外数量通常是个位数

**维护量 = 规则数量，不是机器数量。** 1500 台机器的实际维护对象约 5~15 条规则。

约束：`selector` 只允许匹配 agent 自报的标签（project / hostname / agent_id / os / arch / 自定义 labels），**不允许写任意表达式或脚本**（否则又踩 §6.3 那条 RCE 红线）。

**agent 的标签从哪来**：agent 自动采集（hostname、os、arch、project）+ `config.yaml` 里手写的一组 `labels`（如 `role: web`、`env: prod`）。机器自身的属性不需要人工登记，只有"业务角色"需要写一次——而且写在**这台机器**的 `config.yaml` 里，service 侧不用维护。

> **重要：这一层完全在 service 侧，agent 只发一个 GET。** 所以规则引擎有多复杂、管理界面什么时候做，都不影响 agent 契约，可以增量补。这也是把"管理功能"和"agent 定型"解耦的具体体现。

### 6.7 service 不需要"登记"agent，但必须能"看见"落后

一个容易被忽略的点：pull 模型下 **service 不需要事先知道有哪些 agent**（这正是 push 模型必须维护状态表的原因）。agent 来拉取时带着标签和 `current` 版本号，service 顺手就得到一份"活着的 agent 及其对齐情况"的视图——**这份视图是观测得来的，不需要人工维护**。

由此产生一个**必需能力**：service 要能回答"哪些 agent 没对齐期望状态"。

- 拉取请求里的 `current=12` 就是天然的回执 → service 记录 `agent_id → 已应用版本 / 最后拉取时间 / 最后拉取结果`
- 需要能列出：期望已升到 13 但仍报 12 的 agent；超过 N 分钟没来拉取的 agent；拉取成功但对齐失败的 agent
- **没有这一条，1500 台里某台插件没生效你不会知道**，直到有人问"为什么这个项目的图少了一条线"

建议暴露为 service 自身指标（`monitor_desired_lag_agents`、`monitor_desired_last_pull_timestamp{}`），直接画在 Grafana 上——用这套系统监控这套系统。

### 6.8 维护量随什么增长（结论表）

| 运维动作 | 现状（人工 scp） | 插件化 + 规则匹配 | 随机器数增长？ |
|---|---|---|---|
| 新增采集项 | 改 agent 代码，全部重编译重分发 | 新增插件 → 改镜像 | 否 |
| 升级插件 | 不存在此动作 | 改镜像 | 否 |
| 启停某类机器的插件 | 逐台改 `config.yaml` | 改一条规则 | 否 |
| 改插件参数 | 逐台改 `config.yaml` | 改规则里的 `config` | 否 |
| **升级 agent 二进制** | 换二进制 + `systemctl restart`（或容器换镜像 tag） | 同左 | **是** |
| 机器失联 / agent 挂掉 | 人工发现 | systemd `Restart=always` + 告警 | 否（但必须配） |

**唯一随机器数增长的是 agent 二进制本身**——这是"壳不做自更新"这个决策的必然代价（§2.4），必须认清：将来若发现壳里有必须修的缺陷，1500 台就要动 1500 次。缓解在于它是**部署工具链的常规操作**（`systemctl restart` / 改镜像 tag），不是找不到解药——但工作量确实随机器数线性增长。

三条缓解措施：

1. **尽量把"可能变的东西"放进插件**，agent 只留稳定契约（协议、加解密、插件监管）。这正是 §2 那张白名单存在的意义——它不是教条，是在控制未来的滚动成本。
2. **agent 必须能被系统服务托管**：Linux 用 systemd（`Restart=always`），Windows 用服务。agent 自带的 `-d` 守护模式只作为没有 systemd 时的兜底（`go run` 那种父子进程模型在 systemd 下会出问题）。
3. **agent 版本号要上报**（心跳里已有 `agent_version`），并在 service 侧能看到"还有多少台在跑旧版本"——真要滚的时候，你知道工作量到底是多少。

## 七、插件依赖：明确不支持

**设计决定：插件之间不允许声明依赖。**

理由：

1. 依赖一旦被允许，立刻需要解决：启停顺序、版本兼容矩阵、循环检测、依赖失败时的传播策略、被依赖方升级时的协调。这是组合级复杂度，收益却很低。
2. 真实需求（k8s 容器与控制器共用 clientset；两个采集器共用一次 HTTP 探测）应该**合并成一个插件、产出多组指标**——声明式契约里 `metrics` 本来就是数组，每组可带自己的 `timeout` 和标签，合并零损失。
3. 需要"共享一次昂贵采集"的时候，共享应该发生在插件内部（进程内的变量），而不是跨进程依赖——跨进程共享必然引出生命周期耦合。

**直接落到现状**：当前 `agent/Metrics/K8sContainer.go` + `k8sController.go` 是两个采集器、两个 source、两套 `UnRegister*.go`。插件化后合并为 `agent-plugs/k8s` 一个插件，内部共用一个 `clientset`，往外声明两组指标（容器资源组 timeout 3m、控制器副本组 timeout 3m）。顺带解决掉"两个采集器分别初始化 k8s client"的重复开销。

## 八、service 高并发设计

### 8.1 先算清楚量级

300~1500 台，每台每 15s 上报一次：

- 打散良好：1500 ÷ 15 = **100 QPS**
- 打散失败（全部对齐在同一秒）：**1500 请求 / 秒**

两个数字都不是 Go + AES-GCM 的瓶颈（AES-GCM 在该级别 CPU 上约 1~3 GB/s，单请求 50KB 密文解密耗时在微秒级）。**真正的瓶颈是锁竞争和 GC**，不是 CPU。所以优化方向很明确：不要把时间花在换框架上，花在减少锁和减少分配上。

### 8.2 三层削峰

**第一层：源头相位打散（投入产出比最高，零成本）**

现状问题：`agent/Collect/CollectData.go` 的三个 ticker 都从进程启动那一刻开始计时，同一批上线的机器会永远对齐在同一个秒点，制造周期性尖峰。

改法：agent 启动时，每个插件首次采集延迟 `rand(0, interval)`，之后用 `time.NewTicker(interval)` 继续。1500 台机器的 15s 心跳就从"某 1 秒内 1500 个请求"变成"每 10ms 一个请求"。

**这是唯一一个能让峰值下降两个数量级的改动，必须做。**

**第二层：服务端批量写（减少锁竞争）**

现状：`hander.go` 每个请求提交一个 task 到 worker pool，task 内部 `mu.Lock() → 写 GaugeVec → mu.Unlock()`。1500 QPS 下就是 1500 次加锁解锁 + 1500 次 `WithLabelValues` 查表。

改法：把"每请求一个任务"改为"按 (source, project) 攒批"：

```
请求 → 解密解压校验（同步，快）→ 写入对应分片的 buffer → 立即回 200
                                        │
                              每 200ms 或攒够 500 条
                                        ↓
                              一次性加锁 → 批量写 GaugeVec → 解锁
```

GaugeVec 的 `WithLabelValues` 本身有内部缓存，批量写的收益主要来自**分片锁的持有时长下降一个数量级**。配合 `prometheus.GaugeVec` 的 `CurryWith` 预取子指标可再省一层查表。

**第三层：队列满时的策略修正**

现状是"队列满 → 当前 goroutine 代为执行"（`hander.go` 第 497 行）。这个策略在高并发下是**反效果**：它把背压直接传导到 HTTP handler，导致响应变慢、连接堆积，雪崩起点就从这里开始。

改法：队列满 → **丢弃该批并计数**，暴露 `monitor_ingest_dropped_total` 指标。理由：这是一套 gauge 监控，丢一轮数据只是曲线上少一个点，下一个采集周期就补上了；而让 handler 阻塞会连锁到所有 Agent。

### 8.3 连接层与运行时

| 项 | 措施 |
|---|---|
| FD / somaxconn | 已有启动检查（`printPlatformLimits`）。容器内需注意 ulimit 继承自 dockerd，必要时 `--ulimit nofile=65536` |
| 服务端超时 | 补 `ReadHeaderTimeout`（现只有 Read/Write/Idle），防 Slowloris |
| Agent 侧连接复用 | 用共享的 `*http.Client` + 自定义 Transport（`MaxIdleConnsPerHost` 提到 50），现代码每次 `http.Post` 走默认 Transport，keep-alive 复用不足 |
| Agent 侧对象复用 | gzip.Writer / bytes.Buffer 用 `sync.Pool`，避免每轮分配 |
| GOMAXPROCS | 已显式设为 `NumCPU`，容器内建议用 `automaxprocs` 感知 cgroup 限制（否则容器给了 4 核但 Go 看到宿主机 64 核，会创建过多 P 导致调度开销） |
| 自身可观测 | service 增加 `monitor_ingest_*` 自监控指标（请求数、解密失败数、解压字节数、队列水位、丢弃数、各 source 处理耗时分位）——**当前完全没有，这是最值得补的一块** |

### 8.4 验收基线（必须实测，不能靠估算）

```
场景：1000 并发 POST /metrics_data，每请求 50KB 密文（约 1000 条指标），持续 60s
目标：P99 < 200ms，无 5xx，dropped_total = 0，RSS 平稳（GC 后回落到基线 ±10%）
工具：vegeta 或 k6（需自己实现 AES-GCM 加密的请求体，可复用 Go 客户端）
```

这条基线是**准入条件**：不达标就不进入下一阶段——壳与插件全都依赖"接收端扛得住"。

### 8.5 链路级优化（不在这里重复论证）

上面三层是**架构级**削峰（把请求摊开、把锁持有时长缩短、把队列做有界）。除此之外还有三项**链路级**优化——替换 gzip 实现、减小上报载荷、分片 `dynMu`——连同接收链路的耗时分解表，见 **`服务端设计.md §6.7`**。这里不重复，只留两条结论：

- **不要为了性能选静态指标**：动态比静态单次接收慢约 19%，换算成机器成本是 100 QPS 下 **单核 0.7%**；而"每次加指标要改服务端 + 插件两处"是架构属性、不可优化。
- **三项优化里收益最大的不是锁**，而是 **gzip 实现替换**（解压快 2~4 倍）与 **减小载荷**（载荷减半则 gzip 与 JSON 成本同时减半）。

## 九、安全

### 9.1 沿用现有防护（已实现，保留）

- 密钥 fail-fast：`SetEncryptionKey` 长度非法直接 Fatal，热加载非法只告警保留原密钥
- 防重放：timestamp ±5 分钟
- 资源上限：请求体 10MB / 解压 64MB / 单次 20000 条 / 标签值 512 字节
- 白名单实例化 + 代理头仅"直连方可信"时采信
- 指标名 / 标签名正则校验、拒绝 `__` 前缀、拒绝插件声明 `project` 标签
- 单指标时间序列基数上限（50000）、动态指标总量上限（2000）、注销阈值下限（20s）

### 9.2 纯插件自描述带来的新风险与低成本补偿

你选了"纯插件自描述，service 不校验清单"。这意味着**拿到密钥的人可以注册任意指标**。密钥是 1000 台机器共享的，一台被攻陷就等于密钥泄露。三条低成本补偿：

1. **不靠指标名前缀来防冒名**（曾推荐加，**已否决**）："`hard` 插件只能注册 `hard_*`"这类命名约定确实能挡住"一台被攻陷的机器伪造其他采集器的数据"，但它与"指标名只增不改、Grafana 面板零改动"直接冲突（`服务端设计.md §5.5`）——代价是所有面板与告警规则都得改。冒名防护改由下一条承担，**它不依赖命名约定**，因此不与这条纪律打架。
2. **跨 source 重名拒绝**（已实现）：`EnsureMetric` 里已经做了 source 归属校验。
3. **全局限流**：把密钥泄露的最坏影响限制在"灌指标把内存打满"，而基数与总量上限已经挡住这一条。再叠加 service 的单机 QPS 限流（令牌桶）可以进一步收窄。

### 9.3 插件分发的安全

- HMAC 签名 + 时间窗 + nonce 去重 + IP 白名单（§5.3）
- sha256 校验后再落盘，**校验失败绝不执行**
- 解压时防目录穿越（拒绝含 `..` 的 tar 条目）
- 插件二进制放在非 root 可写目录，且**不要放在 PATH 里**，只按绝对路径由 agent 拉起
- 如果以后要更强的保证，可加 ed25519 签名（service 私钥签 `index.json`，agent 内置公钥）。这是**将来能加而不需要改 agent 协议**的（公钥可随 agent 二进制内置），所以现在不必做。

### 9.4 无 agent 的上报方

`trafficSwitching` 目前没有 agent 采集器，由流量切换平台直接上报。插件化后它有两种落法：

- **A（推荐）**：流量切换平台按声明式契约直接 POST `/metrics_data`。它自己维护指标定义，service 侧给它一份独立的 source 名单与密钥。不进插件体系——它本来就不是"装在机器上的采集器"。
- B：为它写一个"推送接收插件"，让某台 agent 转发。多一跳、多一个故障点，不推荐。

**带来的一个后果**：service 仍需支持"非 agent 来源"的声明式上报，因此 `source` 的校验不能只按插件清单来。建议 source 白名单改为配置文件驱动（`server/config/sources.yaml`），插件型 source 由插件清单自动生成，外部型 source 手工登记。

## 十、仓库结构与 module 布局

现有代码是两个 module：`agent` 与 `monitor-server`。新增插件层后，**协议类型必须三方共用**（agent 要收发、插件要实现、service 要解析），否则就会出现同一个结构体三处定义、改一处漏两处。

```
monitor/
├── go.work                       # 本地开发用 workspace，聚合四个 module
├── pkg/
│   └── plugproto/                # module: plugproto —— 唯一的协议定义处
│       ├── wire.go               #   DeclarativePayload / DeclaredMetric / MetricSample
│       ├── plugin.go             #   Hello/Collect/Shutdown 请求响应结构
│       └── limits.go             #   各维度上限常量（三方共享，避免不一致）
├── agent/                        # module: agent —— 壳
│   ├── cmd/agent/main.go
│   └── internal/
│       ├── config/               # 读 config.yaml（只解释 enable/interval/timeout）+ 三维取值 + 热加载
│       ├── proto/                # 【防腐层】唯一读插件数据的文件，见 docs/壳契约-v1.md
│       ├── pluginmgr/            # 清单 / 下载 / 校验 / 解压 / 进程监管 / stdio 客户端
│       ├── scheduler/            # 按插件 interval 调度 + 相位打散
│       ├── transport/            # gzip + AES-GCM + POST + 重试背压 + sync.Pool
│       ├── heartbeat/            # 心跳（壳内）
│       └── statusapi/            # 只读状态端点
├── agent-plugs/                  # module: agent-plugs —— 全部插件
│   ├── sdk/                      # 插件 SDK
│   ├── hard/  nginx/  ssl/  k8s/
│   ├── build.sh
│   └── dist/                     # 构建产物（gitignore）
├── server/                       # module: monitor-server —— service
│   ├── cmd/server/main.go
│   └── internal/
│       ├── ingest/               # 解密解压校验分流
│       ├── registry/             # 动态指标注册表 + 注销（现 Metrics/Dynamic.go）
│       ├── pluginrepo/           # 插件清单 + 制品下发 + HMAC 校验
│       ├── whitelist/            # （现 IpPass）
│       └── selfmetrics/          # service 自身监控指标
├── deploy/
│   ├── Dockerfile.service
│   └── docker-compose.yml
└── docs/
```

**为什么 `plugproto` 要独立成 module**：agent 需要协议类型，但 agent **绝不能依赖 `agent-plugs`**（否则插件代码会被链接进壳，编译产物膨胀、依赖污染）。共享类型抽到最小的独立 module 是唯一干净的解法。

## 十一、框架选型

| 领域 | 推荐 | 理由 | 明确不用 |
|---|---|---|---|
| HTTP 路由 | 标准库 `net/http`；需要中间件链再加 `chi` | Go 1.22+ 的 `ServeMux` 已支持 `GET /path/{id}`，本项目路由不到 10 条 | gin / echo（多一层抽象，现有代码已是纯 net/http） |
| 配置合并（**仅 service 侧**） | `koanf` | 天然支持多来源叠加，**恰好就是"两层配置"的语义**：先 Load `default.yaml` 再 Load `config.yaml`，后者自动覆盖前者 | viper（重、隐式全局状态，且 service 侧现在 yaml.v3 与 viper 各读一遍配置） |
| 日志 | 标准库 `log/slog` + `lumberjack`（需轮转时） | 结构化、零依赖、内置 | zap / logrus（本项目日志量不需要） |
| 配置合并（**插件 SDK 侧**） | **手写，零第三方依赖** | 两层合并就是"读两个 map、后者覆盖前者"，约 30 行，写在 SDK 里（§4.3）。**agent 侧不做合并**，也就不需要任何配置框架——壳的依赖越少，越不会被上游破坏性变更波及（§2.3） | koanf / viper 都不用在 agent；插件侧只用 yaml.v3 |
| 数据校验 | `go-playground/validator` 或手写 | 协议字段校验规则不复杂，手写反而更清晰；结构体多时再引入 | — |
| 压缩加密 | 标准库 `compress/gzip` + `crypto/aes`+`cipher` | 已验证，性能足够 | — |
| 进程监管 | **自研**（~200 行） | 协议是自定义 stdio；`hashicorp/go-plugin` 面向 gRPC/net-rpc，握手与插件形态不匹配，引入后要绕它的抽象 | hashicorp/go-plugin |
| 重试退避 | `cenkalti/backoff` 或手写 | 只有插件重启和上报重试两处，手写指数退避即可 | — |
| 测试 | 标准 `testing` + `testify` | 插件测试用 `os/exec` 直接跑真实二进制（比 mock 更有价值） | gomock 等（本项目的边界就是真实进程） |
| 压测 | `vegeta` 或 `k6` | 需自己构造 AES-GCM 请求体，建议用 Go 写压测客户端 | — |
| 容器 | 多阶段 Dockerfile + `alpine` / `distroless` | 见 §5.5 | — |
| cgroup 感知 | `uber-go/automaxprocs` | 容器内 GOMAXPROCS 与宿主核数不匹配是常见性能坑 | — |

**明确不引入**：DI 框架（wire/dig）、ORM、消息队列（1500 台量级不需要 Kafka）、etcd/consul、WASM 插件、Go `plugin` 动态库，以及**任何用在 agent 侧的非必要第三方库**（壳的依赖预算见 §2.3）。

## 十二、构建路线

顺序不能反，每一步都有依赖：

| 阶段 | 内容 | 退出条件 |
|---|---|---|
| **0. 契约落地** | 抽 `pkg/plugproto`，三端改用共享类型；补单测 | 类型定义唯一；三端编译通过 |
| **1. service 先能收** | **删旧链路**（80 个静态定义 + 旧 `data` 路径）→ 声明式路径端到端打通 + `monitor_ingest_*` 自监控 + **压测基线达标** | §8.4 基线通过。**不达标不进入下一阶段** |
| **2. 插件 SDK + 打样** | `agent-plugs/sdk` + `hard` 插件跑通 hello/collect/shutdown；进程级单测 | 手工 `echo '{"id":1,"cmd":"hello"...}' \| ./hard` 能正确应答 |
| **3. agent 壳** | 配置读取 / 懒下载 / 进程监管 / 调度打散 / 上报 / 心跳 / 状态端点 | 一台真实机器上跑通 hard 插件全链路 |
| **4. 其余插件** | `nginx` / `ssl` / `k8s`（合并原 k8sController）逐个做成插件 | 指标名与 `插件设计 §5` 映射表逐字一致（见下） |

### 12.1 不做迁移，也不做兼容（2026-09-20 定）

本项目**不存在新旧架构并存的窗口**，因此：

- **没有灰度、没有兼容层、没有"切换"这个动作。**
- 80 个静态定义与旧 `data` 路径**在阶段 1 一开始就删除**。这不是"迁移完成后的清理"，而是**新链路的前置条件**：动态注册与静态定义同名即 `AlreadyRegisteredError` → 400，**不删则新链路一个指标都报不进来**（`服务端设计 §2.2`）。
- 旧 `data` 路径**不能静默丢弃**：显式返回 4xx + 日志（`source=hard 的上报走了已废弃路径`），以便知道还有谁落在旧路径上——否则那些来源会静默缺数据、直到有人看面板才发现。

删掉兼容层省下的三样东西：80 条 `compatMetrics` map、一条"迁移期已上线指标标签集合不可变"的临时约束、一个"迁完记得删兼容层"的人工动作。

### 12.2 阶段 4 的关键约束：指标名不变

插件化改变的应该是"数据怎么来"，不是"指标叫什么"。`docs/插件设计.md §5` 的映射表是 80 个指标名的**唯一权威**，实现时逐字核对——静态定义已删，这张表是唯一的对照物。名字一致，现有 Grafana 面板与告警规则零改动。

**另外 5 项会改指标契约的事项不在本次范围**（标签命名统一、`controllerName` 取 Deployment 名、`cleanNamespace` 去硬编码、外部命令改读 procfs、传输层升级）。它们需要单独拍板、单独排期——理由不是"没时间"，而是**它们都会改名字或取值口径**，混进构建流程会让"构建失败"与"改名失败"无法归因。清单见 `docs/README.md §四「本次范围外」`。

## 十三、风险清单

| 风险 | 后果 | 对策 |
|---|---|---|
| 插件 stdout 被日志污染 | 协议解析失败，采集全断 | SDK 强制重定向 stdout + agent 侧非 JSON 行自检告警 |
| 插件 OOM / 死循环 | 单机内存被打满，整机指标丢失 | 独立进程隔离 + 硬超时 kill + 连续失败熔断；可配 `GOMEMLIMIT` |
| 插件升级失败 | 该采集器消失，可能直到有人看面板才发现 | 原子替换 + 握手失败回滚到 `.old` + 失败计数告警 |
| **壳里出现必须修的缺陷** | 唯一不可就地替换的组件出问题，1000+ 台要动二进制 | 壳不自更新（§2.4），更新由 systemd / 容器编排负责：物理机换二进制 + `systemctl restart`，容器换镜像 tag 滚动更新；同时用 §2.3 四条把出错概率压到最低 |
| 壳启动后"半死"（进程活着但不干活） | 最难排查的状态，且自动重启机制不会触发 | 启动自检（配置 / 密钥 / 插件目录 / 连通 service），任一不过直接退出，交给 systemd `Restart=always` 或容器重启策略（§八） |
| 插件演化改动了协议字段名 | 被迫改壳，破坏"壳终生不改" | §3.5 冻结边界表 + `proto` 版本号协商 + 壳显式拒绝不认识的高版本 |
| agent 容器内无写权限 | 插件下载失败 | 部署文档明确要求挂载可写卷（`emptyDir` 或 hostPath） |
| **静态定义已删、旧 agent 仍在报** | 旧上报无处落地，静默缺数据 | 旧 `data` 路径**显式返回 4xx + 日志**（`服务端设计 §2.2`）；旧 agent 是一次性替换的，不设并存窗口 |
| 1500 台同时拉取插件 | service 带宽与 IO 尖峰 | 插件下载加 0~30s 抖动 + 只在下发版本变化时下载 |
| 批量改插件启用要触达每台机器 | 需要配置管理工具（Ansible 等） | 这是"不做远程管理"的代价（§6.0）；换来壳里零远程控制代码。Ansible 本来就是滚 agent 的前提 |
| **agent 二进制本身是唯一随机器数增长的工作量** | 发现壳缺陷时 1000+ 台要滚 | systemd `Restart=always` 托管 + 心跳里的 `agent_version` 在 service 侧可见（§2.5、§6.8） |
| 某台机器插件静默失效 | 面板少一条线，无人知晓 | 壳的只读状态端点（§2.1 第 7 项）+ service 侧按 source / project 的活跃上报统计 |
| 平台制品不齐 | arm64 机器拿不到插件 | `index.json` 必须列全平台；agent 找不到自己平台时保持旧版本并明确告警 |

## 十四、重构中必须保留的资产

以下是当前代码里做对了、不应该在重构中丢掉的东西：

1. **只做管道，查询与告警交给 Prometheus 生态。** 不替换 Prometheus、不自研时序库，这是整套系统最省的决策。
2. **全 GaugeVec + 超时注销，不用 counter。** 序列会被 `DeleteLabelValues` 摘掉，如果语义是 counter，它再次出现时会从 0 重算，Prometheus 侧会产生错误的 rate 尖峰。这条经验必须保留。
3. **Worker Pool + 分片锁。** 同 project 串行、不同 project 并发。分片思路在批量写重构后依然有效（分片 key 从 `source` 扩展为 `source+project`）。
4. **先回 200 再异步处理。** 上报端不需要等待处理完成，这让 Agent 侧的超时与重试逻辑变得简单。
5. **部署友好。** 单二进制、单实例、零外部依赖，`scp` 上去就能跑。这是自建监控相比引入整套可观测平台最大的优势，别丢掉。
6. **校验密度高。** timestamp 防重放、基数/长度/条数/解压上限、密钥 fail-fast、白名单实例化、代理头仅可信直连采信——这些是重构里最容易在"重写"时被简化掉的，要显式保留。
7. **按 source 独立注销阈值。**（`Handers/timeouts.go`）这条经验已经固化进声明式协议的 `timeout` 字段（取值来自 `manifest.yaml` 的 `default_timeout`，**与采集周期同源**），是"把踩过的坑变成契约"的正面例子。
