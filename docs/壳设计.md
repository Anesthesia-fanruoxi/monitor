# Agent 壳设计

> 定位：**一个跑进程、搬字节、加解密、发 HTTP 的通用搬运工。**
> 读者：实现壳的人。
> 约束来源：`docs/壳契约-v1.md`（**冻结，本文不得与之冲突**；冲突以契约为准）。
> 本文只讲「怎么实现」，不重复论证为什么这么设计。

---

## 一、壳的职责（引用契约，不重复论证）

壳只做 7 件事（`插件化架构设计.md` §2.1）：

1. 读配置（自己取值 + 把 `plugins.<name>` 原样交给插件，见 §5.1）
2. 插件生命周期（懒下载 → 校验 → 启停 → 替换）
3. 调度（按 manifest 声明、config 可覆盖的 `interval` 派发 collect）
4. 组装上报报文（`project` 读 `config.yaml`、`source` = 插件目录名、`timestamp` = 采集时刻；**不向插件注入业务参数**，见契约 §2.5 与 §7.6）
5. 传输（JSON → gzip → AES-GCM → POST，带重试与背压）
6. 心跳（**在壳内**，不下沉为插件）
7. 只读状态端点

**壳不做**：不做业务计算、不解析指标内容、不保存业务状态、不实现采集逻辑、不接收远程指令。

## 三、目录布局与行数预算

```
agent/
├── cmd/agent/main.go              250   生命周期、守护、启动自检、优雅退出
└── internal/
    ├── config/                    130   manifest 读取、周期三级取值、热加载、plugins 子树整体交给插件
    ├── proto/                     110   【防腐层】唯一读插件数据的文件
    │   ├── decode.go                    Envelope（4 字段）+ 上限检查 + 宽容解析
    │   ├── encode.go                    hello / collect / shutdown 三行 JSON
    │   └── proto_test.go
    ├── pluginmgr/                 500   清单、下载、校验、解压、进程监管、stdio 客户端
    │   ├── manager.go                   生命周期编排（reconcile）
    │   ├── instance.go                  单插件实例（进程 + stdio）
    │   ├── fetch.go                     懒下载、sha256、原子替换、回滚
    │   └── safeio.go                    路径穿越防护、大小上限
    ├── scheduler/                 120   interval 调度、相位打散、单飞
    ├── transport/                 200   组装信封、压缩、加密、POST、重试、背压
    ├── heartbeat/                  80   心跳（壳内）
    ├── statusapi/                 100   只读状态端点【外围】
    └── logging/                    80   slog 初始化 + 插件 stderr 前缀转发【外围】
```

**预算校验**：内核（proto + config + pluginmgr + scheduler + transport + heartbeat）= **1140 ≤ 1400**；外围（statusapi + logging）= **180 ≤ 200**；总量 **1580**。

> 数字是**预算**不是指标。它的用途只有一个：涨到 2 倍时你能立刻察觉有东西溜进来了。

## 四、启动流程

```
main()
 ├─ 1. 解析命令行（-d 守护、-c 配置路径、-v 版本）
 ├─ 2. 初始化日志（slog，level 可配）
 ├─ 3. 启动自检（6 项，任一不过 exit 非 0）
 │     ① 配置可解析且必填项齐全（metrics_url / encrypted / project）
 │     ② encrypted 长度 ∈ {16,24,32}
 │     ③ 插件根目录可写
 │     ④ 每个已启用插件的 manifest.yaml 可解析，周期与阈值通过钳制表
 │     ⑤ 探测 metrics_url 可达（可配置为仅告警，见 §17）
 │     ⑥ 已启用插件的制品在位（不在则尝试下载一次，失败即退出）
 ├─ 4. 加载配置（取 enable/interval/timeout + 校验；**不生成任何文件**）
 ├─ 5. 拉起插件（reconcile：只启动 enable=true 的）
 ├─ 6. 启动心跳（第一个 tick 也加 0~interval 抖动）
 ├─ 7. 启动 scheduler（每个插件一个 goroutine）
 ├─ 8. 启动 statusapi（默认只监听 127.0.0.1）
 ├─ 9. 启动配置热加载（5s 轮询或 fsnotify）
 └─ 10. 等待 SIGINT/SIGTERM → 优雅退出
```

**优雅退出顺序**（重要，决定进程是否留下僵尸插件）：

```
收到信号
 → 停止接收新任务（cancel context）
 → 等待在途 collect 结束（最多 5s）
 → 向所有插件发 shutdown，等 5s
 → 未退出者 SIGTERM，再等 2s
 → 仍未退出者 SIGKILL
 → 停止 sweeper / 状态端点 → 退出
```

**为什么自检失败要退出而不是降级运行**：一个"进程活着但半死"的壳是最难排查的状态——systemd 认为它健康、监控面板认为它离线、日志里全是零散告警。宁可反复重启（退避可见、日志明确），也不要半死不活。

## 五、config 模块

### 5.1 谁取哪些键（2026-09-18 改判：壳不做合并）

**`config.yaml` 只有一份，壳与插件都读它**，各取自己那部分：

```
config.yaml 的 plugins.<name>
  ├── enable / interval / timeout      → 壳读（保留键，过钳制表后交给 scheduler）
  └── 其余所有键                        → 插件读（SDK 取出来与制品的 default.yaml 合并）
```

壳**只读这三个键**：不合并、不校验参数、**不生成任何派生文件**。合并（`plugins.<name>` 覆盖 `default.yaml`）在插件 SDK 里做，产物只在内存中（契约 §9.1）。

```go
// internal/config 的实现范围（约 130 行）
func Load(path string) (*Config, error)
func (c *Config) PluginKeys(name string) (*PluginKeys, error)  // enable / interval / timeout + 三级取值 + 钳制
```

手写约 130 行，**不使用任何配置框架**。**在 agent 侧引入 koanf / viper 是负资产**：壳的依赖越少，越不会被上游破坏性变更波及。（插件 SDK 侧需要 YAML 解析，直接用 `gopkg.in/yaml.v3` —— I3 只约束壳。）

> **别把 `manifest.yaml` 和 `default.yaml` 弄混**——两个文件都在制品包里，分工完全不同：
>
> | 文件 | 内容 | 谁读 | 何时读 |
> |---|---|---|---|
> | `manifest.yaml` | 制品元信息：`name` / `version` / `default_interval` / `default_timeout` | **壳** | 启动与加载配置时 |
> | `default.yaml` | 插件自己的参数默认值（如 `k8s` 的 namespace 白名单） | **插件**（壳不读） | 每轮 collect（SDK 带缓存） |
>
> 周期与阈值放 `manifest.yaml` 而不是 `default.yaml`，是因为后者是"插件参数的默认值"——**让壳去读插件的配置文件属于暴露面扩大**；而 manifest 本来就是壳在下载、校验、解压时读的东西（契约 §2.5）。插件侧正好相反：它读 `default.yaml`，**不读 `manifest.yaml`**（周期与版本由壳经 env 告诉它）。

### 5.2 壳与插件的共享契约（两条，冻结）

`plugins.<name>` 是壳与插件**唯一共享的配置位置**。随之冻结的只有两条：

1. **容器键名 `plugins`**，以及**壳保留键 `enable` / `interval` / `timeout`** 的名字。改任一项等于同时改壳与 SDK，要走契约评审（契约 §12 第 1 条）。
2. **除保留键外的所有键，壳一律不解释**：不校验、不报错、不做类型检查。插件新增配置项**永远不需要改壳**。代价是壳无法替插件校验参数——写错的参数要等插件自己报错，这是刻意的取舍（契约 §9.1）。

> 反过来，**顶层键（`project` / `metrics_url` / `encrypted` / …）与插件无关**，以后加 `log_level` 这类键不影响任何插件。

### 5.3 热加载

- 现状 `LoadConfig` 有 30 秒缓存，采集每轮重新读以支持热更新。
- 目标：**5 秒缓存**（或加 fsnotify 立即感知）。
- 配置变更的行为分两种：

| 变更 | 行为 |
|---|---|
| `plugins.<name>.enable` 变化 | 启动 / 停止该插件进程 |
| `plugins.<name>.interval` / `.timeout` 变化 | 下一轮调度生效，**不重启进程** |
| 其它插件参数 | **壳什么都不做**——插件每轮自己读 `config.yaml`（SDK 带 mtime 缓存），改动下一轮自然生效 |
| 顶层配置（`metrics_url` / `encrypted` / `project`） | 热更新内存值；**非法值只告警并保留旧值**，绝不因配置写错导致全网上报失败 |
| 新增 / 删除插件条目 | 对应启动 / 停止 |

**"配置改错"必须退化为"5 秒后还是旧配置在跑"，而不是"整机采集停摆"。**

> 插件参数那一行是这次改判最直接的红利：以前壳要先重写 `effective.yaml` 插件才看得到变化，**壳里那段写文件的代码本身就是一条失败路径**（磁盘满、权限、被安全软件拦住）；现在壳完全不参与。

## 六、防腐层 `internal/proto`

**壳里唯一允许读插件输出的文件。** 细节规则见契约 §2，这里给实现。

### 6.1 Envelope

```go
type Envelope struct {
    ID      uint64          `json:"id"`      // 1. 请求响应配对
    OK      bool            `json:"ok"`      // 2. 本轮成功与否
    Proto   int             `json:"proto"`   // 3. 协议版本，只接受 1
    Metrics json.RawMessage `json:"metrics"` // 4. 指标字节块，不透明，永不解码
}
```

`Metrics` 用 `json.RawMessage` 是**整个契约的技术核心**：它一旦被反序列化成结构体，壳就开始认识指标字段了，`samples`/`labels` 一改名就会打到壳。

**这四个字段全部是传输语义，没有一个是业务字段**（契约 §2.1）。`interval` / `timeout` 曾经在这里，2026-09-18 已移出——它们由 `config` 模块在启动时算好直接交给 `scheduler`，**插件输出里不含任何调度参数**（契约 §2.5）。这也是 `proto` 模块比上一版少 50 行的原因：不再需要宽容解析 `Duration`。

**校验靠 lint 而不是靠自觉**：`internal/proto` 里只允许出现 4 个 json tag。任何人加第 5 个字段，`grep -o 'json:"[a-z_]*"' decode.go | sort -u` 当场变 5 行（契约 I1）。

### 6.2 宽容解析

```go
func DecodeEnvelope(line []byte) (Envelope, error)   // 仅当"根本不是 JSON"时返回 error
```

`id` / `ok` / `proto` 三个字段接受多种写法（字符串数字、`null`、缺失），规则见契约 §2.2。**但 `metrics` 不做任何宽容**：它要么是一段合法 JSON，要么整轮按失败处理——`json.RawMessage` 只在最外层做一次合法性判断，**绝不进入它的内容**。

> **`Duration` 类型已经从这一层消失。** 需要解析 `"15s"` 这类值的地方只剩 `config` 模块（读 manifest 与 config 里的周期），它读的是本地文件而不是插件输出——**不受"插件可能用任何语言写"这条约束影响**，所以不需要那么宽容的解析器。

**宽容必须留痕**：所有降级走 `warn-once`（每个插件每个字段只告警一次）。宽容却不告警，等于把插件的 bug 永久藏起来。

### 6.3 缺省与钳制（两张表，逐行实现 + 单测）

**缺省降级表**：

| 字段缺失 / 非法 | 取值 |
|---|---|
| `metrics` | 空 → 本轮无数据，**不记为失败**（"这轮没采到"不是错误） |
| `ok:false` | 判该轮失败 + 计数，`metrics` 内容一律忽略（不发送、不缓存） |
| `proto` 缺失 | 视为 `1` |
| `proto > 1` | 拒绝该插件（不启动 / 停止重启），报"需升级 agent" |
| `id` 不匹配 | 丢弃该响应 + 计一次失败 |
| 整行不是 JSON | 判该插件失败（按"写坏 stdout"处理，§7.4） |

**参数钳制表**（防止坏输入把宿主机打死）：

| 参数 | 范围 | 越界处理 |
|---|---|---|
| 单行 stdout | ≤ 8 MiB | kill 进程 + 判该轮失败 |
| 单轮输出总量 | ≤ 32 MiB | 同上 |
| 单插件并发 collect | 1 | 上一轮未结束 → 跳过本轮并计数 |
| `interval`（来源是 config/manifest，**不是插件**） | `[1s, 30m]` | 取默认 `30s` + 告警 |
| `timeout`（来源同上） | `[2×interval, 30m]` | 取 `2.5 × interval` |

**最后两行虽然不再来自插件，仍然必须留在表里**——写配置的人同样会写错，而 `interval: 0` 会让壳空转、`timeout < interval` 会让时间序列在两轮之间被摘掉。钳制发生在 `config` 模块（§5.1），不在这两层。

### 6.4 允许出现的 source 字面量白名单

契约 I2 要求壳不认识插件名（不出现 `hard`/`nginx`/`ssl`/`k8s`）。**唯一的例外是 `heart`**：心跳在壳内，壳必须以 `source = "heart"` 上报它。因此 grep 校验的准确形式是：

```
壳内不得出现 "hard" / "nginx" / "ssl" / "k8s" / "k8sController" / "trafficSwitching" 字面量
（"heart" 例外，且只允许出现在 internal/heartbeat 内）
```

## 七、pluginmgr：插件生命周期

### 7.1 状态机

```
disabled ──enable=true──▶ resolving ──有制品──▶ starting ──hello ok──▶ running
                              │                    │                    │
                          无制品→ downloading      │hello 失败          │进程退出/超时
                              │      ↓             │(回滚 .old)         │
                              └── verifying ───────┘                    ▼
                                   ↓                                   backoff
                             installing(原子替换)                        │
                                                                  连败 ≥5 且从未健康
                                                                        ▼
                                                                     failed（停止重启）
```

| 状态 | 含义 | 对外可见（状态端点） |
|---|---|---|
| `disabled` | 配置里 `enable=false`，**不下载** | 是 |
| `resolving` | 查 `index.json` 取版本与 sha256 | 是 |
| `downloading` | 下载 `.tmp` | 是（带进度） |
| `verifying` | 校验 sha256 | 是 |
| `installing` | 解压 + 原子替换 | 是 |
| `starting` | 拉起进程 + 握手 | 是 |
| `running` | 正常，含「上一轮采集是否成功」 | 是 |
| `backoff` | 崩溃后指数退避中（1s→2s→4s…上限 60s） | 是 |
| `failed` | 连败 ≥5 次且从未健康跑过，**停止自动重启** | 是（需人工介入） |

**`failed` 状态是必需的**：没有它，一个必然崩溃的插件会让壳永远在"重启→崩溃"之间循环，打爆日志和 CPU。

### 7.2 懒下载（用户要求：未启用不下载，启用才下载）

```
reconcile（配置热加载后 / 插件不存在时触发）
  for each plugins.<name>:
      enable=false                → 确保进程未运行；**不下载、不占用磁盘**
      enable=true 且制品在位      → 直接启动
      enable=true 且制品不在位    → 从制品仓库下载 → 校验 → 安装 → 启动
```

下载流程（与制品仓库对接，细节见服务端设计 §7）：

```
1. GET /agent/index.json            （带 HMAC 签名）
2. 取本平台条目（linux/amd64）；无条目 → 保持现状 + 明确告警
3. 检查 min_agent_version ≤ 当前壳版本；不满足 → 拒绝并告警"需升级 agent"
4. 下载到 agent-plugs/<name>/.download/<name>.tgz.tmp
5. 校验 sha256；不匹配 → 删文件 + 重试至多 3 次（退避 5s/15s/30s）
6. 解压（路径穿越防护，见 §7.5）
7. 停止旧进程 → 目录原子替换（旧目录挪到 .old）
8. 启动新进程 + hello 握手
9. 握手失败 → **回滚到 .old 并重启旧版本**
10. 成功 → 删除 .old 与 .download
```

**第 9 步是硬要求。** 没有回滚，一次坏发布能让 1000 台机器的某个采集器同时消失，而且你可能几天后看面板才发现。

### 7.3 进程监管与 stdio 客户端

```go
type Instance struct {
    // 下面三个值由 config 模块算好后注入（manifest 默认值 + config 覆盖 + 钳制），
    // 不来自插件输出（契约 §2.5）
    Name     string
    Version  string
    Interval time.Duration
    Timeout  time.Duration

    cmd    *exec.Cmd
    stdin  io.WriteCloser
    stdout *bufio.Reader
    stderr io.ReadCloser

    mu      sync.Mutex     // 保证一次只有一个在途请求（协议不支持并发）
    nextID  uint64
    state   State
    fails   int
    healthy bool           // 是否曾经活过 1 分钟
}
```

```go
func (i *Instance) Call(req []byte, timeout time.Duration) (proto.Envelope, error)
```

要点：

- `Call` 持 `mu` 全程，**单飞**：上一轮未结束就不发起下一轮（返回 `errBusy`，调度器跳过本轮）。
- 每次写入后**必须 flush**，否则插件收不到这一行。
- `stdout` 用 `bufio.Reader.ReadBytes('\n')` 读一行，**长度超过 8 MiB 直接判失败**。
- `stderr` 单独 goroutine 逐行读取，加 `[plugs/<name>]` 前缀转发到自己的日志。
- 超时处理：`Call` 超时后 **kill 进程**（不是只放弃等待），然后按"崩溃"处理进入退避。一个卡死的插件不 kill 就会永远占着调度。
- **`Call` 的返回值只用两个字段**：`Env.OK` 决定成败计数，`Env.Metrics` 原样转交 transport。**没有第三个字段可用**——`Envelope` 只有 4 个字段（契约 §2.1）。

### 7.4 退避与熔断

| 情形 | 行为 |
|---|---|
| 进程退出（非 shutdown） | 指数退避重启：1s → 2s → 4s … 上限 60s |
| 存活超过 1 分钟 | 视为健康，**重置退避计数** |
| 单轮 collect 超时 | kill + 计一次失败 + 退避重启 |
| 连续失败 ≥ 5 次且从未健康跑过 | 标记 `failed`，**停止自动重启**，只保留状态展示与日志 |
| 插件写坏 stdout（非 JSON 行） | 判定失败，同"进程退出"，并附带明确告警 |

### 7.5 安全底线（`safeio.go`）

壳是唯一以 agent 身份执行外部文件的组件，这三条必须一次写对：

1. **路径穿越防护**：解压制品时拒绝任何 `..`、绝对路径、符号链接条目。制品来自 service，但壳不能假设 service 永远可信且无 bug（tar 里的 `../../etc/...` 是经典手法）。
2. **大小上限**：下载 ≤ 64 MiB，解压后总量 ≤ 256 MiB。超限即中止并删除临时文件。
3. **只执行明确路径**：`exec` 路径恒为 `agent-plugs/<name>/<name>`，**不查 PATH、不 glob、不执行目录下其它文件**。插件名必须命中配置里声明的名字。

### 7.6 进程环境：只注入"壳算出来的值"

壳启动插件时设置的环境变量**只有下面这些**，一个业务参数都没有：

| 变量 | 内容 | 为什么必须由壳给 |
|---|---|---|
| `MONITOR_CONFIG` | agent `config.yaml` 的绝对路径 | 只有壳知道它被 `-c` 指到哪；**值由插件自己读**（§5.1） |
| `MONITOR_PLUGIN_DIR` | 插件自己的目录 | 壳才知道制品落在哪；SDK 用它的 basename 定插件名 |
| `MONITOR_PLUGIN_INTERVAL` | 生效的采集周期（manifest 默认 → config 覆盖 → 钳制） | 只有壳做三级取值与钳制（契约 §9） |
| `MONITOR_PLUGIN_TIMEOUT` | 生效的注销阈值 | 同上；SDK 用它填 `DeclaredMetric.timeout` |

**不注入的东西**（这是本条的全部要点）：

| 值 | 谁取 | 怎么取 |
|---|---|---|
| `project` | 壳，且只留在壳内 | 读 `config.yaml`，写进上报报文（§9.2）。**插件任何地方都不出现 project**——同一份二进制要能装在任意项目的任意机器上 |
| `source` | 壳 | = 插件目录名 |
| `timestamp` | 壳 | 采集时刻 |
| `hostname` 等本机事实 | **插件自己** | `os.Hostname()`（SDK 提供 helper，见插件设计 §3.7） |
| 插件需要的任何其它本机信息 | **插件自己** | 读 `/proc`、执行命令、读自己的配置 |

> 一句话规则：**壳只注入"壳算出来才有的值"，业务事实一律插件自取。**
> 于是 `collect` 请求就是 `{"id":2,"cmd":"collect"}`（契约 §3）——**壳不需要在每轮往插件里塞任何东西**。

**一处必须守住的实现细节**：`hostName` 会同时出现在插件指标（`hard` 等）与壳内的心跳指标（`heart`）里，两边的值必须由**同一套算法**得出（`os.Hostname()`，失败退回 `/etc/hostname`，带 5 分钟缓存）。壳不能复用 SDK 的实现（契约 I3 的依赖白名单不允许），所以这段算法在壳与 SDK 各有一份——**用一条断言测试按住**（同一台机器上两处取值必须相等），否则面板上同一台机器会出现两个主机名标签值。

## 八、scheduler

```go
func (s *Scheduler) Run(ctx context.Context, inst *pluginmgr.Instance, interval time.Duration)
```

### 8.1 相位打散（这是削峰的唯一有效手段）

```go
first := time.Duration(rand.Int63n(int64(interval)))   // 启动时随机延迟 0~interval
```

现状是三个 ticker 都从进程启动那一刻开始计数，1500 台机器如果同时被自动化部署，就会在同一秒集中上报。**这一行改动把峰值降低两个数量级**，而且它必须在 agent v1 里——事后补就要滚 1500 台。

注意：每个插件的相位**独立随机**，不要用同一个种子或同一个基准时间。

### 8.2 单飞与跳过计数

```
tick 到点 → 若上一轮未结束 → 跳过本轮 + skipCount++（状态端点可见）
         → 否则发起 collect
```

**不排队**。排队会让慢插件拖垮调度，且一个失败轮次堆积起来后没有任何价值（gauge 数据过期即无用）。

### 8.3 周期变更

`interval` / `timeout` 的取值以 `config.yaml` 为准（manifest 只提供默认值）。变更后**只影响下一次调度**，不重启进程——插件对此完全无感知，它只在自己的 `Collect` 被调用时干活（§5.2）。

## 九、transport

### 9.1 为什么不聚合多个插件的数据

一个自然的想法是"把所有插件的数据合并成一个 payload 再发"。**不做**，理由是失败隔离：

> k8s 插件产出 5 MB，如果和 hard 插件合并成一个请求，请求体可能超过服务端 10 MiB 限制，**导致 hard 的数据也一起被 400 拒绝**。

每个插件的数据独立成一个 payload 独立发送：一个插件的数据有问题，不影响其它插件。请求数从 100 QPS 变成约 400 QPS（4 个插件），仍然远低于容量。

### 9.2 发送

**发给 service 的字段一个都不新增**——它们与服务端 `hander.go` 里现有的 `SendPayload` 完全对齐，`server` 侧零改动：

```go
type Payload struct {
    Project   string          `json:"project"`    // 来自 config.yaml
    Source    string          `json:"source"`     // = 插件目录名；heartbeat 用 "heart"
    Timestamp int64           `json:"timestamp"`  // 毫秒，壳取当前时间
    Schema    string          `json:"schema"`     // 常量 "v2"
    Metrics   json.RawMessage `json:"metrics"`    // 插件原文，零解码
}

func (t *Transport) Send(ctx context.Context, p Payload) error
```

**壳在这里做的唯一一件事是"补四个外层字段"**：`project` 读 `config.yaml`、`source` 取插件目录名、`timestamp` 取采集时刻——**三项都不问插件**（§7.6）；`Metrics` 的值就是插件输出的原始字节，`json.Marshal` 对 `json.RawMessage` 是**直接拷贝、不解析结构**——所以"壳不解析插件字段"这条在传输路径上依然成立，而且零解析开销。

> 服务端据此分流：`len(payload.Metrics) > 0` → 声明式路径（`handleDeclarativePayload`），否则走旧 `data` 路径。**这意味着 service 不需要为新壳改一行代码。**

链路：`json.Marshal` → `gzip` → `AES-GCM` → `POST application/octet-stream` → URL = `<metrics_url>/metrics_data`。

- 加密：`gcm.Seal(nonce, nonce, data, nil)`，**nonce 前置拼接**（与服务端现有解密封装一致）。
- HTTP 客户端：超时 30s、`MaxIdleConns=100`、`MaxIdleConnsPerHost=10`、`IdleConnTimeout=90s`。
- 仅接受 2xx，否则报错并携带最多 256 字节响应体（**服务端的 400 里带具体原因，是排障的关键信息，一定要打到日志里**）。
- `gzip.Writer` 与 `bytes.Buffer` 走 `sync.Pool`（每 15 秒 × 4 插件 × 1500 台 = 每秒上百次分配）。

### 9.3 背压：每插件一个"最新值槽"

```
每插件维护一个深度为 1 的待发送槽：
  新一轮数据到达 → 覆盖槽内旧数据（旧的丢弃并计数）
  发送 goroutine 取出并发送
```

**深度为 1 是刻意的**：gauge 数据只关心最新值，积压旧轮次毫无价值，反而会拖垮内存。失败重试 3 次（1s/2s/4s）后丢弃本轮 + 计数，下一轮照常。

### 9.4 心跳独立通道

心跳（§10）**与业务数据分开、独立发送、独立重试**。理由：心跳是"这台机器是否活着"的唯一信号，不能因为某个插件的数据体积过大导致请求失败而连带丢失。

## 十、heartbeat

**心跳留在壳内，不下沉为插件。** 否则"插件被停用"会被服务端误判为主机离线。

```go
// 每 15s，source = "heart"
metrics: [
  { name: "is_active",     help: "agent 状态是否存活", type: "gauge",
    labels: ["hostName"], samples: [{labels:{hostName:...}, value: 1}], timeout: "45s" },
  { name: "agent_version", help: "agent 版本号",       type: "gauge",
    labels: ["hostName"], samples: [{labels:{hostName:...}, value: 1.2}], timeout: "45s" },
]
```

三个注意点：

1. **`agent_version` 是 float**（现状如此）：多段版本号只报 `major.minor`。保持兼容，不要改成字符串。
2. **`hostName` 标签名是驼峰**（现状如此），与 `os_version` 这类蛇形混用。**保持不变**——改名会破坏现有 Grafana 面板。
3. **超时语义**：旧路径心跳超时是 `is_active = 0`（保留序列），动态注册表的行为是**删除序列**。**已定（2026-09-20）：服务端采用方案 A——面板查询改为 `absent(is_active{...})` 或 `is_active != 1`，协议不加字段**（见服务端设计 §5.3）。壳侧不需要改动。

心跳同时也承担"证明壳自己活着"的作用：service 侧统计 `monitor_agent_versions{version}` 就能回答"多少台还在跑旧壳"。

## 十一、为什么壳不做自更新（2026-09-18 改判）

**本节是删除项，不是设计项。** 现有 `CheckVersion.go`（393 行）连同守护模式的回滚逻辑一并删除。

现有实现有四道防线，看起来完备：

| 环节 | 现有实现 |
|---|---|
| 取版本 | `GET /version` 比对 |
| 下载 | `GET /agent/agent` |
| 校验 | sha256 |
| 落地 | 写 `<exe>.new` |
| 备份 | `backupFile` 存 `<exe>.bak` |
| 替换 | `os.Rename` 原子替换 |
| 重启 | 写 `restart.flag`，守护进程检测后立即重启 |
| 回滚 | 新版本连崩 5 次且从未健康跑过 → 自动回滚 `.bak` |

**问题出在"替换"这一步的语义上**：`syscall.Exec` / `os.Rename` 换掉的是**进程里的二进制**，而容器里真正被版本化的是**镜像**。于是出现版本漂移——容器内跑的是新壳、镜像还是旧壳，**下次容器重建就悄无声息地回退了**。这种"看起来成功、实际是假象"的更新通道，比没有更危险。

而更新这件事本来就有更可靠的主人：

| 部署形态 | 谁负责更新 | 怎么滚 |
|---|---|---|
| 物理机 | systemd | 换二进制 + `systemctl restart`；`Restart=always` 兜住异常退出 |
| 容器 | 容器编排 | 换镜像 tag，按滚动策略逐节点推 |

**壳只需要老实做一件事：启动自检失败就退出（壳契约 §八），把重启交给 systemd 或编排器。** 这正是"壳只做自己算得出来的事"这条原则在更新问题上的延伸——进程生命周期不属于壳。

删掉的收益：**−250 行**（总量 1830 → 1580），以及整类"替换自己崩在半路"的故障。

代价与缓解：壳里出现必须修的缺陷时，1000+ 台要动二进制。这在物理机上是"换二进制 + restart"、在容器里是"改一个镜像 tag"，属于常规操作；缓解手段是①把易变的东西放进插件、②`agent_version` 在 service 侧可见（§十 heartbeat）以便随时知道工作量。

> **`auto_update` 键保留**，但语义收窄为**"是否自动更新插件制品"**；壳自身不再读它做任何事。

## 十二、statusapi（外围模块）

只读，**默认只监听 `127.0.0.1`**（可配；暴露公网会把"哪些插件、什么版本、什么时候采的"泄漏出去）。

```json
{
  "agent_version": "1.0.0",
  "project": "jiexianghua",
  "uptime_seconds": 86400,
  "offline_mode": false,
  "plugins": [
    {
      "name": "hard", "version": "1.2.0",
      "interval": "15s", "interval_source": "config",
      "timeout": "45s", "timeout_source": "manifest",
      "state": "running",
      "last_collect_at": "2026-09-18T15:30:00+08:00",
      "last_collect_ok": true, "last_error": "",
      "skip_count": 0, "restart_count": 0
    },
    { "name": "k8s", "version": "0.9.1", "interval": "60s", "interval_source": "manifest",
      "state": "backoff", "restart_count": 3,
      "last_error": "handshake timeout" },
    { "name": "ssl", "version": "1.0.0", "state": "disabled" }
  ]
}
```

这个端点里的每一项都是**壳自己掌握的事实**，没有任何一项来自插件的自述——插件自述状态那条线已整体砍掉（契约 §2.5）。各字段的归属：

| 字段 | 来源 |
|---|---|
| `name` | `config.yaml` 的键名 / 目录名（两者必须一致，启动时校验） |
| `version` | `agent-plugs/<name>/manifest.yaml` |
| `interval` / `timeout` | manifest 默认值 + config 覆盖，算完后**带上来源标记** |
| `state` / `last_collect_at` / `last_error` / `restart_count` / `skip_count` | 壳观测（进程活着吗、每轮有没有按时回、失败几次、跳过几次） |
| `offline_mode`（顶层） | `config.yaml` 的 `allow_offline`。`true` = 启动自检时连不上 service 但被允许继续跑（§八 第 5 项）——**只看这一个布尔就能区分"这台机器本来就在离线环境"与"它的网络坏了"**，避免以后误判 |

**`interval_source` 是本次新增的一个小字段**（取值只有 `config` / `manifest` / `default` 三个枚举）：排查"为什么这台机器采得比别人勤"时，一眼看出周期是被人改过、还是插件作者给的、还是兜底值。**它不涉及任何插件知识**，纯壳侧信息。

`last_error` 里是**非结构化文本**——来自插件的 `stderr`（壳加前缀转发）或壳自己的失败判定，不是插件主动上报的结构化信息。这是刻意取舍：**让插件把诊断写进日志就够了**，不必为它发明一个协议字段（契约 §2.5）。

请求体**不含任何指标数据**（那是 `/metrics` 的事），只有状态。这是排查"为什么这台机器的图少了一条线"的第一入口。

## 十三、logging

- 标准库 `log/slog`，输出到 stdout（systemd / docker 收集）。
- 插件 `stderr` 逐行读取并加 `[plugs/<name>]` 前缀转发。
- **warn-once 机制**：宽容降级类的告警每个插件每个字段只打一次，避免刷屏。
- 日志级别可配。**默认不打印每轮采集成功的日志**（1500 台 × 4 插件 × 每分钟 = 大量噪音），只打状态变化与错误。

## 十四、goroutine 清单与 recover 边界

壳里只有这几类 goroutine，**每一类都必须有明确的 recover 边界**：

| goroutine | 数量 | 职责 | recover |
|---|---|---|---|
| main | 1 | 生命周期 | **不 recover**（panic 即退出，交给 systemd + 回滚） |
| worker（每插件一个） | = 插件数 | 调度 + collect | **必须 recover**：插件相关代码的 panic 只损失一轮 |
| sender（每插件一个） | = 插件数 | 取槽发送 | **必须 recover**：一次发送的 panic 不能停掉整个 sender |
| stderr 读取 | = 插件数 | 转发插件日志 | **必须 recover** |
| heartbeat | 1 | 心跳 | **必须 recover** |
| config watcher | 1 | 热加载 | **必须 recover** |
| sweeper / HTTP | 各 1 | 状态端点 | 标准库 net/http 自带 recover |

**只有一种情况允许壳退出：启动自检失败或收到 SIGTERM。其余一切异常都要在更小的作用域里被吃掉。**

这条是"降低壳出错风险"最实际的一招：壳代码再小也可能有 bug，但只要每个失败域都有 `recover` 兜底，一个小 bug 最多损失一轮数据，而不是整台机器的采集全停。

```yaml
auto_update: false                      # 冻结：只决定插件制品是否自动更新，壳自身不更新
allow_offline: false                    # 冻结：true = 启动自检"能连通 service"失败时仅告警并继续（§八 第 5 项）
plugins:                                # 容器键冻结
  hard:
    enable: true                        # 壳只解释这三个键
    interval: 15s                       # 覆盖 manifest 的 default_interval（可省略）
    timeout: 45s                        # 覆盖 manifest 的 default_timeout（可省略）
    # 插件自己的参数：壳不看、不校验，插件自己来读这一子树（§5.1）
```

`interval` / `timeout` 的三级取值（config > manifest > 兜底）见 §5.1 与契约 §9。

**改这份 schema 的键名等价于改壳**，必须走壳契约的评审清单。其中 `plugins` 容器键名与三个保留键**同时是插件的接口**（§5.2），改它们还要同步 SDK。

## 十七、待拍板

1. **`hostName` 等历史标签名是否保持**。现状 `hostName`（驼峰）与 `os_version`（蛇形）混用，改名会破坏现有 Grafana 面板。建议**保持不动**，重构不是改名的时机。
2. **状态端点是否默认监听 `127.0.0.1`**。建议是；如果要跨机查看需显式配置并自行保证网络隔离。
3. **`agent_version` 是否继续用 float**。现状多段版本只报 `major.minor`，够用但无法区分 `1.2.0` 与 `1.2.3`。改为独立字符串指标会新增一个指标名（不影响面板），但也意味着面板要加一条。
4. **`manifest.yaml` 里的 `default_interval` / `default_timeout` 由谁写**（周期从"插件自报"搬到静态声明后新增的问题）。两个选项：插件仓库里手写一个 `plugin.meta.yaml`（清晰、可 review，代价是多一份要维护的文件）；或由 `build.sh` 从代码里的常量提取（少一份文件，代价是构建脚本要写提取逻辑，且周期值藏在代码里、review 时看不到）。建议**前者**——周期是插件作者对"这个采集器多久采一次合适"的判断，属于元信息，值得显式写在能被 review 的地方。
