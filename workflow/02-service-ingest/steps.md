# 02 service 接收链路与压测准入 — 步骤

> 目标：service 只保留**一条**链路（声明式），先把旧链路清干净；然后在压测基线下证明它扛得住。**压测不达标不进入下一阶段**（硬闸门）。
> 前置：01。**两项前置决策已定（2026-09-20）**：① 加全局序列闸门 `MaxSeriesTotal = 200000` + `MaxSamplesTotalPerReport = 20 万`；② `heart` 的 `is_active` 超时采用**方案 A**——面板查询改 `absent(is_active{...})` / `is_active != 1`，协议不加字段。
> 参考：`docs/服务端设计.md` §2（删除清单）、§4（接收链路）、§5（动态注册表）、§6（写入路径）、§12（测试与压测）、`docs/插件设计.md §5`（80 个指标名，唯一权威）
> 起点：声明式路径的代码骨架已落盘但**未端到端验证**——`server/Modles/declarative.go`、`server/Metrics/Dynamic.go`、`server/Handers/Dynamic.go`、`hander.go` + `main.go` 的改动。

## 步骤

### S1 删旧链路（先做，因为它是新链路的前置条件）

- **动作**：整体删除「80 个静态定义 + 旧 `data` 路径」这套旧机制：
  | 删什么 | 说明 |
  |---|---|
  | `Metrics/Metric.go` 的 `init()` 里 80 个 `MustRegister` | 只留 `CustomRegistry` 定义 |
  | `Metrics/{Hard,Nginx,Ssl,Container,Controller,Heart,TrafficSwitching}Metric.go` | 6 个文件整体删除 |
  | `Handers/HanderData.go` | 7 个 `Handle*Data` + 项目字典保留、`JoinLabels` 删除 |
  | `Handers/UnRegister*.go`（7 个） | 注销循环统一由 `Dynamic.go` 的 sweeper 承担 |
  | `Handers/timeouts.go` | 按 source 的硬编码阈值表（阈值随指标声明走） |
  | `hander.go` 里的旧路径分发 + `allowedSources` | `SendPayload.Data` 一并删掉 |
- **为什么必须先删**：动态注册用 `registry.Register`（不是 `MustRegister`），与静态定义同名即 `AlreadyRegisteredError` → **400「重名」**。**静态定义不删，新链路一个指标都报不进来**（`§2.2`）。所以这不是"迁移动作"，是新链路的**前置条件**。
- **旧 `data` 路径不能静默丢弃**：保留一个显式拒绝分支——返回 4xx 并在日志打出 `source=hard 的上报走了已废弃路径`。否则将来无从知道还有谁落在旧路径上，那些来源会静默缺数据、直到有人看面板才发现。
- **产出**：删除清单（逐个文件确认，不漏也不多删）。
- **验收**：
  - `grep -rn "HanderData\|UnRegister\|allowedSources\|MaxDataItems" server/` 无残留；
  - `go build ./...` + `go vet ./...` 干净；
  - service 代码量下降约一半。

### S2 抽 `internal/registry` 与 `internal/ingest`

- **动作**：把接收管道（解密 / 解压 / 校验 / 分流）与动态注册表拆成独立包。
- **产出**：`server/internal/registry/`、`server/internal/ingest/`
- **验收**：两包各自的单测全绿（`§12.1` 表的前三行：`registry` / `ingest/decode` / `ingest/validate`）。

### S3 声明式路径端到端打通

- **动作**：带 `metrics` 字段的上报 → 校验 → 动态注册 → 写值 → `/metrics` 可见。
- **验收（两部分）**：
  1. `§12.2` 的 9 条声明式用例全通过：
     - 正常上报 → `/metrics` 可见（校验 HELP、标签顺序 `project` 在第 0 位）
     - `schema: v1` → 400
     - 指标名含 `-` → 400
     - `common` 里有未声明标签 → 400
     - 样本里有未声明标签 → 400
     - 声明 `project` 标签 → 400
     - 同一指标被两个 source 上报 → 第二个 400
     - 超时后序列消失
     - 中文 project 映射正确
  2. **80 个指标名逐个上报均能落地**：写一个 Go 客户端，按 `docs/插件设计.md §5` 的映射表逐个构造最小声明（`name` + `help` + `labels` + 一条 sample），**全部能注册成功且 `/metrics` 可见**——这一步专门证明「已无任何静态定义与之冲突」，是 S1 的兜底验证。

### S4 动态注册防护全套（`§5.4` 防护常量表）

- **动作**：逐项实现并配用例：
  | 防护 | 原因 |
  |---|---|
  | 指标名 / 标签名正则校验、拒绝 `__` 前缀 | `__` 是 Prometheus 保留前缀 |
  | 拒绝插件声明 `project` 标签 | 防伪造项目归属 |
  | **单指标时间序列基数上限** | **最关键**——没有它，插件不断变化标签值就能吃光内存 |
  | 指标名全局唯一 + 跨 source 重名拒绝 | 防一个插件冒名篡改另一个插件的数据 |
  | 动态指标总量上限 | 防无限注册 |
  | 注销阈值下限 `MinTimeout` / 上限 `MaxTimeout` | 防极短阈值导致序列频繁增删 |
  | 标签集合变更时注销重注册 | 让插件能升级改标签而不必重启 service |
- **验收**：表中每一条各一个失败用例 + 一个通过用例。
- **注意**：授权上限类防护必须**同步返回 400**（错误原因要具体），不要静默丢弃——静默丢弃是"数据不见了但没人知道"。

### S5 全局序列闸门 `MaxSeriesTotal`

- **动作**：加全局闸门 `MaxSeriesTotal = 200000`，以及单次上报样本总数上限 `MaxSamplesTotalPerReport = 20 万`。没有前者，"每指标 5 万 × 2000 指标"等于没上限；没有后者，`64 × 20000 = 128 万`条样本可以一次进来。**已定（2026-09-20）**，取值见 `docs/服务端设计.md §5.4`。
- **验收**：超限后拒绝且计数在 `/metrics` 可见。

### S6 自监控指标 `monitor_ingest_*`（§6.6，必须做）

- **动作**：暴露接收量、队列水位、丢弃计数、重注册抑制计数（`reRegisterCount`）。
- **验收**：`/metrics` 里能看到上述四项。
- **为什么必须做**：新链路把"数据从哪来"变成了动态的，**某个 source 静默失效**是最难发现的故障，自监控是唯一能在 service 侧看到它的手段。

### S7 批量写 + 队列满丢弃计数（§6.3、§6.4）

- **动作**：① 批量写把锁持有时长降一个数量级；② **队列满时丢弃并计数，不要沿用现在的"降级为当前 goroutine 执行"**。
- **为什么改**：现有降级"不丢数据"是单体进程下的合理取舍；但 service 侧队列满意味着上游已经超发，此时用当前 goroutine 接着干会把接收协程一起拖住，形成雪崩。**丢弃 + 计数**让故障可见且可控。
- **验收**：压测尖峰被摊平（P99÷均值 < 3），丢弃有计数且不静默。

### S8 换 `klauspost/compress/gzip`（§6.7）

- **动作**：**只服务端换**。壳侧不换的原因：壳契约 I3 的依赖白名单（stdlib + yaml.v3）不能破。
- **验收**：解压耗时下降；端到端用例仍全绿。

### S9 压测基线准入（§12.3）— 硬闸门

- **动作**：用 **Go 写**压测客户端（`vegeta`/`k6` 要自己实现 AES-GCM 请求体，不如直接写）。压测前确认 `ulimit -n` 足够（现有代码启动时会打印 FD 限制与 somaxconn 并在偏低时告警）。
- **验收**（六项全达标，缺一不可）：
  | 项 | 目标 |
  |---|---|
  | 负载 | 1000 并发连接、每请求 50 KB 压缩体、持续 60 秒 |
  | P99 延迟 | < 200 ms（不含异步写入） |
  | 错误率 | 0（不含主动拒绝的非法请求） |
  | 内存 | 稳态 RSS 增长 < 200 MB，无持续增长（观察 10 分钟） |
  | 序列数 | 20 万条序列下 `sweep` 单次 < 100 ms |
  | 打散验证 | 每秒请求数 P99 ÷ 均值 < 3 |
