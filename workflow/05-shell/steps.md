# 05 agent 壳 — 步骤

> 目标：实现唯一需要守护的进程——配置、插件监管、调度、上报、心跳、只读状态端点。**壳是唯一不可就地替换的组件（1000+ 台要动二进制），所以它的全部努力都在"降低出错概率"。**
> 前置：01、03、04。**前置决策已定（2026-09-20）**：启动自检"能连通 service"**默认要求**；`config.yaml` 的 `allow_offline: true` 时退化为"仅告警并继续"，并在状态端点与心跳里标注 `offline_mode`。
> 参考：`docs/壳契约-v1.md`（全文，**冲突时以它为准**）、`docs/壳设计.md`、`docs/插件化架构设计.md §二 §六`
> **预算：内核 ≤1140 行、总量 ≤1580 行**（契约 §10）

---

## 步骤

### S1 配置（`internal/config`）

- **动作**：只读 `plugins.<name>` 下的 `enable` / `interval` / `timeout` 三键，其余键**一律不解释**（透传给插件，由插件经 SDK 读）。
  - 周期与阈值的**三级取值**：config 覆盖 → `manifest.yaml` 的 `default_interval`/`default_timeout` → 兜底 30s
  - 取值后**钳制**（下限/上限）
  - **5 秒热加载**（或 fsnotify 立即感知）
  - 手写合并，**不引配置框架**（`koanf`/`viper` 在壳侧是负资产）
- **产出**：`agent/internal/config/`
- **验收**：
  - 契约 §9 与 `壳设计 §5.1` 的用例；
  - **"配置改错"必须退化为"5 秒后还是旧配置在跑"，而不是整机采集停摆**；
  - `plugins.<name>.enable` 变化 → 启停进程；`interval`/`timeout` 变化 → 下一轮生效且**不重启进程**；其它插件参数变化 → 插件下一轮读生效且**不重启进程**；顶层配置（`metrics_url`/`encrypted`/`project`）→ 热更新内存值，**非法值只告警并保留旧值**。

### S2 契约 8 条不变式（I1~I8）逐条落地

- **动作**：逐条实现 + 给出可执行的验证方式（grep 或测试断言）。
- **验收**：契约 §4 每条不变式的验证均可执行且全过。重点：
  - I1：`internal/proto` 恰好 4 个 json tag，且包外无业务字面量（01 已做，此处回归）
  - I3：依赖白名单
  - I4：不落业务状态——**写盘清单只有 `agent.pid`、`agent-plugs/`**；测试断言临时目录内的文件清单完全匹配

### S3 插件监管（`internal/pluginmgr`）

- **动作**：
  - **懒下载**：按 `index.json` 只为需要的平台拉取；加 **0~30s 抖动**；**只在下发版本变化时下载**
  - **原子替换**：同目录写 `<exe>.new`，替换前 `backupFile` 存 `<exe>.bak`，`os.Rename` 原子替换
  - **握手失败回滚**到 `.bak`；失败计数告警
  - **硬超时 kill**：单轮 collect 超时强杀
  - **连续失败熔断**：连续 N 次失败后停止重启该插件（不影响其它插件）
  - 找不到自己平台的制品时：**保持旧版本并明确告警**，不静默跳过
- **产出**：`agent/internal/pluginmgr/`
- **验收**：**契约 §11 的 10 个假插件矩阵全绿**（含"echo 固定 JSON 的假插件应覆盖壳全部逻辑"——如果需要真实 nginx/k8s 数据才能测，说明业务知识漏进壳了）。

### S4 调度器（`internal/scheduler`）

- **动作**：按生效周期调度；**相位打散**（多插件请求时刻分散）；**同一插件同时只允许一个在途请求**（契约前提）。
- **验收**：多插件启动后请求时刻分散，service 侧观测每秒请求数 P99 ÷ 均值 < 3。

### S5 传输与上报（`internal/transport`）

- **动作**：`JSON → gzip → AES-GCM → POST /metrics_data`，沿用现有实现。
  - 密钥 fail-fast：`SetEncryptionKey(string) error`，启动时非法即退出；热加载路径非法只告警并保留原密钥
  - **`project` 从 `config.yaml` 读出后写进 payload**——插件不知情
  - 上报报文：`project` / `source` / `timestamp` / `schema` / `metrics`
- **验收**：端到端落进 service 且中文 project 映射正确；插件侧代码里搜不到 `project`。

### S6 心跳留在壳内（不下沉为插件）

- **动作**：`is_active` / `agent_version` 两指标由壳自己上报，`source=heart`、标签 `{hostName, project}`、周期 15s、阈值 45s。
- **验收**：停掉壳后 45s 内 service 侧摘掉 heart 序列（`is_active` 置 0）。
- **为什么不下沉**：如果心跳也是插件，"用户停用了 heart 插件"和"主机真的离线了"在服务端看来完全一样。

### S7 只读状态端点（`internal/statusapi`）

- **动作**：展示每个插件的名称 / 状态 / 版本 / 最近一轮时间。**只读**。
- **验收**：见 `ui.md` 的界面清单逐项可查。
- **红线**：**不新增第 5 类输入**（契约 §一）。曾经考虑让壳监听 `127.0.0.1` 供插件 POST 上报状态——**已否决**（本机任意进程可伪造、约 150 行全落内核冻结区、而 stdio 管道本来就够用）。

### S8 失败域隔离

- **动作**：按契约 §5 隔离。壳必须处理子进程退出回收（**容器里注意 PID 1 的僵尸回收**）。
- **验收**：杀掉一个假插件，其余插件与心跳**不受影响**；插件 OOM / 死循环 / FD 泄漏都不影响壳。

### S9 启动自检

- **动作**：契约 §8 的 6 项自检，任一不过**直接退出**并说明原因，交给 systemd `Restart=always` 或容器重启策略接管。**唯一例外**：第 5 项"能连通 service"在 `config.yaml` 的 `allow_offline: true` 时退化为"仅告警并继续"，并在状态端点与心跳里标注 `offline_mode`（**已定 2026-09-20**）。
- **验收**：各项各造一次失败，壳均退出且日志说明具体原因；`allow_offline: true` + service 不可达时**能启动**且 `offline_mode=true`（`ui.md` 验收清单里有这一条）。
- **为什么**：壳"启动后半死"（进程活着但不干活）是最难排查的状态，且自动重启机制不会触发。启动自检是唯一能防住它的手段。
- **为什么允许这个例外**：内网有纯离线机器，硬要求连通会让它们永远起不来。而 `offline_mode` 这个布尔让"这台机器本来就在离线环境"与"它的网络坏了"在状态端点里可区分——**例外必须留痕，否则等于没有防护。**

### S10 行数预算校验

- **验收**：内核（proto + config + pluginmgr + scheduler + transport + heartbeat）≤ 1140 行；外围（statusapi + logging）≤ 180 行；总量 ≤ 1580 行（不含注释与测试）。
- **备注**：数字的意义不在精确，而在**它涨到 2 倍时你能立刻察觉有东西溜进来了**。
